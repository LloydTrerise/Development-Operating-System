## DEVOS-062 — Implement Build Adapter, and DEVOS-063 — Implement Test Adapter

Implemented together: the two capabilities turned out to be identical in shape (input `{ command }`, output `{ exitCode, stdout, stderr }`, risk class R2) and share one provider adapter, so splitting the actual code across two tasks would have meant an artificial seam with nothing on either side of it. Each still has its own capability definition, seed row, and acceptance criteria; this entry covers both.

New `build-run`/`test-run` capabilities (`packages/tools/src/capabilities/`), registered in `capabilityDefinitions` and seeded (`SEED_BUILD_RUN_CAPABILITY_ID`/`SEED_TEST_RUN_CAPABILITY_ID`, ids `...000019`/`...00001a`) exactly like Sprint 4's four. Risk class R2 — the same class as `git-commit`: a local action inside the controlled workspace, not an external/PR-facing action (R3) or a production one (R4).

New `runCommand` primitive (`packages/integrations/src/exec/run-command.ts`) — deliberately **not** `runGit`'s `execFile`-with-a-fixed-argv-array pattern. Build/test commands are free-form strings that routinely need shell features (`&&`, pipes, npm's `--` argument forwarding) no spec names a concrete invocation contract for (flagged in the README); `command` is real, `node:child_process` `exec`, run against a real workspace directory — but only ever sourced from a project's own configured `Integration` (an admin-controlled setting, the same trust level as `repositoryPath`), never from agent or model output, which is never given tool authority directly (Constitution Principle 6/7). Unlike `runGit`, a non-zero exit code does not reject the promise — a failing build/test is expected, meaningful data the capability's own output schema exists to capture, not an infrastructure fault; only a genuine failure to spawn the shell at all (no numeric exit code at all) throws.

`createCommandProviderAdapters` (`packages/application/src/tasks/command-provider-adapters.ts`) wires `runCommand` into DEVOS-052's `ProviderAdapter` shape, mirroring `git-provider-adapters.ts` exactly (a real workspace closed over by the factory; `target` unused since the workspace already carries the repository path) — one adapter object serves both `build-run` and `test-run`, since they differ only in which command runs.

New unit tests: `packages/tools/tests/registry.test.ts` updated for six capabilities; `packages/application/tests/command-provider-adapters.test.ts` (3 cases, all against a real temp directory and real `node -e` subprocess commands — no mocked shell): a real successful command, a real failing command still recorded as a `SUCCEEDED` invocation with `exitCode: 1`, and a real assertion that the command actually executes inside the given workspace directory (`cd`/`pwd`). `packages/application/tests/tool-capabilities.test.ts`'s existing "registers all capability definitions" count updated 4 → 6.

**Live-verified against real Postgres**: ran the seed script; confirmed both new `tool_capabilities` rows exist with the correct `risk_class`/schemas via a direct query (scratch script, removed after use). The unit tests above already constitute live verification of the adapter itself (real subprocess execution, real filesystem), consistent with this sprint's "build/test commands run for real, locally" scoping decision — no additional live-process proof is needed beyond DEVOS-064's own end-to-end use of these two capabilities together. ## DEVOS-064 — Implement Test Evidence Artifact

No agent for Stage 8 — Automated Validation (§18 names no "Validation Agent"; build/test are purely mechanical) — so `runValidationTask` (`packages/application/src/tasks/run-validation-task.ts`) calls the Tool Gateway directly, mirroring how `runDevelopmentAgentTask` applies its change, but with no model call anywhere in the function. New `ToolTaskHandlerDeps` (`packages/application/src/tasks/deps.ts`) — deliberately does not extend any `AgentTaskHandlerDeps` shape, since there is no agent-runtime dependency here at all; otherwise identical to `DevelopmentAgentTaskHandlerDeps` minus the agent/model/PR-provider fields.

Consumes the project's **latest `CODE_CHANGE` artifact**, project-scoped (mirroring DEVOS-061's plan lookup), not run-scoped — this task will eventually run inside the same run as development once DEVOS-066 wires the full workflow, but the handler itself makes no assumption about that positioning, the same discipline DEVOS-061 already established. Builds a fresh workspace via DEVOS-055's `createWorkspace`, then `runGit(['checkout', branchName], ...)` to the `CODE_CHANGE` artifact's own recorded `branchName` — the development task's own ephemeral workspace no longer exists by the time validation runs.

**The build/test commands are read from the project's Git integration configuration** (`buildCommand`/`testCommand`, new optional fields alongside the existing `repositoryPath`/`defaultBranch`) — not a new `Integration` type, since there is no external "build system" being connected to here, just a shell command run against the same repository the Git integration already describes. Missing configuration fails the task with a clear error rather than guessing a command (AGENTS.md §7).

A non-zero build/test exit code does **not** fail this task — `build-run`/`test-run` invocations "succeeding" (Tool-Gateway sense) and the command itself failing are different things; the `TEST_EVIDENCE` artifact's own `passed: boolean` field is exactly where that distinction is recorded, matching §18's "an agent must not claim validation succeeded unless the relevant checks actually ran and passed" — the checks _ran_; whether they _passed_ is data, not this task's own success/failure. This task only throws on a genuine infrastructure problem: no `CODE_CHANGE` artifact, no active Git integration, no configured command, or the Tool Gateway itself rejecting an invocation (policy/schema failure).

The published `TEST_EVIDENCE` artifact (free-text `artifactType`, no schema/union change needed, same as `CODE_CHANGE`) records exactly what §18 requires: commands executed, exit codes, stdout/stderr, the resolved revision (`git rev-parse HEAD` after checkout), a timestamp, and traceability (`derivedFromArtifactId`/`derivedFromArtifactVersionId`) to the `CODE_CHANGE` it validates.

New unit tests: `packages/application/tests/run-validation-task.test.ts` (3 cases, all against a real local git repository with a real committed branch and real `node -e` build/test commands — no mocked shell or git): a real passing build+test publishing a `passed: true` evidence artifact with real captured stdout; a real failing test command publishing `passed: false` without the task itself throwing (proving the pass/fail distinction is data, not a task failure); and a clear thrown error when no build/test command is configured. Not yet wired into `apps/worker`'s dispatcher (no `TOOL_TASK` handler registered, no seeded workflow node) — deferred to when the seeded three-node workflow is built (once DEVOS-065/066's review agent exists too), the same "supporting piece first, full wiring later" sequencing DEVOS-054–056 followed before DEVOS-057/061 wired development in.

**Live-verified**: the unit tests above already constitute live verification (real git repository, real branch checkout, real shell commands, real published artifact against a real local filesystem storage backend) — consistent with how DEVOS-057 was first proven at the package level before DEVOS-061's later apps/worker wiring added its own separate live-verification pass. ## DEVOS-067 — Implement Rework Transitions, and DEVOS-068 — Implement Retry/Rework Limits

Implemented together: the rework trigger and its bound are the same code path (`runReviewAgentTask`'s post-publish block), not two separable changes.

**Seeded workflow, v2 (not an edit to v1).** `SEED_DEVELOPMENT_PATH_WORKFLOW_V2_GRAPH`/`SEED_DEVELOPMENT_PATH_WORKFLOW_V2_VERSION_ID` (`packages/database/src/seed-constants.ts`, id `...00001d`) adds a second, three-node `WorkflowVersion` under the _same_ `development-path` `WorkflowDefinition` DEVOS-061 created — `development` → `validation` (`TOOL_TASK`, no agent) → `review` (`AGENT_TASK`, `review-agent`) — rather than mutating `SEED_DEVELOPMENT_PATH_WORKFLOW_GRAPH` (v1), which Workflow Principle 8 ("published workflow versions are immutable," §8) protects and DEVOS-061's own E2E test still targets by exact version id. Unlike planning → development (DEVOS-061, which crosses a human approval gate and therefore needed a genuinely separate run), development → validation → review has no gate anywhere in the spec's own flow diagram (§7) — so the existing "materialize every node up front, complete once all succeed" engine model already fits this three-node sequence within one run, with no engine changes needed.

**The rework loop itself, however, still can't be a loop within that run** — the same constraint DEVOS-061 already found (`maybeCompleteRun` only completes once every task succeeds; nothing dynamically inserts a task into an already-running run) applies again here. `runReviewAgentTask` resolves it the same way DEVOS-061 did: a `CHANGES_REQUIRED` decision calls `startRunForVersion` directly (`packages/application/src/workflows/run-creation.ts`, the exact same use case the public API route uses) to start a brand-new run of the _same_ workflow version, for the _same_ work item — not a dynamic in-run loop, and not a new workflow/version. New `ReviewAgentTaskHandlerDeps` fields (`memberships`, `workflowDefinitions`, `workflowVersions`, `workflowTasks`, `createDraft`, `startRun`) are exactly `@devos/application`'s own `WorkflowUseCaseDeps` shape, structurally satisfied so `deps` can be passed straight through — the same "reuse the existing use case, don't reinvent it" approach already used for the Tool Gateway.

**Rework count lives on the work item, not scanned from artifact history.** `Artifact` has no `workItemId` field of its own (it's only inside a published version's `metadata`), so counting "how many times has _this_ work item been reworked" by scanning `REVIEW_EVIDENCE` artifacts would need an extra version fetch per candidate and still be a project-wide, not work-item-scoped, count. Simpler and precise: `workItem.metadata.reworkCount`, incremented on every auto-triggered rework. **`MAX_AUTOMATIC_REWORK_CYCLES = 2`** (an explicit, flagged assumption — no numeric bound exists anywhere in the spec corpus, per this sprint's README) — at the limit, no further run is started and `workItem.status` is set to `'REWORK_LIMIT_REACHED'` (`WorkItemStatus` is already documented as an unconstrained opaque string, so this needs no schema change) rather than looping indefinitely.

**"The developer/agent receives the relevant findings" (§20) required a real enhancement to DEVOS-057's existing `runDevelopmentAgentTask`.** It now also looks up the project's latest `REVIEW_EVIDENCE` artifact; when its `decision` is `CHANGES_REQUIRED`, the findings are folded into the model's input as `priorReviewFindings` and recorded as an `ARTIFACT` context-manifest source. `developer/v1`'s prompt text was updated in place (not versioned to v2) to explain this optional field — a backward-compatible addition to context, not a change to the agent's existing input/output contract, and no test anywhere asserts the prompt file's exact byte content (checked directly before editing).

**Found and fixed a real bug this rework loop would otherwise hit on its second cycle.** A rework's development task gets a brand-new workspace (a fresh clone) but typically proposes the _same_ branch name as the rejected attempt — continuing the same change, not starting an unrelated one. `createBranch` (`packages/integrations/src/github/github.adapter.ts`) previously always ran a plain `git checkout -b`, which creates a new local branch from the current default-branch HEAD with no knowledge of the earlier attempt's commit; pushing it back would then be rejected as a non-fast-forward update. Fixed by checking whether `branchName` already exists on `origin` first (`git ls-remote --exit-code --heads`) and, when it does, basing the new local branch on it (`git fetch` + `checkout -b <branch> origin/<branch>`) instead of the default branch — a second (or third) development attempt now correctly continues the same branch rather than failing to push. New regression test: `packages/integrations/tests/github-adapter.test.ts` (two independent clones, same branch name, both commits land in the same real branch history).

New unit tests: `packages/application/tests/run-review-agent-task.test.ts` gained 3 cases (a `CHANGES_REQUIRED` decision starts exactly one real rework run for the right work item and increments its rework count; a `PASS` decision starts none; three consecutive `CHANGES_REQUIRED` calls trigger exactly 2 automatic reworks then escalate on the third) — bringing that file to 6 cases total. `packages/application/tests/run-development-agent-task.test.ts` gained 1 case (a `CHANGES_REQUIRED` `REVIEW_EVIDENCE` artifact's findings are actually threaded into the model's input as `priorReviewFindings`).

Also wired into `apps/worker` in this same task (earlier than DEVOS-064/065's own entries anticipated, since the seeded v2 workflow needed both handlers to exist first): `agent-task-router.ts` gained the `review-agent` case (deps type widened to `DevelopmentAgentTaskHandlerDeps & ReviewAgentTaskHandlerDeps`); `main.ts` registered `runValidationTask` for the new `TOOL_TASK` node type (reusing the same widened deps object structurally, no second construction needed) and added a `REVIEW`-role fixture mapping (`review-v1`) so `AGENT_MODEL_ADAPTER=fixture` can exercise the full three-node pipeline with no live Gemini call.

**Live-verified against real Postgres**: re-ran the seed script; confirmed both `development-path` workflow versions exist correctly (v1 unchanged at its original id, v2 with the correct three-node/two-edge graph) via a direct query, scratch script removed after use. Full package-scoped validation (`@devos/application`, `@devos/integrations`, `@devos/database`, `@devos/worker`): typecheck/lint/test/build all clean. Full end-to-end live verification of the rework loop (a real review triggering a real second development attempt that successfully pushes to the same branch) is deferred to DEVOS-071's E2E test, which exercises this exact path for real rather than through fakes. ## DEVOS-071 — Build/Test/Review E2E

The last task in Sprint 5: a real, spawned-process end-to-end proof of the full development → validation → review pipeline (v2 `development-path` workflow, DEVOS-067/068), including a genuine rework cycle closing end-to-end — not just each stage's own package-level tests in isolation.

**A real rework loop can't be exercised with single static fixtures.** Both the development and review agents' fixture-driven outputs are entirely determined by their fixture file, not reactive to `priorReviewFindings` or any other actual input — so a single `review-v1` fixture can only ever return `PASS`, and a single `developer-v1` fixture can only ever propose the same content. Proving the rework loop for real (a first review returning `CHANGES_REQUIRED`, a development attempt that actually addresses it, a second review returning `PASS`) needed a way for a fixture-driven role to return _different_ results across successive invocations within one worker process. Rather than a test-only hack, built this as a small, generally-useful production-code enhancement: `createFixtureModelAdapter` (`packages/agents/src/fixtures/fixture-model-adapter.ts`) now accepts `AgentFixture | AgentFixture[]` per role — an array is consumed in order across invocations, holding on the last entry once exhausted. Single-fixture roles are completely unaffected (every existing caller keeps working unchanged; new regression case added to `fixture-model-adapter.test.ts`). Driven from `apps/worker/src/main.ts` via new `DEVELOPMENT_FIXTURE_SEQUENCE`/`REVIEW_FIXTURE_SEQUENCE` env vars (comma-separated fixture references, unset everywhere else so every other test/run keeps using its single default fixture).

**Two new real, recorded Gemini fixtures** (same one-off-script precedent as DEVOS-057/065, not `refresh-fixtures.ts`, which is hardcoded to the four planning-path stages): `review-changes-required/v1` (`decision: "CHANGES_REQUIRED"`, 2 real BLOCKER findings: a test failure and an empty STATUS.md) and `developer-reworked/v1` (a development proposal addressing those findings). The second fixture needed two recording attempts: the first, given a fictional "STATUS.md is empty" finding, produced content byte-identical to the existing `developer-v1` fixture's real (non-empty) content — the model correctly had nothing genuinely new to add against a premise that didn't match reality. Caught by a validation assertion in the recording script (`statusFile.content === originalContent` → throw) rather than silently accepting a hollow rework. Re-recorded with an engineered, unambiguous requirement ("add an Owner line naming the DevOS Sprint 5 team," quoting the real prior content verbatim in the finding) that guarantees genuinely different text — the resulting fixture's content is verifiably distinct from `developer-v1`'s.

**A real bug surfaced only by this live rework path, not by any unit test**: the rework's second `runDevelopmentAgentTask` attempt failed at `createCommit` with "nothing to commit." Root cause, found via a direct DB query against the failed task's own output: `developer-v1`'s _static_ fixture content is byte-identical across cycles, and `createBranch`'s DEVOS-067 resume-fix correctly checks out the origin branch that already carries cycle 1's exact commit — so cycle 2 genuinely had nothing new to commit.
