# DEVOS-045 — Implement Approval Model

**Dependencies:** DEVOS-043/044 (a policy may determine that an approval is required); Sprint 1's `workflow_runs`. **Scope:** The `approvals` table and domain entity (`specs/database/poc-database-schema.md` §11.1: `project_id`, `workflow_run_id`, `approval_type`, `status`, `requested_by`, `decided_by`, `decision_reason`, `evidence_reference` JSONB, `requested_at`, `decided_at`) within `packages/domain/src/approval/` and `packages/policy/src/approvals/` (`repository-code-structure.md` §11/§17 — approvals are split between domain entities/state rules and policy-package approval logic; there is no dedicated `packages/approval`). The domain model's conceptual lifecycle (`domain-model.md` §20) draws five states (Required/Requested/Rejected/Changes Requested/Approved) but the documented `status` column lists only three (Pending/Approved/Rejected) — this task reconciles the mismatch explicitly (documented in the decision log) rather than silently picking one. **Acceptance:** An approval request is created bound to specific evidence (a scope hash over the exact artifact/version set being approved, `poc-api-contracts.md` §30); approve/reject decisions verify the scope hash, reviewer role, and current workflow state before taking effect, and are recorded with `decided_by`/`decision_reason`/`decided_at` (§29–§30); the client cannot grant itself authority through the request payload.
