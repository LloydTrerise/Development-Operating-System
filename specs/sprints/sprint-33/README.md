# Sprint 33 — Workflows/Designer & Projects: Restyle + Gap Closure

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.5 (E28 UI/UX Redesign & Full Functional Coverage, fifth sprint).
**Conversion date:** 2026-09-22
**Status:** Converted per explicit user authorization ("start sprint 33, run through without waiting for authorisation between tasks", 2026-09-22). Depends on Sprint 29's theme/nav/`features/`/routing foundation (COMPLETE). No dependency on Sprint 31 or 32.

## Goal

Restyle the Workflow Designer, Workflows, Workflow Library, and Projects pages to the Nocturne mockup's own layout language, and close three real, disclosed UI/client-wrapper gaps: starting a run from a specific historical workflow version, project membership management, and lightweight organisation/project rename settings. Like Sprint 31 (not Sprint 32), this sprint's backlog names "backend gaps" that direct inspection found are not backend gaps at all — see grounding below.

## Grounding (confirmed by direct code inspection before scoping)

- **`POST /workflow-versions/:workflowVersionId/runs` (DEVOS-224's named gap) already exists and is already wired** — `apps/api/src/routes/workflow-runs.ts:31-45` calls the existing, unmodified `startWorkflowRunFromVersion` use case. The real gap is a missing `apps/web/src/api-client.ts` client wrapper (only `startRun`, which calls the sibling `/workflows/:workflowId/runs` route against a workflow's *active* version, exists today) and missing UI. DEVOS-224 is scoped as a client-wrapper + UI story, not a new backend route.
- **All 4 project membership routes (DEVOS-226's named gap) already exist and are already wired** — `apps/api/src/routes/projects.ts:84-131` (`GET`/`POST /projects/:projectId/members`, `PATCH`/`DELETE /projects/:projectId/members/:userId`), backed by the existing, unmodified `listMembers`/`addMember`/`changeMemberRole`/`removeMember` use cases (`packages/application/src/projects/`), each already OWNER-gated via `canManageMembers`/`resolveMembership`, with `assertNotLastOwner` already protecting the last-owner-removal case. The real gap is zero client wrappers and zero UI — this codebase has never had a members panel anywhere. DEVOS-226 is scoped as client-wrapper + UI work only.
- **`GET`/`PATCH /organisations/:organisationId` and `/projects/:projectId` (DEVOS-227's named gap) already exist and are already wired** — `apps/api/src/routes/organisations.ts:39-68` and `apps/api/src/routes/projects.ts:62-82`, backed by the existing, unmodified `updateOrganisation`/`updateProject` use cases, OWNER-gated via `canUpdateOrganisation`/`canUpdateProject`. `updateOrganisation` already has a client wrapper (`api-client.ts:439-447`); `updateProject`/`getProject`(single) do not. `UpdateOrganisationInput` (`packages/domain/src/organisations/organisation.ts:23-27`) only accepts `name`/`status`/`budgetUsd`; `UpdateProjectInput` (`packages/domain/src/projects/project.ts:33-38`) accepts `name`/`description`/`status`/`budgetUsd`. Neither accepts `slug` — a project/organisation's slug is immutable once created, confirmed by the type, not assumed. Per the backlog's own explicit "rename only... no new fields invented" acceptance text, this sprint's settings panel exposes **name** only on each area, even though the route itself also accepts `status`/`budgetUsd` — a deliberate scope choice the approved backlog already made, not a limitation this sprint discovered.
- **No user-directory or user-search capability exists anywhere in this codebase** (confirmed: `apps/api/src/routes/me.ts` only resolves the caller's own identity; no `GET /users` or equivalent route exists). `addMember`'s real `principalId` input has no way to be looked up by name or email. DEVOS-226's "invite/add" action is therefore scoped as adding a member **by raw principal ID** (a text field), not an email-based invite flow — disclosed here as a real, pre-existing platform limitation, not fabricated as a searchable directory.
- **The mockup has no dedicated screen for Workflows (the editor/designer's own definition-picker list) or Workflow Library** beyond the general Designer screen (below) — `Design/DevOS.dc.html`'s own `navGroups` names only a `designer` route and a `null` "Definitions" placeholder (Sprint 29's DEVOS-204 already mapped Workflow Library onto that placeholder slot). Per the backlog's own DEVOS-223 acceptance text ("New theme's table/card patterns"), both `WorkflowsPage.tsx`'s definition-picker list and `WorkflowLibraryPage.tsx`'s table are restyled to the established Nocturne table/list conventions (already used by `WorkItemsPage.tsx`, `ApprovalsPage.tsx`), not to a named mockup layout.
- **The mockup's Designer screen** (`Design/DevOS.dc.html` lines 715-804) is a 3-column grid: a 184px node-palette column (grouped "Node palette" then "Agents"), a flexible canvas column, and a 264px "Selected node" inspector column, with a header row (version badge, running-version note, Diff/Validate/Publish actions). `WorkflowsPage.tsx` today stacks `WorkflowPalette`/`WorkflowCanvas`/`WorkflowNodeInspector` vertically, one above the next, not as the mockup's 3-column layout. DEVOS-222 restyles this into the mockup's real 3-column arrangement — **visual language and layout only**; `WorkflowCanvas.tsx`'s real `@xyflow/react` (React Flow) node/edge creation, drag-drop, and connection logic (confirmed present and unchanged since Sprint 13) is not touched, per the backlog's own explicit "unchanged React Flow behavior" instruction. `WorkflowPalette.tsx` (51 lines, already MUI `Chip`-based) and `WorkflowNodeInspector.tsx` (537 lines) are restyled for layout/visual fit only, not behavior.
- **The mockup's Projects screen** (`Design/DevOS.dc.html` lines 611-647) is a grid-of-cards layout: each card shows the project name/slug, a "current" badge when selected, a 4-stat row, and a health line. `Project` (`api-client.ts:47-58`) carries `status`/`budgetUsd` but no per-project stat aggregates (work-item count, run count, etc.) and no health signal — the mockup's own `p.stats`/`p.health`/`p.healthIcon` fields have no real data source anywhere in this codebase. DEVOS-225 restyles `ProjectsPage.tsx` into the mockup's card-grid *shape* (icon, name/slug, current badge, a bordered stat row) using only real, already-available data (project `status`, and — reusing the same per-project fan-out pattern `HomePage.tsx`/`WorkflowLibraryPage.tsx` already established — a real work-item count via `listWorkItems`), omitting the fabricated health line entirely rather than inventing one. This mirrors the exact "omit rather than fabricate" discipline `HomePage.tsx`'s own DEVOS-208/209 already established for its System Health tile.
- **Project cards are clickable in the mockup** (`cursor:pointer`), and Sprint 29 already established the `/{area}/:id` detail-routing convention (`DetailPageLayout.tsx`, first proven by `/work-items/:id`, then Sprint 31's real DEVOS-213 work item detail). This sprint adds a real `/projects/:id` detail route hosting DEVOS-226's membership panel and DEVOS-227's project settings panel, reusing that convention rather than inventing a new one. Organisation settings (DEVOS-227's other half) has nowhere equivalent to live yet, since `OrganisationsPage.tsx` itself is not restyled until Sprint 34 (backlog §6.6, DEVOS-229) and has no detail route — this sprint adds a minimal inline expand-in-place settings section directly on the existing `OrganisationsPage.tsx` list (matching that page's own current un-restyled list-based structure) rather than pre-building a `/organisations/:id` route a whole sprint ahead of that page's own real restyle. This is a disclosed, low-cost, easily-revisited placement choice, the same kind DEVOS-204 already made and documented for nav placement.
- **Organisation-level membership is explicitly out of scope** — the backlog's own §6.12 (Sprint 39, DEVOS-254/255) is a separate, not-yet-approved future sprint for organisation-scoped membership (`projectId: null` memberships); DEVOS-226 here is project membership only, per its own acceptance text.

## In scope

- **DEVOS-222** — Workflow Designer restyle: 3-column mockup layout (palette/canvas/inspector) on unchanged React Flow behavior.
- **DEVOS-223** — Workflows + Workflow Library restyle: Nocturne table/list visual language, no named mockup layout.
- **DEVOS-224** — Start run from a specific workflow version: closes the `POST /workflow-versions/:id/runs` client-wrapper/UI gap on the Workflow Library's version history.
- **DEVOS-225** — Projects restyle: mockup's grid-of-cards layout using only real data (status, real work-item count), omitting the fabricated health line.
- **DEVOS-226** — Project membership management: closes the 4 member-route client-wrapper/UI gap with a real panel on a new `/projects/:id` detail page — add by principal ID (no directory exists), list, change role, remove.
- **DEVOS-227** — Organisation & Project settings: closes the client-wrapper/UI gap for `updateProject`/rename-only settings on both areas — a section on the new `/projects/:id` page, and an inline expand-in-place section on the existing `OrganisationsPage.tsx` list.
- **DEVOS-228** — Validation, documentation, and gap disclosure.

## Out of scope

Any new backend route, use case, or domain field. Organisation-level (org-scoped) membership (Sprint 39). A full `OrganisationsPage.tsx` restyle or `/organisations/:id` detail route (Sprint 34). An email/name-based member-invite directory (no such capability exists anywhere in this codebase). Fabricated project health/stat fields the mockup shows but no real data source backs. Any change to `WorkflowCanvas.tsx`'s drag/connect/node-creation behavior, `updateDraftWorkflow`/`publishWorkflowVersion` semantics, or `changeMemberRole`/`removeMember`'s existing last-owner protection.
