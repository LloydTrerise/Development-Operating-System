# Sprint 35 — Artifact Library & Viewer (net-new, largest gap)

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.7 (E28 UI/UX Redesign & Full Functional Coverage, seventh sprint).
**Conversion date:** 2026-09-22
**Status:** Converted per explicit user authorization ("convert to specs and implement. Implement the whole sprint without asking for authorisation", 2026-09-22). Depends on Sprint 29's theme/nav/`features/`/routing foundation (COMPLETE) and the reserved-but-empty "Artifacts" nav group it created. No dependency on Sprints 30–34, though it reuses their established `Paper`/`PanelHeader` restyle convention, `DetailPageLayout`'s `/{area}/:id` routing convention, and the dense-table list pattern (`WorkItemsPage.tsx`/`AgentsPage.tsx`).

## Goal

Build the epic's largest confirmed net-new UI gap: a real Artifact Library (search/filter/browse) and a real Artifact Viewer (detail, version history, diff), backed entirely by the artifact routes that already exist and are already tested — this sprint adds zero backend routes or contract changes, per the epic's own Delivery Principle (`specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §7/§9). It also closes the two disclosed "partial" gaps the epic's own backend/UI audit found for evidence display: `RunCard.tsx`'s hardcoded version-1 evidence fetch and `ApprovalsPage.tsx`'s name/type-only evidence resolution both gain a real link through to the new Artifact Viewer.

## Grounding (confirmed by direct code inspection before scoping — unlike Sprints 31/33/34, nothing here needed correcting against the backlog's own framing)

- **All 6 backend routes this sprint depends on already exist, unmodified** (`apps/api/src/routes/artifacts.ts`): `GET`/`POST /projects/:projectId/artifacts`, `GET /artifacts/:artifactId`, `GET /artifacts/:artifactId/versions`, `GET /artifacts/:artifactId/versions/:version`, `GET /artifact-versions/:artifactVersionId`, `GET /artifacts/:artifactId/provenance`. Confirmed via direct read, not assumed from the backlog's own claim.
- **Only 3 of the 6 have a client wrapper today** (`listArtifacts`, `getArtifactVersion` by number, `getArtifactVersionById`) — `createArtifact`, `getArtifactForPrincipal` (the real application-layer name for `GET /artifacts/:artifactId`), and `listArtifactVersions` are genuinely unwrapped, exactly matching DEVOS-234's own claim.
- **`POST /projects/:projectId/artifacts` returns only the created `Artifact`, not `{ artifact, version }`** — confirmed by direct read of `apps/api/src/routes/artifacts.ts`'s handler (`return toArtifactDto(artifact);`), even though the underlying `createArtifact` application-layer function returns both. `createArtifact`'s client wrapper is typed `Promise<ApiResult<Artifact>>`, matching the real route response, not the richer application-layer return value.
- **A real, disclosed content-fetch gap, found during this sprint's own grounding, not by the backlog**: `ArtifactStorage.get(uri)` (`packages/storage/src/artifact-storage.ts`) can resolve a version's `contentUri` back to its raw stored bytes, but no API route anywhere calls it — every artifact route returns only `contentUri`/`contentHash` (an opaque content-addressed pointer and its hash), never the decoded content itself. Per this epic's own Delivery Principle (§7/§9: "Sprints 29–38 require no backend/API change"), this sprint does **not** add a content-serving route. The Artifact Viewer's "Content" panel (ui-spec.txt §20) is honestly scoped to what a version's own `metadata` field already carries (populated with real structured data for evidence artifacts — `decision`/`passed`/`findings`/etc., per `run-review-agent-task.ts`/`run-validation-task.ts`/`run-release-task.ts`) plus the real `contentType`/`contentUri`/`contentHash` pointer fields, disclosed as the closest real substitute for a raw-content preview — not a file viewer.
- **`getArtifactProvenance` (`GET /artifacts/:artifactId/provenance`) returns no more than what the artifact's own `provenance` field already carries** — confirmed by direct read of `packages/application/src/artifacts/get-artifact-provenance.ts`: it returns `{ workflowRunId?, workflowTaskId? }` only, sourced from the same `artifact.workflowRunId`/`artifact.workflowTaskId` fields `toArtifactDto` already serializes into the Artifact DTO's own `provenance` object. The domain contract's richer `ArtifactProvenance` type (`packages/contracts/src/artifacts.ts`: `origin`, `agent`, `contextManifestId`, `sourceRefs`) is not implemented by any real code path. DEVOS-234 still wires this wrapper exactly as named — this finding is disclosed in the Viewer's own UI text, not silently hidden or worked around.
- **`Artifact`'s DTO has no `createdBy` field** — confirmed by direct read of `toArtifactDto`: only `ArtifactVersion` carries `createdBy`. `ui-spec.txt` §19's "Filter: ... author" is therefore not buildable as an artifact-level filter without an N-version fan-out; DEVOS-235 filters by type/status/name-search only (all real, no fabricated author filter) and discloses the gap.
- **No raw-diff library exists in this monorepo** (`grep` for `diff`/`jsdiff`/`diff-match-patch` in every `package.json` found nothing). DEVOS-237 adds one small, pure, unit-tested line-diff function local to the artifacts feature rather than a new dependency, per `AGENTS.md` §11 ("avoid unnecessary dependencies... prefer the existing repository architecture") — diffing the same pretty-printed `metadata` JSON the Content panel already shows, not raw file bytes (which no route serves, per the content-fetch gap above).
- **Evidence artifacts' real one-hop relationship**: `REVIEW_EVIDENCE`/`TEST_EVIDENCE`/`RELEASE_EVIDENCE` versions' `metadata.derivedFromArtifactId` (confirmed real, per `DEVOS-BUILD-STATE.md`'s own Sprint 21/DEVOS-168 grounding) points back to the `CODE_CHANGE` artifact they evaluate — already present in data this sprint fetches anyway, zero extra request. This is the one real "Relationships" signal (ui-spec.txt §20) that exists; DEVOS-236 surfaces it as a link when present and discloses that no downstream/reverse index exists (would need a full-project artifact-version scan, out of this sprint's own bounded scope).
- **`RunCard.tsx`'s hardcoded `getArtifactVersion(artifact.id, 1)` calls** (`apps/web/src/features/runs/RunCard.tsx:135,140`) and **`ApprovalsPage.tsx`'s evidence resolution stopping at `{ artifactName, artifactType }`** (`apps/web/src/features/approvals/ApprovalsPage.tsx:27,113`) were both confirmed by direct read, matching DEVOS-238's own claim exactly.
- **The "Artifacts" nav group already exists, empty** (`apps/web/src/App.tsx:101`, reserved by Sprint 29's DEVOS-204) — DEVOS-235 populates it with a single `/artifacts` entry, matching the same reservation precedent Sprint 36 (Integrations) will later fill.

## In scope

- **DEVOS-234** — Artifact API client completion: `createArtifact`, `getArtifactForPrincipal`, `listArtifactVersions`, `getArtifactProvenance` client wrappers against the 4 existing, unmodified routes named above; `ArtifactVersion`'s frontend type widened with the already-returned-but-untyped `contentUri`/`contentHash` fields (zero backend change — the DTO already includes them, only the frontend type was narrower).
- **DEVOS-235** — Artifact Library page: new `features/artifacts/ArtifactLibraryPage.tsx` at `/artifacts` (search by name, data-derived type/status filter chips mirroring `WorkItemsPage.tsx`'s DEVOS-212 convention, row-click navigation to `/artifacts/:id`), a "New artifact" creation form exercising `createArtifact` (mirroring `AgentsPage.tsx`'s own creation-form convention), and the "Artifacts" nav entry populated.
- **DEVOS-236** — Artifact Viewer: new `features/artifacts/ArtifactViewerPage.tsx` at `/artifacts/:id` (`DetailPageLayout`, `backTo="/artifacts"`): header (type/version/status), a version selector (defaults to latest), Content (contentType/contentUri/contentHash pointer plus the selected version's `metadata`, pretty-printed, disclosed as the closest real substitute for raw content), Metadata (project name via `ProjectContext`, `createdBy`, `createdAt`), Provenance (via `getArtifactProvenance`, disclosed as identical to the artifact's own `provenance` field), Relationships (the one real `metadata.derivedFromArtifactId` one-hop link, when present).
- **DEVOS-237** — Artifact version history & diff: a version-history table on the Viewer (every version, `listArtifactVersions`); a two-version picker rendering an added/removed/unchanged line diff (new local `diff-lines.ts` pure function, unit-tested) over each version's pretty-printed `metadata` JSON — disclosed as a metadata diff, not a raw-content diff, per the content-fetch gap above.
- **DEVOS-238** — Replace hardcoded version references with real navigation: `RunCard.tsx`'s Artifacts accordion rows and its Test/Review evidence panels gain a real "View in Artifact Viewer" link to `/artifacts/:id`; `ApprovalsPage.tsx`'s evidence list rows become real links to `/artifacts/:id` (using `getArtifactVersionById`'s already-present `artifactId` field) instead of plain, unlinked text.
- **DEVOS-239** — Validation, documentation, and gap disclosure: full monorepo validation green; full real `tests/e2e` suite green; new unit tests for the 4 new wrappers and the diff function; live dev-server verification.

## Out of scope

Any new backend route, use case, or domain field (no content-serving route, no richer provenance, no `createdBy` on the Artifact DTO, no reverse/downstream relationship index). A raw file-content viewer (no route serves decoded bytes). A real per-artifact "Review" panel (comments/approval state) beyond the existing evidence-to-approval linkage already visible from the Approvals page itself — no reverse "approvals citing this artifact" lookup is built, since it is not named in DEVOS-236's own acceptance text and would require an unscoped full-project approvals scan. `Export` (ui-spec.txt §19) — no supported-representation-generation capability exists anywhere in this codebase. Any change to `createArtifact`/`getArtifactVersion`/`getArtifactVersionById`/`listApprovalsForRun`/`listApprovalsForProject` semantics. A third-party diff library.
