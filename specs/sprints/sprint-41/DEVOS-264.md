# DEVOS-264 — Search UI

**Priority:** P0 | **Estimate:** 1.5d
**Depends on:** Sprint 40's DEVOS-262 (`GET /projects/:id/search?q=...`).
**Depended on by:** DEVOS-265 (reuses this story's result-rendering/navigation logic inside the Command Palette).

## Scope

The top-bar search input — real, but new; `README.md`'s grounding found no such input exists yet in `apps/web/src/App.tsx`, only in the `Design/DevOS.dc.html` mockup — is wired to Sprint 40's real `GET /projects/:id/search?q=...` route, with results grouped by entity type per `ui-spec.txt` §27, respecting the caller's permissions (already enforced server-side via `resolveMembership`).

## Implementation

- `api-client.ts`: new `ProjectSearchResults` interface (`projectId`, `query`, `workItems: WorkItem[]`, `artifacts: Artifact[]`, `workflows: WorkflowDefinitionSummary[]`, `agents: Agent[]` — reusing every existing entity type, no new shape invented) and `searchProject(projectId, query)` wrapper (`GET /api/v1/projects/:projectId/search?q=<encoded>`).
- New `features/search/GlobalSearch.tsx`: a real MUI `TextField` (search icon adornment) rendered in `App.tsx`'s `AppBar`, disabled with a placeholder when no project is selected. Query changes debounce 300ms (mirroring `useWorkflowGraphValidation`'s established `DEBOUNCE_MS` convention) before calling `searchProject`; a query under 2 trimmed characters clears results without a request. Results render in a MUI `Popper`/`Paper` dropdown below the input, grouped into "Work Items" / "Artifacts" / "Workflows" / "Agents" sections (only non-empty sections shown), each row showing the entity's real name/title plus its type/status chip. Loading, error (via the same `ApiResult` shape every other wrapper uses), and zero-results states are all real, not placeholders. Selecting a result navigates and closes the dropdown: work item → `/work-items/:id`; artifact → `/artifacts/:id`; agent → `/agents/:id`; workflow → `/workflow-library?workflowId=:id`. Escape or an outside click closes the dropdown without navigating.
- `WorkflowLibraryPage.tsx`: a new `useSearchParams()` read of `workflowId`; once `rows` has loaded and contains a matching definition, it is expanded (`setExpandedId`, triggering the existing `listWorkflowVersions` fetch the same way clicking the row's own expand button does) and scrolled into view (`document.getElementById` + `scrollIntoView({ block: 'center' })` on a `TableRow` id keyed by definition id) — mirrors `ApprovalsPage.tsx`'s `?approvalId=` convention, adapted to this page's plain-table shape (no split-pane exists here to just `setSelectedId` into).

## Out of scope

A `/runs/:id` or `/workflows/:id` detail route (`README.md`'s disclosed pre-existing gaps). Including `knowledge_sources` in results (Sprint 40's own boundary). Fuzzy/typo-tolerant matching beyond Postgres's own `plainto_tsquery` behavior (DEVOS-261, unchanged). The Command Palette itself (DEVOS-265, this story only supplies the reusable rendering/navigation logic it calls into).

## Acceptance

`pnpm --filter @devos/web typecheck lint build` clean. New `apps/web/tests/api-client.test.ts` case(s) for `searchProject`. Live-verified against a real running `apps/api`/dev server and the real seeded "DevOS POC" project: typing a real matching query in the top-bar search shows real, grouped, non-empty results; selecting a work item/artifact/agent result navigates to its real detail page; selecting a workflow result navigates to `/workflow-library` with the matching row expanded and scrolled into view; a query below 2 characters or with no matches shows no dropdown/a real empty state, not an error.

## Actual results

Implemented exactly as scoped. `api-client.ts`'s `ProjectSearchResults`/`searchProject` mirror the route's own DTO shape exactly, reusing `WorkItem`/`Artifact`/`Agent`/`WorkflowDefinitionSummary` unchanged (the workflow shape's two extra optional fields are simply absent on search results, confirmed safe since they were already optional). `GlobalSearch.tsx` renders in `App.tsx`'s `AppBar` between the project selector and the API-status indicator; `use-project-search.ts` is the one shared debounced-search hook both `GlobalSearch` and `CommandPalette` (DEVOS-265) call, avoiding a second implementation as scoped. `SearchResultGroups.tsx` is the one shared grouped-result renderer both surfaces use.

`pnpm --filter @devos/web typecheck lint build` clean (confirmed individually, then again as part of the full monorepo run below). `apps/web/tests/api-client.test.ts` grew from 56 to 57 cases (`DEVOS-264: searches a project at the real cross-entity search route`, asserting the real `?q=` URL encoding).

**Live-verified against a real running `apps/api`/dev server and the real seeded "DevOS POC" project** (a throwaway Playwright script run from inside `apps/web`, deleted afterward): typing "rollback" in the top-bar search produced a real `GET .../search?q=rollback` request and a real, grouped, non-empty dropdown (a real `Work Items` section, matching real seeded "Rollback test" work items); clicking the first result navigated to its real `/work-items/:id` detail page; a 1-character query produced zero network requests and no dropdown, confirmed via network-event capture, not just a UI screenshot.

**One real, pre-existing gap found and disclosed while live-verifying the workflow deep-link, not introduced by this story**: `WorkflowLibraryPage.tsx`'s own `Promise.all(projects.map(project => listWorkflows(project.id)))` fan-out (Sprint 14's DEVOS-135) never resolves against the real seeded organisation's current state — a direct query found **4416** real accumulated stray `Project` rows belonging to that one organisation (no delete route exists for `Project`, the same accepted-gap pattern Sprint 37/39 already established for `Agent`/`Integration`, now compounded by 40 sprints of live-verification projects never being cleaned up). A 30-second timeout probe against plain `/workflow-library` with **no** query parameter at all showed the identical zero-rows-rendered symptom, proving this predates and is unrelated to this story's own `?workflowId=` addition — it is `WorkflowLibraryPage`'s pre-existing architecture, now genuinely broken by real accumulated data volume, not a regression. Out of this UI-only search/palette sprint's scope to fix (a page-wide performance rewrite of an unrelated existing page). To verify the `?workflowId=` deep-link logic itself for real, a Playwright network-route interception filtered only the already-real `/projects` list response down to the one real "DevOS POC" project (every other response, including the real workflow-versions fetch, was untouched) — with a bounded project set, the linked row (`00000000-0000-4000-8000-000000000004`, the real seeded "Intake to Artifact" definition) rendered, scrolled into view, and expanded correctly (a real `GET /workflows/.../versions` 200 fired, and real version-history content appeared), confirming the deep-link code is correct and the fan-out volume is the sole blocker. An unknown `?workflowId=` value was also confirmed to load the page without error and highlight nothing, under the same bounded interception.

Zero console/page errors throughout the bounded-verification run (confirmed via a `page.on('console'/'pageerror')` capture); the earlier unbounded run against the real, full 4416-project catalog produced thousands of `net::ERR_INSUFFICIENT_RESOURCES` errors (browser connection-pool exhaustion from thousands of concurrent per-project `fetch()` calls) — further evidence for, not a consequence of, the gap disclosed above.
