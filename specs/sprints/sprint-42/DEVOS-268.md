# DEVOS-268 — Event-consumption and notification materialization

**Priority:** P0 | **Estimate:** 1.5d
**Depends on:** DEVOS-267 (`Notification`/`NotificationRepository`).
**Depended on by:** DEVOS-269 (routes read what this story writes).

## Scope

Wires `publishPendingEvents()` (`packages/database/src/repositories/publish-events.ts`, dead code since Sprint 1) into a real periodic consumer loop in `apps/worker` for the first time, with a new sink that resolves recipients for a triggering `EventEnvelope` and materializes one `Notification` row per recipient. Recipient rule, as narrowed and disclosed in `README.md`'s grounding: all project members of any role (via the event's own `projectId` → `MembershipRepository.listForProject`) — the backlog's additional "specific approval assignee" clause does not apply, since no assignee concept exists on `Approval` anywhere in this codebase.

## Implementation

- New `packages/application/src/notifications/deps.ts`: `NotificationMaterializationDeps { notifications: NotificationRepository; memberships: MembershipRepository }`.
- New `packages/application/src/notifications/materialize-notification.ts`: `createNotificationEventSink(deps): EventSink` — for a received `EventEnvelope`, short-circuits (no-op) when `envelope.projectId` is undefined (every event in the trigger list carries one in practice; a defensive, disclosed no-op rather than a thrown error for any that don't); otherwise resolves recipients via `deps.memberships.listForProject(envelope.projectId)` and calls `deps.notifications.create(...)` once per distinct `principalId`, each with `type: envelope.type`, `referenceType: envelope.aggregateType`, `referenceId: envelope.aggregateId`, `read: false`, `createdAt: envelope.occurredAt`.
- `packages/application/src/index.ts`: barrel-export the two new files.
- `apps/worker/src/main.ts`: a new `notificationDrainTimer`, mirroring `metricsSnapshotTimer`'s exact shape (DEVOS-093) — `setInterval` calling `publishPendingEvents(outboxEvents, notificationSink)`, configurable via `NOTIFICATION_DRAIN_INTERVAL_MS` (disabled at `0`), `.unref()`'d, cleared in the existing `shutdown()` handler. `outboxEvents`/`notifications`/`memberships` repositories constructed alongside the process's other repositories.

## Out of scope

Any change to `publishPendingEvents()`/`consoleLogEventSink()` themselves. Any per-approval assignee/routing concept (disclosed gap, out of this sprint). Any notification-preference/mute/digest mechanism. Any route (DEVOS-269).

## Acceptance

`pnpm --filter @devos/application --filter @devos/worker typecheck lint test build` clean. New unit test(s) for `createNotificationEventSink` in `packages/application/tests/notifications.test.ts` (fakes-based): materializes one row per project member for a real envelope, zero rows for an envelope with no `projectId`, correct `type`/`referenceType`/`referenceId` mapping. Live-verified against real Postgres and a real running `apps/worker`: a real triggering action (e.g. requesting a real approval) produces a real outbox event that the drain loop picks up within one interval and materializes into real `notifications` rows for every real project member.

## Actual results

Implemented exactly as scoped, with one real, necessary, disclosed addition beyond the story's own text. `NotificationMaterializationDeps`/`createNotificationEventSink` added at `packages/application/src/notifications/{deps,materialize-notification}.ts`, barrel-exported from `packages/application/src/index.ts`. No `EventSink` type is imported into `packages/application` (it lives in `@devos/database`, which `packages/application` does not depend on, per `AGENTS.md` §13) — `createNotificationEventSink` returns a plain `(envelope: EventEnvelope) => Promise<void>`, structurally compatible with `EventSink`, and `apps/worker/src/main.ts` (which depends on both packages) assigns it directly with no cast needed. `apps/worker/src/main.ts` gained a new `notificationDrainTimer`, mirroring `metricsSnapshotTimer`'s (DEVOS-093) exact shape — unconditional `setInterval`, configurable via `NOTIFICATION_DRAIN_INTERVAL_MS` (default `5000`, disabled at `0`), `.unref()`'d, cleared in the existing `shutdown()` handler — calling `publishPendingEvents(outboxEvents, notificationSink)` each tick.

**A real, necessary, disclosed finding surfaced during this task's own live verification, not anticipated by the backlog or this file's original scoping**: `outbox_events` had accumulated a real backlog of **27,178 unpublished rows** in this environment's own real Postgres — every event ever written since Sprint 1, since nothing had ever called `publishPendingEvents()` before this task. `listUnpublished` orders oldest-first with a 50-row limit, so a freshly-inserted real test event sat behind the entire backlog and was not reached within any practical live-verification window (confirmed: it was still unpublished after a real 5-second worker run). Materializing that entire historical backlog into real per-member `Notification` rows the moment this feature's drain loop started would have flooded every real project member with tens of thousands of historical, already-resolved notifications — not what "Notifications (Backend)" is for, and not a reasonable reading of the backlog's own intent. Fixed with a new migration, `packages/database/migrations/0044_mark_pre_notification_outbox_backlog_published.ts`, mirroring `0031_projects_add_project_type_id.ts`'s own established "backfill existing rows before a new feature starts reading them" precedent — a single bulk `UPDATE outbox_events SET published_at = now() WHERE published_at IS NULL`, run once, so notifications begin from the point this feature goes live forward. `down()` is a deliberate, disclosed no-op (which rows were originally unpublished is information the up-migration itself destroys — nothing correct to restore). Confirmed via direct Postgres query: 27,178 → 0 unpublished rows after the migration, in a single fast bulk statement (not a slow per-row loop).

New tests: `packages/application/tests/notifications.test.ts` (4 cases, fakes-based) — materializes one notification per real project member for a real envelope; a real no-op for an envelope with no `projectId`; zero notifications for a project with no members; only notifies members of the triggering project, not an unrelated one.

`pnpm --filter @devos/application --filter @devos/worker typecheck lint build` clean; `pnpm --filter @devos/application test`: **41/41 test files, 342/342 tests green** (including the 4 new cases). `pnpm --filter @devos/database typecheck lint build` re-confirmed clean after adding the new migration. `prettier --check` clean across every file this task touched.

**Live-verified against real Postgres and a real running `apps/worker`** (started via `node dist/main.js`, `NOTIFICATION_DRAIN_INTERVAL_MS=1000`, stopped cleanly afterward): after the backlog migration ran, a freshly-inserted real `ApprovalRequested` outbox event (for the real seeded "DevOS POC" project) was picked up by the real drain loop within one interval and materialized into **4 real `notifications` rows**, one per real project member (`seed-user`, `devos-agent-runtime`, `devos-tool-invocation-approval-test` ×2 — a real pre-existing duplicate membership row, not introduced by this task), each with the correct `type`/`referenceType`/`referenceId`/`read: false`. Test rows (the outbox event and the four materialized notifications) were deleted afterward; the real seeded project's real membership/outbox state is otherwise unchanged.
