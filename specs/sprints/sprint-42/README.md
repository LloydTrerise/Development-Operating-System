# Sprint 42 — Notifications (Backend)

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.15 (E28 UI/UX Redesign & Full Functional Coverage, thirteenth sprint).
**Conversion date:** 2026-09-23
**Status:** Converted per explicit user instruction ("proceed", 2026-09-23, in direct response to a position report naming Sprint 42 as the recorded next action). Depends on Sprint 29's project-scoped `resolveMembership()`/`MembershipRepository` conventions (reused, not re-invented) and the already-existing, currently-dead `publishPendingEvents()` outbox-drain mechanism (Sprint 1) and `EventEnvelope`/`EventType` contract (`packages/contracts/src/events.ts`, unchanged since Sprint 1).

## Goal

Close the first of the two remaining named-but-backend-less `ui-spec.txt` areas the backlog tracks for this phase (§2.4): a real notification system. This sprint is backend-only — DEVOS-267 adds the `Notification` entity/table/repository, DEVOS-268 wires the outbox's existing drain function into a real periodic consumer for the first time and materializes per-recipient rows from it, and DEVOS-269 exposes `GET`/`PATCH` routes. Sprint 43 (not this sprint's scope) wires the header notification bell UI on top of the routes this sprint ships.

## Grounding (confirmed by direct code inspection before scoping)

- **`publishPendingEvents()` re-confirmed still genuinely dead code, exact location matches the backlog's own citation.** `packages/database/src/repositories/publish-events.ts` — a real, already-tested, idempotent outbox-drain function (`listUnpublished` → sink → `markPublished`/`recordFailure`) taking an injectable `EventSink` — has exactly one real sink today (`consoleLogEventSink`, a `console.log` stand-in from Sprint 1) and is called nowhere in `apps/worker`/`apps/api` outside its own test file. DEVOS-268 gives it its first real caller and its first real sink.
- **The full `EventType` trigger list already exists, unchanged since Sprint 1, confirmed by reading `packages/contracts/src/events.ts` directly**: `WorkflowRunStarted`, `WorkflowTaskStarted`, `WorkflowTaskCompleted`, `WorkflowTaskFailed`, `AgentExecutionStarted`, `AgentExecutionCompleted`, `ArtifactCreated`, `ArtifactPublished`, `ApprovalRequested`, `ApprovalGranted`, `ApprovalRejected`, `ToolInvocationStarted`, `ToolInvocationCompleted`, `ValidationFailed`, `WorkflowRunCompleted`, `WorkflowRunFailed`. Every `EventEnvelope` already carries `aggregateType`/`aggregateId`/`projectId?`/`correlationId` — real, already-populated fields DEVOS-267's `Notification` entity reuses directly (as `referenceType`/`referenceId`) rather than inventing a parallel shape.
- **A real, disclosed narrowing of the backlog's own DEVOS-268 recipient-rule text, found by reading the real `Approval` entity (`packages/domain/src/approval/approval.ts`) directly, not assumed from the backlog's wording.** The backlog says the recipient rule is "all project members of any role, plus, where applicable, the specific approval assignee" (confirmed by the user 2026-09-21). No such concept exists on `Approval` today: its real fields are `requestedBy` (who triggered the request, not who must decide it) and `decidedBy` (populated only after a decision, i.e. after the notification would already need to have been sent) — there is no `assignedTo`/`approverId`/single-decider field anywhere in this codebase; any project member may decide any pending approval (subject to `enforceSeparationOfDuties`, which only ever _excludes_ `requestedBy`, never _names_ a single required decider). DEVOS-268 will therefore resolve recipients for every trigger type, `ApprovalRequested` included, via "all project members of any role" only — the "plus the specific approval assignee" clause is real backlog text but describes a concept this codebase has never built; DEVOS-268's own task file records this as a disclosed scope narrowing, not a silent drop, and flags it as a candidate follow-up (a real per-approval assignee/routing concept) outside this sprint.
- **A real, already-proven home for a new periodic consumer, confirmed by reading `apps/worker/src/main.ts` directly.** This process already runs one unconditional `setInterval`-based periodic job outside the task dispatcher's own tick (`metricsSnapshotTimer`, DEVOS-093, disabled via `METRICS_SNAPSHOT_INTERVAL_MS=0`, `.unref()`'d so it never blocks process exit, cleared in the existing `shutdown()` handler) — DEVOS-268's own drain loop mirrors this exact shape (a new `notificationDrainTimer`) rather than overloading `task-dispatcher.ts`'s own queue-claiming tick (DEVOS-121/145's `resumeReadyWaits`/`expirePending`), which is deliberately scoped to workflow-task/approval state, not cross-cutting event consumption.
- **Real per-table column grounding for DEVOS-267, mirroring `audit_records`' (`packages/database/migrations/0012_audit_records.ts`) closest existing precedent — a per-recipient, append-mostly, timestamped row referencing another entity — rather than inventing a new shape.** Unlike `audit_records`, a notification has no defined organisation-scoped or project-scoped listing route in this sprint's own acceptance (`GET /notifications` is for "the current principal" only, DEVOS-269) — so, per §9's "no new business rule invented," the table carries only the columns the backlog literally names (recipient principal id, type, reference to the triggering entity, read/unread state, timestamp) plus a `read_at` nullable timestamp (needed to actually persist DEVOS-269's mark-as-read action, not a new concept beyond "read/unread state"). No `organisation_id`/`project_id` column is added — nothing in this sprint's three stories needs one, and adding one speculatively would be exactly the kind of unrequested future-proofing §8 warns against.

## In scope

- **DEVOS-267** — `Notification` domain entity + `NotificationRepository` (`packages/domain/src/notifications/notification.ts`); `notifications` table via new migration `0043_notifications.ts`; `packages/database/src/repositories/notifications.ts` implementing the repository against real Postgres; barrel exports in both packages.
- **DEVOS-268** — A new sink (materializes a trigger `EventEnvelope` into one `Notification` row per resolved recipient) plus a new periodic drain loop in `apps/worker/src/main.ts` calling `publishPendingEvents()` for the first time ever, real or against real Postgres.
- **DEVOS-269** — `GET /notifications` (current principal's own rows) and `PATCH /notifications/:id/read` routes.
- **DEVOS-270** — Validation, documentation, and gap disclosure, including a real end-to-end proof that a real triggering event produces a real notification row for the right recipient(s).

## Out of scope

Any notification bell/list UI or API-client wrapper (Sprint 43). Any real per-approval "assignee"/routing concept (disclosed narrowing above — a real gap, not this sprint's to close). Any change to `EventEnvelope`/`EventType`/the outbox table itself. Any notification-preference/mute/digest/email/push mechanism — none is named by the backlog and none exists anywhere in this codebase today. Any change to `consoleLogEventSink`'s continued use, if any, elsewhere.
