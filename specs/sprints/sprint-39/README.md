# Sprint 39 — Organisation Membership, Tool Capability Control & System Health

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.12 (E28 UI/UX Redesign & Full Functional Coverage, eleventh sprint — no §6.11 exists in the source document).
**Conversion date:** 2026-09-22
**Status:** Converted and authorized per explicit user instruction ("convert to specs and start sprint 39 with a standing run through the sprint authorisation", 2026-09-22) — a single instruction covering both conversion and full end-to-end execution, matching the pattern established for Sprints 30–38. Depends on Sprint 29's theme/nav/routing foundation (hard prerequisite for the whole epic) and Sprint 33's DEVOS-226 project-membership UI (styling precedent for DEVOS-255).

## Goal

Close three of the four backend-plus-UI gaps §2.4 named as included in this epic: real organisation-level membership management, a real enable/disable control for tool capabilities, and a real aggregated system-health signal on the Home dashboard. Unlike Sprints 29–38, this sprint adds real new backend routes and one new repository method — the epic's own Delivery Principle ("every net-new UI story wires a real, already-existing backend route," §3) does not hold for Sprints 39–43, exactly as §7's own dependency table already discloses.

## Grounding (confirmed by direct code inspection before scoping)

- **DEVOS-254 (org membership) — backlog's sizing confirmed accurate.** `Membership.projectId` is genuinely nullable (`packages/domain/src/projects/membership.ts:9`); `resolveOrganisationMembership` (`packages/application/src/organisations/membership-access.ts`) already exists and is already used by `getOrganisationCostReport`/`getOrganisationEngineeringReport`/`listAuditRecordsForOrganisation`; the full CRUD pattern exists verbatim at project scope (`packages/application/src/projects/{add-member,remove-member,change-member-role,list-members}.ts`) as a direct template, each using `resolveMembership`/`canManageMembers`/`assertNotLastOwner`. **One real, necessary addition beyond the backlog's own text**: `MembershipRepository` has no method to list all memberships within an organisation (only `listForProject`/`listForPrincipal`) — needed both for the new `GET /organisations/:id/members` route and for an org-scoped last-owner guard. A new `listForOrganisation(organisationId)` is added, scoped to return only org-level (`projectId: null`) rows — the rows this feature actually manages, not every project-level membership in the org too (a real, disclosed scoping choice, not a generic cross-join). `OrganisationUseCaseDeps` (`packages/application/src/organisations/deps.ts`) gains `auditRecords: AuditRecordRepository`, additive, mirroring `IntegrationUseCaseDeps`/`PolicyUseCaseDeps`'s own identical addition — needed so `membership.added`/`membership.removed`/`membership.role_changed` can be audited at org scope exactly as they already are at project scope (`AuditRecord.projectId` is already optional, confirmed by direct read, so an org-scoped audit record with no `projectId` is not a new pattern — `policy.published` already does this).
- **DEVOS-256/257 (tool capability enable/disable) — the backlog's own placement claim is false, confirmed by direct inspection, not assumed.** `ToolCapability.status: 'ACTIVE' | 'DISABLED'` exists and enforcement already works (`invoke-tool.ts:338` already rejects a non-`ACTIVE` capability) — that much the backlog gets right. But **"within Project Types, where capabilities are already surfaced" is false on both counts**: grep across `apps/web/src/` for `ToolCapability`/`toolCapabilities` returns zero matches — no capability of any kind is surfaced anywhere in the UI today; and `ToolCapability.projectId` scopes a capability to a real `Project`, not a `ProjectType` — no `ProjectTypeToolCapability`/template-clone concept exists anywhere (confirmed by grep), so `ProjectTypesPage.tsx` (which edits org-wide **templates**, with no real project selected at all) is not even the right kind of page to host a real per-project capability toggle. **Corrected placement**: a new "Tool Capabilities" panel on `ProjectDetailPage.tsx`, alongside the real per-project "Members"/"Settings" panels Sprint 33 already established there — the actually-consistent home for real, per-project, mutable state. `ToolCapabilityRepository` has no update path at all (only `getById`/`getByProjectAndKey`/`listForProject`/`create`) and no route of any kind exists to list or mutate a project's capabilities — `registerCapability`/`listCapabilitiesForProject` (`packages/application/src/tools/`) are real but were never wired past `apps/api`'s own internal `toolInvocationSummaryDeps` construction (confirmed by grep — no `apps/api/src/routes/*.ts` file references either function). **DEVOS-256's scope is therefore corrected to include both a new `GET /projects/:id/tool-capabilities` list route (reusing the already-written, already-tested `listCapabilitiesForProject` unchanged) and the new `PATCH .../:capabilityId` toggle route** — DEVOS-257's UI literally cannot function with the toggle route alone, since nothing lists capabilities today. `ToolUseCaseDeps` gains `auditRecords: AuditRecordRepository`, same additive shape as DEVOS-254 above. A new `canManageToolCapabilities(role): boolean` is added to `packages/domain/src/projects/authorization.ts`, mirroring that file's own established one-function-per-consequential-action convention (`canRegisterIntegration`, `canPublishAgent`, etc.) exactly, rather than reusing an existing function whose name doesn't describe this action.
- **DEVOS-258/259 (system health) — re-confirms the position report's own finding: DEVOS-259 is net-new tile creation, not wiring an existing placeholder.** `apps/web/src/features/home/` has zero health-related UI (confirmed by grep); `use-home-dashboard-data.ts` already computes `activeIntegrationCount` client-side as "the one real 'health' signal that exists," by its own comment. The existing unauthenticated `GET /health` (`apps/api/src/routes/health.ts`) checks only database connectivity and takes no project scope — left completely unmodified, per §9's "no change to an existing route's contract." A **new, separate, authenticated, project-scoped** `GET /projects/:id/system-health` is added instead, matching how every other Home-dashboard signal is already project-scoped. **A real, disclosed design decision**: the new route does not invent an "ok/degraded" verdict for integrations or capabilities themselves — a `DISABLED` capability (DEVOS-256's own new toggle) is a deliberate admin action, not a fault, so fabricating a health judgement from it would misrepresent an intentional state as a problem. The route instead reports real counts (`integrations: {total, active}`, `capabilities: {total, active}`) plus the one signal that **does** have genuine ok/error semantics today — database connectivity, reused unchanged from `database.checkHealth()` — composed at the route layer exactly as `createHealthRoutes` already does it, keeping the new application-layer use case free of any `DatabaseClient` dependency (so it stays unit-testable with fakes, like every other use case in this codebase). `HomePage.tsx`'s existing 5-tile KPI grid (`repeat(5, 1fr)`) widens to 6, adding a new tile — the same "widen the grid, add a tile" shape DEVOS-242 already established for the existing Integrations tile, not a replacement of it.
- **Zero schema/migration changes anywhere in this sprint** — confirmed for all three features: `Membership.projectId` is already nullable; `ToolCapability.status` is already a column; system health needs no new persistence at all, only new read-side aggregation. Matches the backlog's own §2.4 sizing exactly.
- **No client-side role/permission gating precedent exists anywhere in this codebase** (re-confirmed, same finding every net-new-UI sprint since Sprint 37 has made) — the new Members/Capabilities panels render their mutating actions unconditionally; a real backend 403 surfaces through the existing `ErrorAlert` convention, matching DEVOS-226/245/248 exactly.

## In scope

- **DEVOS-254** — Organisation-level membership backend: `listForOrganisation` repository method; `addOrganisationMember`/`removeOrganisationMember`/`changeOrganisationMemberRole`/`listOrganisationMembers` use-cases (mirroring the project-scoped four exactly, at org scope); `GET`/`POST /organisations/:id/members`, `PATCH`/`DELETE /organisations/:id/members/:userId`.
- **DEVOS-255** — Organisation-level membership UI: extends `OrganisationsPage.tsx`'s existing per-row inline-expand pattern (Sprint 33's DEVOS-227 Settings toggle) with a second "Members" toggle, reusing DEVOS-226's list/add/change-role/remove interactions.
- **DEVOS-256** — Tool capability enable/disable backend: `ToolCapabilityRepository.updateStatus`; `canManageToolCapabilities`; `setToolCapabilityStatus` use-case; `GET /projects/:id/tool-capabilities` (new — reuses the already-written `listCapabilitiesForProject` unchanged) and `PATCH /projects/:id/tool-capabilities/:capabilityId`.
- **DEVOS-257** — Tool capability enable/disable UI: a new "Tool Capabilities" panel on `ProjectDetailPage.tsx` (corrected placement — see grounding above), listing capabilities with a status toggle per row.
- **DEVOS-258** — System health aggregation backend: `getProjectSystemHealth` use case (integration/capability real counts); `GET /projects/:id/system-health` (composes the use case's counts with the existing `database.checkHealth()` at the route layer).
- **DEVOS-259** — System health UI: a new sixth Home-dashboard KPI-row tile wired to DEVOS-258's route (grid widens from 5 to 6 columns).
- **DEVOS-260** — Validation, documentation, and gap disclosure: full monorepo validation green; full real `tests/e2e` suite green; live dev-server verification of all three features; `DEVOS-BUILD-STATE.md`/`DEVOS-ROADMAP.md` updated only on the user's explicit approval, per `AGENTS.md` §18/§19 (this document does not authorize touching either).

## Out of scope

Any schema/migration change (none needed, confirmed above). Any change to an existing route's request/response contract (`/health`, project-scoped members routes, `invoke-tool.ts`'s enforcement, etc. — all left unmodified). Any new authorization model beyond `role === 'OWNER'` checks reusing `resolveMembership`/`resolveOrganisationMembership` exactly as-is. Real user identity, invite, or configurable roles (§9, excluded from the whole epic). A dedicated `/system-health` page or route beyond the one new Home tile. Any change to `ProjectTypesPage.tsx` (confirmed the wrong home for capability toggling — left untouched).
