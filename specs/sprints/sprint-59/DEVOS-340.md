## Real bugs found

Two real bugs were found and fixed during this sprint's own implementation — disclosed here per `AGENTS.md` §7/§17, not silently corrected:

1. **`packages/database/src/repositories/organisations.ts`'s `create()` hardcoded `initialisation_enforcement_exempt_at: null`**, ignoring whatever value the caller's `Organisation` object actually carried — inconsistent with every other optional field on that same method (`budget_usd`, `owner_principal_id`, both `?? null`). This was caught by the full real `tests/e2e` suite, not a unit test: `knowledge-platform-marketplace-pilot.test.ts`'s own cross-organisation scenario constructs a throwaway organisation directly through this repository and marks it exempt (to keep that scenario testing cross-org authorization, not this sprint's unrelated gate — see bug 2) — the hardcoded `null` silently discarded that flag, so the fixture organisation was never actually exempt and the new gate intercepted the request before the real cross-org check could run. Fixed to mirror `owner_principal_id`'s own established `?? null` pattern.
2. **The same e2e test's own fixture organisation had no real setup at all** (no project/LLM-provider/policy) and, before bug 1's fix, wasn't reliably exempt either — so DEVOS-337's new gate, not the test's own intended `installKnowledgeSource` cross-organisation check, was the first thing to reject the request, changing the response from a masked `404` to a `403 DEVOS_ORGANISATION_NOT_INITIALISED`. Confirmed as a real, legitimate consequence of this sprint's own change (not a defect in the gate) — the acting principal has genuine project-level standing in that organisation (having created its target project as a fixture step), which `resolveOrganisationMembership`'s own pre-existing, Sprint-58-predating project-level fallback (`packages/application/src/organisations/membership-access.ts:39-42`) already treats as sufficient standing to read that organisation's real live status; the same principal could already read that status directly via `GET .../initialisation-status` before this sprint shipped. Fixed by marking the test's own throwaway organisation exempt in the fixture itself (mirroring a real pre-existing, migration-`0062`-backfilled organisation) so the test's own original intent — cross-organisation rejection — is what actually executes, undisturbed by this sprint's unrelated new gate.

No other bugs were found. Every migration, domain type, repository, use case, route wiring, and new test passed validation clean on first implementation, apart from these two, both caught by the full real `tests/e2e` suite exactly as that suite exists to do.

## Written confirmation: exactly which routes are gated, which are exempt, and what stayed the same

**What was added** — one new, real, server-side enforcement layer, and nothing else:

- A new application-layer guard (`requireOrganisationInitialised`) and a new, distinct, structured error (`OrganisationNotInitialisedError` / `DEVOS_ORGANISATION_NOT_INITIALISED`, `403`, naming exactly which of `hasProjectType`/`hasLlmProvider`/`hasPolicy` are still outstanding).
- A new `resolveOrganisationId` hook on the `Route` type, and real wiring of it across **47 of the 62 real mutating routes** in `apps/api/src/routes/*.ts` — the complete, verified disposition of every one is `DEVOS-338.md`'s own completed audit table.
- **3 routes are deliberately, permanently exempt as setup routes** regardless of an organisation's status: `POST /projects`, `POST /organisations/:organisationId/llm-providers`, `POST /organisations/:organisationId/policies`.
- **12 routes are exempt because they are not organisation-scoped at all**: organisation creation itself (`POST /organisations`), every `ProjectType` management route (6, pre-existing, ungated-by-design), every platform-operator route (2), every registration-token route (2), and the recipient-scoped notification-read route (1).
- A new, narrow, nullable `Organisation.initialisationEnforcementExemptAt` field and migration `0062`, real-backfilled for every one of this environment's 3 pre-existing organisations in the same migration.

**What stayed completely unchanged**:

- Sprint 58's own live computation of `INITIALISED`/`hasProjectType`/`hasLlmProvider`/`hasPolicy` — `getOrganisationInitialisationStatus` was not modified at all; this sprint only adds a consumer of it.
- Every one of the 15 "exempt (not organisation-scoped)" routes' own real behavior — live-verified unaffected in step 10 above.
- `project.create`'s own pre-existing ungated _authorization_ (any principal may still create a project) — this sprint's gate is a different, additive axis (whether the project's organisation is initialised), not a reversal of that authorization, and the setup-route exemption means it is never even reached for `POST /projects` regardless.
- Every genuinely pre-existing organisation's own real behavior — live-verified unaffected, against real production data, in step 9 above.

## Gap disclosure

- **Real test-database residue from this session's own debugging, not yet cleaned up.** Two throwaway organisations (`Other Org …`, each with one project and one membership) were left behind in the real dev Postgres database by this sprint's own earlier, pre-fix runs of `knowledge-platform-marketplace-pilot.test.ts` (its own cleanup step is only reached on a passing assertion — see "Real bugs found" above). An attempt to delete them directly was blocked by this session's own permission controls (destructive action on a shared resource) rather than worked around. Disclosed here plainly, per `AGENTS.md`'s own "when in doubt, ask" governance — the user's explicit confirmation is needed before this residue is removed; it does not affect correctness of anything this sprint built, only tidiness of the shared dev database.
- **DEVOS-338's own three-category disposition (Gated / Exempt-setup-route / Exempt-not-organisation-scoped) is a real, load-bearing design choice, not an incidental default.** In particular, "configuration" of an already-satisfied requirement (e.g. `PATCH`/`DELETE`/`reorder` on `organisation_llm_providers` once one exists, or publishing an already-created organisation-wide policy) is deliberately **Gated**, not exempt — only the one action that transitions a requirement from `false` to `true` is exempt. A future sprint that wants a broader "any mutation touching one of the three subsystems" exemption would need to revisit this deliberately narrow reading.
- **No database transaction spans the guard's own read and the route handler's own write.** A request could, in principle, pass the gate and then have the underlying organisation's status change (e.g. via a concurrent request) before the handler's own write completes — an already-accepted class of race this codebase's own pre-existing mutation paths do not close either (mirrors Sprint 57/`DEVOS-332.md`'s own identical disclosed gap for token redemption).
- **The two agent/knowledge-source "install" routes gate on the _target_ project's organisation** (from `body.targetProjectId`), not the `:organisationId` route param (which only names where the shared marketplace is being browsed from) — a deliberate, disclosed choice (see `DEVOS-338.md`'s own audit table), not an oversight, but worth flagging as the one place in this sprint's wiring where the gated organisation is not the one most visually adjacent in the URL.
- The pre-existing, cross-cutting "access control catalogue fails to load against a fake/null test database" stderr noise (present in every `@devos/api` test run, unrelated to any sprint's own code) remains unrelated and untouched.
