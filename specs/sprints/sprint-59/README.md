## ⚠ Disclosed decision — how "backfill to `INITIALISED`" works when nothing is persisted (read before implementing DEVOS-339)

The backlog's own §6.4/DEVOS-339 assumes the literal shape of Sprint 50's `ASSIGNEE = reporter_id` backfill precedent (`specs/sprints/sprint-50/DEVOS-305.md`): a one-time `UPDATE`/`INSERT` setting a stored value before a new restriction goes live. That shape does not exist here. Sprint 58's own disclosed decision (`specs/sprints/sprint-58/README.md`) deliberately persists **nothing** for `INITIALISED` — it is computed live, on every read, from three already-real tables (`projects`, `organisation_llm_providers`, `policies`). There is no `organisations.status` value and no tracking-table row to backfill.

Direct inspection at conversion time confirms this creates a real, load-bearing tension DEVOS-339 must resolve, not paper over: under live computation, **every genuinely pre-existing organisation that has not already touched all three subsystems would report `initialised: false` the instant this sprint's guard goes live** — exactly the outcome backlog §4 says must not happen ("nothing already in production breaks"). Three options were weighed:

1. **A timestamp cutover compared against `Organisation.createdAt`** (already a real field, `packages/domain/src/organisations/organisation.ts:22`) against a single new deploy-time config value naming when enforcement went live — no new column, mirroring the `GEMINI_API_KEY`/`DEVOS_BOOTSTRAP_PLATFORM_OPERATOR_SUBJECT` single-env-var precedent. **Rejected**: correctness depends on an operator setting the cutover value to match the exact deploy instant; get it wrong (in either direction) and either some pre-existing organisations are wrongly blocked or some post-epic organisations are wrongly exempted, with no record of which is which after the fact.
2. **Fabricate a real `Project`/`organisation_llm_providers`/`Policy` row for every organisation that lacks one**, so live computation genuinely (if synthetically) reports `initialised: true` with no special-casing anywhere in the guard. **Rejected**: this is the exact "separate, disconnected manual checklist" dishonesty Sprint 58's own README explicitly built live computation to avoid — it would inject synthetic setup data into a real organisation's real Projects/Policies/LLM-provider lists purely to satisfy a check the organisation never asked to satisfy, a visible, false behavior change to that organisation's own data, not "zero behavior change."
3. **A new, narrow, one-time-set exemption field on `Organisation` itself, distinct from `INITIALISED`** — e.g. `initialisationEnforcementExemptAt: string | undefined` (nullable timestamptz). A migration backfills it (a real, literal, set-based `UPDATE`, mirroring DEVOS-305's own precedent exactly) for every organisation that exists as of this sprint's migration; every organisation created afterward always has it `null` (never subject to grandfathering, per backlog §4's own "applies to organisations created after this epic ships" scope line). The guard consults this field first — exempt organisations always pass, regardless of live status; non-exempt organisations are judged purely by DEVOS-334's existing live computation, completely unchanged.

**Decision: option 3.** Full reasoning recorded here per `AGENTS.md` §7/§28. This does **not** reopen or contradict Sprint 58's own decision — `INITIALISED` itself, and the three booleans behind it, stay exactly as Sprint 58 left them: computed live, never cached, never stored. What DEVOS-339 adds is a categorically different, one-time historical fact ("was this organisation exempted from a rule that did not exist when it was created") that — unlike a derived status — can never go stale, because nothing about it is ever expected to change after the one backfill migration runs. `Organisation.ownerPrincipalId`'s own precedent (a narrow, dedicated `setOwnerPrincipalId` method rather than folding a distinct-semantics field into the generic `update()`) is the structural model DEVOS-339 follows for this new field.

## ⚠ Disclosed correction — real dependency order differs from the backlog's numeric order (read before sequencing implementation)

The backlog lists DEVOS-337 → 338 → 339 → 340 as if strictly sequential. Direct inspection finds a real hazard in following that literal order during implementation: if DEVOS-338 wires the guard into the live route surface before DEVOS-339's backfill migration has actually run against real data, every genuinely pre-existing organisation is blocked the moment DEVOS-338 ships, for however long the gap is before DEVOS-339 lands — precisely the regression backlog §4 forbids. **DEVOS-338 therefore really depends on both DEVOS-337 (the guard must exist) and DEVOS-339 (the exemption data must already be real before the guard is wired in) — not on DEVOS-337 alone.** This does not change the four tasks' own IDs or numbering (mirroring how Sprint 58 left DEVOS-335 numbered after DEVOS-334 despite depending on it, and disclosed the dependency in prose rather than renumbering) — it is recorded here so whoever implements this sprint does not ship DEVOS-338 ahead of DEVOS-339 inside the same deploy. DEVOS-337's own acceptance is fully testable against an in-memory fake of the exemption dependency, independent of DEVOS-339's real migration landing first.

## Goal

Make the `INITIALISED` status Sprint 58 made genuinely _readable_ also genuinely _enforced_: a mutating request scoped to an organisation that is not `INITIALISED` (and not grandfathered in, per the decision above) is rejected server-side, with a distinct, structured error naming which of the three requirements are still outstanding — not a generic 403, and not merely a UI-level nudge. Every pre-existing organisation keeps working exactly as before. The three routes that let an organisation _complete_ its own setup (creating its first `Project`, its first `organisation_llm_providers` row, its first organisation-wide `Policy`) are never blocked by this gate, regardless of the organisation's current status — otherwise no organisation could ever become `INITIALISED` in the first place.

## Grounding (confirmed against the real, current implementation)

- **The real route surface is larger than the backlog's own estimate.** The backlog's §6.4/DEVOS-338 text (written before Sprints 56–58 existed) estimates "~105 routes." A direct count against the real, current `apps/api/src/routes/*.ts` (30 files) at conversion time finds **131 real routes** (`GET`/`POST`/`PATCH`/`DELETE`), of which **62 are mutating** (`POST`/`PATCH`/`DELETE` — the same three methods `apps/api/src/app.ts`'s existing `isMutatingMethod` check, used by DEVOS-091's rate limiter, already treats as "expensive"). DEVOS-338's own audit table works from this real, current count, not the backlog's stale estimate.
- **`apps/api/src/app.ts`'s `handleRequest`** already has exactly the chokepoint this sprint's guard needs, and an established precedent for using it: `isMutatingMethod` is computed once, after routing and authentication, before the handler runs, and gates the existing mutation rate limiter (DEVOS-091/118) the identical way this sprint's own initialisation guard needs to gate mutating requests. The guard is added at this same point, reusing the pattern rather than inventing a second one.
- **`apps/api/src/http/router.ts`'s `Route` interface** (`method`, `pattern`, `protected`, `handler`) has no field today describing which organisation (if any) a route is scoped to. This is new, required surface for this sprint — not an oversight found late; the backlog's own DEVOS-338 story ("confirming exactly which routes are gated and which are exempt — not assumed blanket coverage") already anticipates that this doesn't exist yet.
- **The route surface is not uniformly organisation-keyed.** Direct inspection of `apps/api/src/routes/organisations.ts` confirms routes there carry `:organisationId` directly in `params`. Most other mutating routes (`apps/api/src/routes/projects.ts`, `work-items.ts`, `workflows.ts`, `agents.ts`, `artifacts.ts`, `knowledge-sources.ts`, etc.) carry `:projectId` instead, requiring a lookup (`ProjectRepository.getById(projectId).organisationId`) to resolve the owning organisation. A further subset (`apps/api/src/routes/policies.ts`'s `POST /policies/:policyId/publish`, and equivalents elsewhere keyed by an entity id rather than a project or organisation id) require an entity-specific lookup to find the owning project or organisation. **There is no single generic resolver that covers every route** — DEVOS-337 defines the guard and a per-route resolution hook; DEVOS-338 is the real, route-by-route work of attaching the right resolver (or none, for a genuinely unscoped route) to each of the 62 mutating routes.
- **`apps/api/src/http/errors.ts`'s `HttpError`** already carries an optional, typed `details?: Record<string, unknown>` field, unused by every existing subclass except where a caller populates it — the natural place to carry which requirement(s) are outstanding, with no change needed to `HttpError` itself. **`packages/domain/src/errors.ts`'s three application-layer error classes (`NotFoundError`/`ForbiddenError`/`ValidationError`) carry no structured payload at all** — none of them fit "a distinct, disclosed error shape... naming which requirement(s) are still outstanding" (backlog §6.4/DEVOS-337) without inventing a new, typed field. DEVOS-337 adds one new application-layer error class for exactly this reason, per `AGENTS.md` §12's "fix the underlying type/design issue" rather than overloading an existing class's plain `message` string.
- **`PolicyRepository.listForOrganisation`** (`packages/database/src/repositories/policies.ts:79-89`, confirmed unchanged since Sprint 58) filters only on `organisation_id`/`project_id IS NULL` — not on publish status. `hasPolicy` (DEVOS-334) therefore already flips to `true` the moment an organisation-wide `Policy` is _created_, before it is ever published. `POST /policies/:policyId/publish` does not need to be a setup-exempt route for this reason — creation alone already satisfies the requirement DEVOS-334 detects.
- **`Organisation.createdAt`** (`packages/domain/src/organisations/organisation.ts:22`) and **`OrganisationRepository.setOwnerPrincipalId`** (a narrow, dedicated method for one distinct-semantics field, DEVOS-290) are the two real precedents DEVOS-339's own new field/method follow.
- **`specs/sprints/sprint-50/DEVOS-305.md`** is the real, grounded precedent for "backfill via a real migration before a new restriction goes live, sequenced explicitly, with an explicit, disclosed `down()` no-op" — the shape DEVOS-339's own migration follows, adapted for organisations rather than work items.
- **Not in scope, confirmed unaffected by this sprint:** `POST /organisations` (registration-token-gated creation, Sprint 57), `POST /platform-operators` and `DELETE /platform-operators/:id` (Sprint 56), `POST /registration-tokens` and `DELETE /registration-tokens/:id` (Sprint 57) are none of them scoped to an _existing_ organisation being mutated — platform operators and registration tokens sit above/outside the organisation tier entirely (backlog §2.8), so none of them has an organisation to gate against. `ProjectType`/`ProjectTypeWorkflow`/`ProjectTypeAgent` management remains "entirely ungated... a consistent, pre-existing architectural choice" (`specs/sprints/sprint-51/DEVOS-310.md:45`), untouched by this sprint for the same reason `project.create`'s own ungated-by-design authorization (a completely separate axis from this sprint's initialisation gate) is untouched.

## In scope

- **DEVOS-337** — The initialisation-gate guard itself: a new application-layer check, a new distinct error type carrying which requirement(s) are outstanding, and the `Route`-level resolution hook DEVOS-338 attaches per route.
- **DEVOS-338** — A real, route-by-route pass over the current, real 62-mutating-route surface, attaching the guard's resolution hook to every route that is genuinely organisation-scoped and not one of the three setup-completing routes, and confirming (not assuming) every other route's exemption.
- **DEVOS-339** — The disclosed backfill mechanism (see above): migration, `Organisation`-level exemption field, real set-based backfill of every pre-existing organisation.
- **DEVOS-340** — Validation, documentation, and gap disclosure.

## Out of scope

Everything Sprint 60 (guided setup wizard UI, full-epic pilot) owns — per the epic map in `specs/DEVOS-ORGANISATION-ONBOARDING-BACKLOG.md` §5. No change to Sprint 58's own live-computation decision for `INITIALISED`/`hasProjectType`/`hasLlmProvider`/`hasPolicy` themselves — those stay exactly as `getOrganisationInitialisationStatus` already computes them. No change to `project.create`'s existing ungated _authorization_ (any principal may create a project) — this sprint's gate is an orthogonal axis (whether the project's _organisation_ is initialised), not a reversal of that authorization. No change to `POST /organisations`, platform-operator routes, or registration-token routes (see grounding above — none are organisation-scoped mutations this gate applies to). No UI (Sprint 60 owns surfacing a blocked mutation's error to a user).
