# DEVOS-338 — Route-by-route pass wiring the guard into the real ~131-route surface

**Priority:** P1
**Depends on:** DEVOS-337 (the guard, error, and `resolveOrganisationId` hook must exist). **DEVOS-339 must also have already run its real backfill migration against real data before this task's own wiring is exposed to real traffic** — see the sprint README's "real dependency order" disclosure; this is a real dependency this task has on DEVOS-339 that the backlog's own numeric ordering does not show.
**Depended on by:** DEVOS-340 (validation exercises this task's own wiring).

## Scope

A real, route-by-route pass over every route in `apps/api/src/routes/*.ts`, mirroring E28 Sprint 44's (`DEVOS-274`) and E29 Sprint 51's (`DEVOS-310`) own full-surface-re-audit precedent: go through the surface item by item, record the real, confirmed outcome for each, and treat "no gap found" as a real, checked result rather than an assumption. This task's own required output is the completed audit table below (filled in with the real, verified outcome for every one of the 62 real mutating routes at implementation time — the table here records the categories and known members found during conversion-time grounding, not yet the exhaustive per-route disposition itself, which is this task's own implementation work), plus the actual `resolveOrganisationId` wiring for every route the table marks "Gated."

## Implementation

For each of the 62 real mutating (`POST`/`PATCH`/`DELETE`) routes across the 30 files in `apps/api/src/routes/`, assign exactly one disposition:

- **Gated** — organisation-scoped, not a setup-completing route. Gets a real `resolveOrganisationId` implementation.
- **Exempt (setup route)** — one of the three routes that let an organisation complete a requirement DEVOS-334 detects. Deliberately never gated, regardless of the organisation's status, because gating it would make it impossible for a non-initialised organisation to ever become initialised.
- **Exempt (not organisation-scoped)** — the route has no organisation to gate against at all (platform-level, or acts before an organisation exists).

Known members of each category, confirmed by direct inspection at conversion time (this task's own implementation must confirm every remaining route in `apps/api/src/routes/*.ts` not named below — this list is a grounded starting point, not a claim of exhaustive coverage yet):

**Exempt (setup route) — exactly three, per the sprint README's grounding:**

- `POST ${prefix}/projects` (`apps/api/src/routes/projects.ts`) — creating a `Project` always carries a `ProjectType` (defaulted if unpicked); this is literally how `hasProjectType` becomes true.
- `POST ${prefix}/organisations/:organisationId/llm-providers` (`apps/api/src/routes/organisation-llm-providers.ts`) — how `hasLlmProvider` becomes true.
- `POST ${prefix}/organisations/:organisationId/policies` (`apps/api/src/routes/policies.ts`, DEVOS-139) — how `hasPolicy` becomes true (creation alone, not publish — confirmed by the sprint README's grounding on `listForOrganisation`'s own filter).

Every _other_ mutating route on these same three resources (e.g. `PATCH`/`DELETE ${prefix}/organisations/:organisationId/llm-providers/:providerId`, the `reorder` route, `POST ${prefix}/policies/:policyId/publish`) is **Gated**, not exempt — only the one action that satisfies a still-outstanding requirement is exempt; managing an already-satisfied requirement further is an ordinary organisation-scoped mutation like any other. This is a deliberately narrow reading of backlog §6.4's "LLM provider configuration" language, chosen because it matches exactly what DEVOS-334 detects (existence of at least one row, not any particular configuration state of it) — confirm or widen at implementation time if a narrower reading proves too restrictive in practice.

**Exempt (not organisation-scoped) — confirmed by direct inspection at conversion time:**

- `POST ${prefix}/organisations` (organisation creation itself — no existing organisation to gate against, and already the subject of Sprint 57's own separate, disclosed gate).
- `POST`/`DELETE ${prefix}/platform-operators*` (Sprint 56) and `POST`/`DELETE ${prefix}/registration-tokens*` (Sprint 57) — both sit above/outside the organisation tier (backlog §2.8); neither has an organisation to resolve.
- Every mutating route under `apps/api/src/routes/project-types.ts` — `ProjectType`/`ProjectTypeWorkflow`/`ProjectTypeAgent` management is "entirely ungated... a consistent, pre-existing architectural choice" (`specs/sprints/sprint-51/DEVOS-310.md:45`), a global, cross-tenant template resource with no owning organisation at all.

**Gated — every other mutating route**, resolved via one of two real mechanisms found by direct inspection:

- **Direct**: routes already carrying `:organisationId` in `params` (`apps/api/src/routes/organisations.ts`'s own member/ownership-transfer routes; `PATCH ${prefix}/organisations/:organisationId`) resolve it with no lookup.
- **Via project**: the majority of the remaining mutating surface (`work-items.ts`, `workflows.ts`, `workflow-runs.ts`, `agents.ts`, `artifacts.ts`, `knowledge-sources.ts`, `integrations.ts`, `tool-capabilities.ts`, `approvals.ts`, `job-roles.ts`'s project-scoped routes, `policies.ts`'s project-scoped policy route) carries `:projectId`; `resolveOrganisationId` calls `deps.projects.getById(projectId)` and returns `.organisationId`, returning `null` (never gated, never errors) if the project itself does not exist — an already-nonexistent-resource 404 is the existing handler's own job to raise, not this guard's.
- **Via a nested entity lookup**: a further subset is keyed by an entity id one level removed from its owning project/organisation (e.g. `POST ${prefix}/policies/:policyId/publish`, and any other route this task's own real audit finds keyed the same way) — `resolveOrganisationId` loads that entity first (reusing the same repository its own route handler already uses) to find its `projectId`/`organisationId`, then resolves onward via the "via project" mechanism above if needed. Each such route's own resolver is necessarily bespoke to that entity's shape; there is no single generic helper that covers all of them, confirmed by the sprint README's own grounding.

Each route file's own `create*Routes` factory function gains the `resolveOrganisationId` field on the `Route` object(s) it returns, reusing that file's own already-injected deps (e.g. `deps.projects` is already present in every project-scoped deps type) — no new deps type or constructor wiring in `apps/api/src/app.ts` beyond what DEVOS-337 already added for the guard's own call site.

## Out of scope

The guard mechanism itself and the `resolveOrganisationId` field's definition (DEVOS-337). The backfill migration/exemption field this task's own "Gated" routes rely on at runtime not immediately blocking every pre-existing organisation (DEVOS-339 — and per the sprint README, this task's own real wiring must not reach production ahead of DEVOS-339's backfill). Any UI (Sprint 60).
