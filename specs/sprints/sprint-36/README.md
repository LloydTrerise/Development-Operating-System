# Sprint 36 — Integrations Page (net-new)

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.8 (E28 UI/UX Redesign & Full Functional Coverage, eighth sprint).
**Conversion date:** 2026-09-22
**Status:** Converted and authorized per explicit user instruction ("proceed", 2026-09-22, following a prior turn's own position report naming Sprint 36 as next). Depends on Sprint 29's theme/nav/`features/`/routing foundation (COMPLETE) and the reserved-but-empty "Integrations" nav group it created (`apps/web/src/App.tsx:105`). No dependency on Sprints 30–35, though it reuses their established `Paper`/`PanelHeader` restyle convention and the dense-table list pattern Sprint 35's `ArtifactLibraryPage.tsx` most recently established.

## Goal

Populate the epic's other still-empty reserved nav group: a real Integrations page (list + register) backed entirely by DEVOS-194's existing, unmodified `Integration` routes — this sprint adds zero backend routes or contract changes, per the epic's own Delivery Principle (`specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §7/§9). It also closes Sprint 30's own deliberately-deferred Home dashboard gap: no integration-health signal existed because no Integrations page existed yet.

## Grounding (confirmed by direct code inspection before scoping)

- **Both backend routes this sprint depends on already exist, unmodified** (`apps/api/src/routes/integrations.ts`, DEVOS-194): `GET`/`POST /projects/:projectId/integrations`. Confirmed via direct read.
- **Zero client wrapper exists today** — confirmed by grepping `apps/web/src/api-client.ts` for `Integration`: no matches. DEVOS-240's own claim ("zero wrapper exists today") holds exactly as stated.
- **No `GET /integrations/:id` route exists, and none is added by this sprint.** The application-layer `getIntegrationForPrincipal` (`packages/application/src/integrations/get-integration.ts`) already exists but — like `createIntegration`/`listIntegrationsForProject` before DEVOS-194 wired them — was never given a route. Per this epic's own Delivery Principle (no new backend routes for Sprints 29–38), this sprint does not add one either. **This means Integrations cannot follow Sprint 35's Library+Viewer (`/area` + `/area/:id`) pattern** — there is no real route to back a detail page. DEVOS-241 is scoped to a single list+register page; integration rows are not clickable/navigable, a real, disclosed divergence from the Artifacts/Agents/Knowledge precedent, not an oversight.
- **No update/disable/delete route exists for `Integration` at all** — only `GET` (list, any project member) and `POST` (create, `OWNER`-gated via `canRegisterIntegration`, enforced inside the use case itself, confirmed by direct read of `create-integration.ts`). The page cannot toggle status or edit an existing row; this matches DEVOS-241's own acceptance text (list + register form only, no mention of edit/disable).
- **`IntegrationStatus` has exactly two real values** (`packages/contracts/src/status.ts:165`): `'ACTIVE' | 'DISABLED'`. Every new `Integration` is created `'ACTIVE'` unconditionally (`create-integration.ts:84`) — there is no create-time way to register one as `DISABLED`, and no route ever flips it. "Health" as ui-spec.txt §24 imagines it (scopes, capabilities, credential status connected/expiring/revoked, a live "Test connection" validating connectivity) **does not exist anywhere in this codebase** — confirmed by grep for `test-connection`/`validateConnectivity` finding nothing. DEVOS-241/DEVOS-242 are scoped to the one real signal that exists: each integration's own `status` field, and a count of `ACTIVE` rows — no fabricated health check, per the backlog's own explicit instruction.
- **`type`/`provider`/`configuration` are free-form strings/JSON with no backend enum validation** (`create-integration.ts:67-75`: only non-empty-string checks) — but they are not merely descriptive. Four real task handlers dispatch on their exact literal values at runtime: `run-development-agent-task.ts:229`, `run-security-scan-task.ts:79`, and `run-validation-task.ts:90` all select an `ACTIVE` integration by `integration.type === 'Git'`; `run-release-task.ts:63/87` selects by `integration.type === 'Deployment'` (for the deploy target) and `'Git'` (for the release commit). `run-development-agent-task.ts:78/104` further dispatches `gitIntegration.provider === 'github'` vs `'gitlab'` to select the real `PullRequestProvider` adapter, and `github-context.ts` reads a real repository target from `configuration.github.{owner,repo}` (or `configuration.gitlab.{projectId,host?}`). A row created with any other `type`/`provider` string persists correctly (the backend never rejects it) but is silently invisible to every one of these real dispatch sites — an inert record, not an error. DEVOS-241's registration form discloses these exact real values as helper text (not enforced — the backend itself doesn't enforce them, so the form doesn't fabricate a validation rule the API doesn't have), so a user who wants a functioning integration, not just a database row, can create one correctly.
- **`configuration` rejects secret-shaped keys recursively** (`assertNoSecretShapedConfiguration`, matching `/password|secret|token|api[-_]?key|credential/i` against every key, nested) — a real `ValidationError` the form surfaces through the existing `ErrorAlert` pattern (matching `ArtifactLibraryPage.tsx`'s own submit-error handling) rather than a client-side pre-check duplicating that regex.
- **The "Integrations" nav group already exists, empty** (`apps/web/src/App.tsx:105`, reserved by Sprint 29's DEVOS-204, explicitly commented "populated for real in Sprint 36") — DEVOS-241 populates it with a single `/integrations` entry.
- **`HomePage.tsx`'s KPI row is a fixed 4-tile `repeat(4, 1fr)` grid** (Work Items / Runs In Progress / Pending Approvals / Artifacts) — DEVOS-242 widens it to 5 columns and adds an Integrations tile. `useHomeDashboardData` fetches from 5 already-existing routes today (`listWorkItems`, `listApprovalsForProject`, `listArtifacts`, `listAuditRecordsForProject`, `listWorkflows`); DEVOS-242 adds a 6th, `listIntegrations`, of the same shape (fire-and-forget, tolerant of failure, matching the existing `if (result.ok) { ... }` pattern for every other tile source).
- **A real, adjacent, out-of-scope gap found while reading `HomePage.tsx`, not touched by this sprint**: the Artifacts KPI tile has been non-clickable since Sprint 30, with an inline comment "no Artifact Library page exists until Sprint 35" — that page has existed since Sprint 35 completed, so the tile is now stale (should link to `/artifacts` like every other tile does). Not named in DEVOS-242's own scope (which is about the Integrations tile only) and not fixed here; disclosed in DEVOS-243.

## In scope

- **DEVOS-240** — Integrations API client: `Integration` type (mirroring `toIntegrationDto`'s real DTO shape exactly: `id`, `projectId`, `type`, `provider`, `name`, `status`, `credentialReference`, `configuration`, `createdAt`, `updatedAt`), `listIntegrations(projectId)` against `GET /projects/:projectId/integrations`, `createIntegration(projectId, input)` against `POST /projects/:projectId/integrations`.
- **DEVOS-241** — Integrations page: new `features/integrations/IntegrationsPage.tsx` at `/integrations` (list table: name/type/provider/status/created, data-derived type/status filter chips mirroring `ArtifactLibraryPage.tsx`'s DEVOS-235 convention, rows deliberately not clickable — no detail route exists) plus a register-new-integration form (type, provider, name, credentialReference, configuration as optional JSON text) matching `POST`'s real request shape, with helper text disclosing the real dispatch-significant `type`/`provider` values named above. New "Integrations" nav entry populated.
- **DEVOS-242** — Home dashboard integration-health tile: `useHomeDashboardData` gains a 6th fetch (`listIntegrations`); `HomePage.tsx`'s KPI grid widens to 5 columns with a new "Integrations" tile showing the real count of `ACTIVE` integrations (the one real health signal that exists), linking to `/integrations`.
- **DEVOS-243** — Validation, documentation, and gap disclosure: full monorepo validation green; full real `tests/e2e` suite green; new unit tests for the 2 new wrappers; live dev-server verification.

## Out of scope

Any new backend route, use case, or domain field (no `GET /integrations/:id`, no update/disable/delete, no real connectivity "Test connection", no credential-expiry tracking, no scopes/capabilities listing). A detail/viewer page for a single integration (no route to back it). Client-side enforcement of `type`/`provider` as a closed enum (the backend itself imposes none — the form discloses real values as guidance, not validation). Any change to `createIntegration`/`listIntegrationsForProject` semantics.
