# Sprint 13 — Visual Canvas MVP (E21 Workflow Designer, part 1)

**Source:** `specs/DEVOS-WORKFLOW-EXPANSION-AND-DESIGNER-BACKLOG.md` §7 "Sprint 13 — Visual Canvas MVP", grounded against direct inspection of the real, current implementation (`apps/web/src/components/ProjectTypeWorkflowsEditor.tsx`, `apps/web/src/api-client.ts`, `apps/api/src/routes/workflows.ts`/`project-types.ts`/`agents.ts`, `packages/contracts/src/workflows.ts`'s `WorkflowNode` shape, `packages/domain/src/workflows/validation.ts`, `packages/application/src/project-types/create-project-type-workflow.ts`/`update-project-type-workflow.ts`).
**Conversion date:** 2026-09-18
**Status:** **COMPLETE** — DEVOS-128–132 all complete, per explicit user approval at each step ("proceed"). See `DEVOS-BUILD-STATE.md`'s 2026-09-18 state-change-log entries for full real evidence.

## Goal

`specs/architecture/organisations-and-project-types.md` §12.2 already named and deferred this exact gap: `ProjectTypeWorkflowsEditor.tsx` is "a structured form editor, **not** a visual graph canvas... a visual canvas is a natural, larger follow-up if the form editor proves too limiting in practice." This sprint builds that follow-up: a real drag-and-drop canvas, replacing the table editor for editing `ProjectTypeWorkflow` templates, with a palette covering every node type Sprint 11/12 made real, a properties inspector, and real-time structural validation.

## Grounding (confirmed by direct code inspection before scoping)

- `ProjectTypeWorkflowsEditor.tsx` today is a plain MUI `Table` of node/edge rows with free-text fields — confirmed by reading the file directly. It edits exactly one thing per node: `id`/`type`/`name`/`agentRef` (only enabled for `AGENT_TASK`). **It has zero UI for any node's `config`** — meaning today's editor cannot author a `CONDITION` rule, a `JOIN`'s `branchFailurePolicy`, a `WAIT`'s `waitType`, or an `APPROVAL`'s `approvalType`/`pollIntervalSeconds` at all, despite all five being real, dispatchable node types since Sprint 11. Closing this gap (not just adding drag-and-drop) is this sprint's real, substantive UI work — the "visual" part is almost secondary to it.
- **No graph/canvas rendering library exists anywhere in this monorepo** (confirmed: no `react-flow`/`@xyflow/react`/`d3`/`cytoscape`/`dagre` in `pnpm-lock.yaml`) — DEVOS-128 requires adding one, a real new dependency decision (flagged below, not silently picked, per `AGENTS.md` §11).
- `WorkflowNode` (`packages/contracts/src/workflows.ts`) has `agentRef`/`approvalType` as first-class optional fields but **no equivalent field for a `TOOL_TASK`'s "which capability/behaviour"** — a `TOOL_TASK` node's real behaviour is entirely determined by `apps/worker/src/tool-task-router.ts`'s `routeToolTask` switch matching the node's own `id` (its `taskKey`) against a fixed, code-defined set (`validation`/`security-scan`/`release-readiness-check`/`release`/`rollback`/`closure`/`diagnose`/`notify`/`log-only`, per Sprint 5–12's own history). There is no per-node "capability reference" an author configures — confirmed by reading every `TOOL_TASK` handler and the contract type directly.
- `ToolCapability` rows (`packages/domain/src/tools/tool-capability.ts`) are **project-scoped, not `ProjectType`-template-scoped** — there is no `ProjectTypeToolCapability` template concept anywhere in this codebase (confirmed: `specs/architecture/organisations-and-project-types.md` §7's template promotion only ever covers `ProjectTypeWorkflow`/`ProjectTypeAgent`). A "real published `ToolCapability` list" to populate a dropdown from, at the `ProjectType`-template level this sprint edits, **does not exist as a concept**, independent of any UI gap.
- `createProjectTypeWorkflow`/`updateProjectTypeWorkflow` (`packages/application/src/project-types/`) already call `validateWorkflowGraph` server-side on every save and throw a `ValidationError` carrying every issue — real, existing, already-enforced structural validation, exactly matching Designer spec ADR-WD-004's "client validation cannot be the security or correctness boundary." Nothing here needs to change to make save-time validation real; it already is.
- `GET /projects/:projectId/agents` (`apps/api/src/routes/agents.ts`) already exists server-side; `listProjectTypeAgents(projectTypeId)` (the existing `api-client.ts` function `ProjectTypeWorkflowsEditor.tsx` already calls) already populates `AGENT_TASK`'s `agentRef` dropdown from the real `ProjectTypeAgent` template list, not free text — this part of the Designer spec's own ambition is **already real** and just needs to move into the new canvas's inspector unchanged.
- **A real correction to the source backlog document's own DEVOS-132 acceptance summary, found by direct inspection:** it describes wiring the canvas to "the existing, already-implemented `WorkflowVersion` draft → validate → publish API." That lifecycle (`GET/PATCH/validate/publish` on `apps/api/src/routes/workflows.ts`) belongs to a real **project's own** `WorkflowDefinition`/`WorkflowVersion` — it has no equivalent for a `ProjectTypeWorkflow` **template** (`ProjectTypeWorkflowRepository` has only `create`/`update`, no version, no draft/validate/publish concept at all, confirmed by reading the interface directly). DEVOS-132, as this sprint's own canvas targets `ProjectType` templates (DEVOS-128's own acceptance criterion), can only mean wiring to the template `create`/`update` API that already exists (and that the old table editor already calls) — the real `WorkflowVersion` draft/validate/publish UI gap is genuinely Sprint 14's job, exactly where DEVOS-136 ("Extend the canvas to per-project workflow editing... closing the other half of the 'zero UI for `WorkflowVersion`' gap") already, correctly, says it is. DEVOS-132 below is corrected to match reality rather than repeating the source document's conflation.

## Real design decisions this sprint makes explicit (flagged, not silently picked)

1. **Canvas library — confirmed by the user: `@xyflow/react`** (2026-09-18). No such dependency exists in this repo today; this is the de facto standard for exactly this "draggable node-and-edge graph with pan/zoom" MVP shape, MIT-licensed, and compatible with this repo's React 19/Vite 7 stack. Added as a new `apps/web` dependency (`pnpm add @xyflow/react --filter @devos/web`), per `AGENTS.md` §11 — no existing dependency provides this capability.
2. **`TOOL_TASK` nodes get an id/name field only, no capability dropdown** — dictated by the grounding above (no per-node capability-reference field exists in the contract, and `ToolCapability` isn't a `ProjectType`-template concept at all), not a preference. The palette/inspector let an author create a `TOOL_TASK` node and set its `id` (optionally from a dropdown of the known recognized taskKeys `apps/worker`'s router already handles, for discoverability) — identical in substance to what the old table editor already allowed, just in the new canvas.
3. **Real-time structural validation (DEVOS-131) runs `packages/domain`'s own `validateWorkflowGraph` directly in the browser** — it is a pure function (no I/O, only `@devos/contracts` as a dependency), so `apps/web` importing it gives instant, zero-round-trip feedback using the literal same logic the server already, separately, and non-negotiably re-enforces on every real save (`createProjectTypeWorkflow`/`updateProjectTypeWorkflow`'s own existing `validateWorkflowGraph` call is untouched — this is additive client-side convenience, never a replacement for the real enforcement point, satisfying ADR-WD-004 by construction). If a first-of-its-kind `apps/web` → `packages/domain` import turns out to drag in Node-specific code during actual implementation (to be confirmed empirically, not assumed), the fallback is a small new "validate without saving" endpoint reusing the exact same function server-side instead.

## In scope (DEVOS-128–132)

Per the source backlog's own story list, scoped to `ProjectType` workflow **templates** only (per-project `WorkflowDefinition`/`WorkflowVersion` editing is Sprint 14's DEVOS-136): canvas foundation (pan/zoom, drag-and-drop); a component palette covering `TRIGGER`/`TASK`/`AGENT_TASK`/`TOOL_TASK`/`APPROVAL`/`CONDITION`/`PARALLEL`/`JOIN`/`WAIT`/`END`; a properties inspector covering every node type's real `config` shape (not just `agentRef`, closing the gap the grounding above identifies); real-time structural validation; wiring to the real, already-implemented `ProjectTypeWorkflow` create/update API.

## Out of scope / deferred

Per-project `WorkflowVersion` draft/validate/publish UI (Sprint 14, DEVOS-136 — the real gap DEVOS-132's own source text actually described). Version diff, execution-path preview, and the workflow library page (Sprint 14, DEVOS-133–135). `LOOP`/`SUBWORKFLOW`/`HUMAN_TASK`/`ARTIFACT`/`NOTIFICATION` node types (still not in `@devos/contracts`' `workflowNodeTypes`, unchanged from Sprint 11/12's own deferral). A generic, authorable `ToolCapability`-selection mechanism for `TOOL_TASK` nodes (would be a new engine capability, not a Designer concern — out of scope per `AGENTS.md` §21's "do not prematurely implement future capabilities" unless explicitly requested).

## Sprint-wide acceptance criteria

An authorised user can visually build, validate, and save a real `ProjectTypeWorkflow` template — covering every node type this sprint's palette offers, including a real `CONDITION` rule, a real `JOIN` policy, a real `WAIT` configuration, and a real `APPROVAL` configuration — matching the Designer spec's own §43 criteria for the subset this sprint's own grounding confirms is real (structure/agents/inputs-outputs/conditions/approvals/validation/save), using only the node types E20 makes real.
