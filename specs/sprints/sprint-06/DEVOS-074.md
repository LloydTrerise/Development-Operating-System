# DEVOS-074 — Implement Deployment Adapter

**Dependencies:** DEVOS-051/052 (tool capability registry + Tool Gateway), DEVOS-073 (release approval gate). **Scope:** "Controlled staging deployment" (source description) — `specs/architecture/repository-code-structure.md` §45 names `deploy.ts` as a tool capability alongside `build-run.ts`/`test-run.ts`, with no input/output schema specified (the same gap DEVOS-062/063 already had to assume an answer for). New `deploy` tool capability through the existing Tool Gateway (DEVOS-052's chain: Typed Validation → Project Scope → Policy → Capability Permission → Credential Resolution → Provider Adapter), risk-classified per §27's Risk Model — a non-production, staging-only external change most closely matches R3 ("Create/merge PR or external change" → Review/approval), an explicit flagged assumption since §27 does not name deployment specifically. **No real external deployment/hosting provider is called** — per this sprint's own scoping decision (README), the provider adapter is a swappable port with a real-but-local staging implementation, mirroring DEVOS-058's `PullRequestProvider` precedent exactly (a real, verifiable local action standing in for a real external one, not a mock). **Acceptance:** a `deploy` invocation through the Tool Gateway, once release policy/approval allow it, performs a real local action against a real local staging target and returns a genuine, verifiable result (not a canned response); the invocation is idempotent under DEVOS-059's existing branch-binding rules; a `deploy` invocation blocked by policy or a missing approval is rejected before the provider adapter is ever reached.
