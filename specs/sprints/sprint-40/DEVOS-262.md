# DEVOS-262 — Cross-entity search aggregator use-case + route

**Priority:** P0 | **Estimate:** 1d
**Depends on:** DEVOS-261 (the four `searchForProject` methods this story fans out across).
**Depended on by:** Sprint 41's DEVOS-264 (search UI) and DEVOS-265 (Command Palette).

## Scope

A new use-case fans out across DEVOS-261's per-entity search methods within a project scope, filtering by `resolveMembership()` exactly as every other project-scoped use-case already does — no new permission model invented. New `GET /projects/:id/search?q=...` route.

## Implementation

- New `packages/application/src/search/deps.ts`: `SearchUseCaseDeps { projects: ProjectRepository; memberships: MembershipRepository; workItems: WorkItemRepository; artifacts: ArtifactRepository; workflowDefinitions: WorkflowDefinitionRepository; agents: AgentRepository }` — mirrors `SystemHealthUseCaseDeps`'s own shape exactly.
- New `packages/application/src/search/search-project.ts`: `searchProject(deps, principalId, projectId, query)` — loads the project (`NotFoundError` if missing), resolves membership (`NotFoundError` if none, matching `getProjectSystemHealth`'s own not-a-403 convention for a non-member), then `Promise.all`s the four repositories' own `searchForProject` calls (each guarded — an empty/whitespace `query` short-circuits to empty arrays for all four, no need to hit Postgres for a query that would never match). Returns `{ projectId, query, workItems: WorkItem[], artifacts: Artifact[], workflows: WorkflowDefinition[], agents: Agent[] }` — plain domain arrays, not a flattened/re-ranked single list, since each entity type has its own real shape the UI (Sprint 41) will render grouped by type per `ui-spec.txt` §27's own stated grouping.
- `packages/application/src/index.ts`: barrel-exports the two new files.
- New `apps/api/src/dto/search.ts`: `toProjectSearchResultsDto` — reuses each entity's existing `to*Dto` function (`toWorkItemDto`, `toArtifactDto`, `toWorkflowDefinitionDto` or equivalent, `toAgentDto`) rather than inventing a new shape, confirming each of those already exists before assuming so.
- New `apps/api/src/routes/search.ts` (mirrors `routes/system-health.ts`'s own minimal shape): `GET /projects/:projectId/search` reads `?q=` from the query string, 400s via the existing validation-error convention if missing/empty, calls `searchProject`, returns the DTO.
- `apps/api/src/app.ts`: new `searchDeps: SearchUseCaseDeps = options.searchDeps ?? { projects: projectDeps.projects, memberships: projectDeps.memberships, workItems: workItemDeps.workItems, artifacts: artifactDeps.artifacts, workflowDefinitions: workflowDeps.workflowDefinitions, agents: agentDeps.agents }` — zero new repository instances, reusing every one already constructed earlier in the function (same convention `systemHealthDeps` already established); wires `createSearchRoutes(API_PREFIX, searchDeps)` into the routes array; `options.searchDeps?: SearchUseCaseDeps` added to the options interface, matching every sibling deps override field.

## Out of scope

Including `knowledge_sources.searchForProject` in the aggregator (disclosed boundary, `README.md`). Any flattened/merged/re-ranked-across-types single result list. Any web UI or API-client wrapper (Sprint 41). Any new authorization/permission model beyond `resolveMembership`.

## Actual results

Implemented exactly as scoped, with one real, necessary, disclosed addition beyond the story's own text: this router had never needed a URL query-string parameter before this sprint (`GET /projects/:id/system-health` and every other existing route reads only `params`/`body`). `RouteContext` (`apps/api/src/http/router.ts`) gained a new `query: Record<string, string>` field, and `apps/api/src/app.ts`'s `handleRequest` now parses `url.searchParams` via `Object.fromEntries` and passes it into every handler call — additive, every existing handler ignores it unchanged (confirmed via the full monorepo typecheck/test run below, zero ripple).

`packages/application/src/search/{deps,search-project}.ts` mirrors `system-health/`'s own two-file shape exactly, as planned. `searchProject` short-circuits to empty results for all four entities on an empty/whitespace query without calling any repository (verified by a dedicated unit test). `apps/api/src/dto/search.ts`'s `toProjectSearchResultsDto` reuses `toWorkItemDto`/`toArtifactDto`/`toWorkflowDefinitionDto`/`toAgentDto` unchanged, confirming each already existed before assuming so. `apps/api/src/routes/search.ts` mirrors `routes/system-health.ts`'s minimal shape; `apps/api/src/app.ts`'s `searchDeps` reuses every repository instance already constructed earlier in the function (`workItemDeps.workItems`, `artifactDeps.artifacts`, `workflowDeps.workflowDefinitions`, `agentDeps.agents`, `projectDeps.{projects,memberships}`) — zero new repository instances, matching `systemHealthDeps`'s own established convention.

**Deliberate scope boundary confirmed, not silently expanded**: `knowledge_sources.searchForProject` (DEVOS-187) is not included in this aggregator, matching the backlog's own literal DEVOS-262 text ("fans out across DEVOS-261's per-entity search methods") — disclosed in `README.md`'s grounding, not an oversight.

New tests: `packages/application/tests/search.test.ts` (5 cases — real aggregation across all four fakes, empty-query short-circuit, no-match empty results, non-member 404, missing-project 404), plus 3 new route-level tests in `apps/api/tests/app.test.ts` (`cross-entity search route (DEVOS-262)` describe block — real aggregated results across all four entity types created through their own real POST routes, missing/empty `q` → 400, non-member → 404). The four existing in-memory repository fakes in `app.test.ts` (`createInMemoryWorkItemDeps`/`createInMemoryWorkflowDeps`/`createInMemoryArtifactDeps`/`createInMemoryAgentDeps`) each gained a simple substring-based `searchForProject` implementation to exercise the new route — a real, minimal stand-in for Postgres full-text search, not a behavioral claim about ranking.

One real fixture-writing correction found while writing the route test: the real `createAgent` use case requires a full `configuration: { role, provider, modelRef }` object (not just `key`/`name`) — the test's initial agent-creation body omitted it, causing the agent to silently fail creation (400) and the assertion to fail with 0 results instead of 1; fixed by supplying a real minimal configuration object, not by loosening the assertion.

Full monorepo `pnpm turbo run typecheck lint test build --filter='!@devos/e2e-tests'`: **76/76 tasks green**, matching Sprint 39's own baseline exactly (no new package). `prettier --write`/`--check` applied and re-verified clean across every file this sprint touched (18 files: 8 domain/database from DEVOS-261, plus this story's 10 — `router.ts`, `app.ts`, `app.test.ts`, `index.ts`, `search/deps.ts`, `search/search-project.ts`, `dto/search.ts`, `routes/search.ts`, `search.test.ts`, plus the sprint's own spec files).
