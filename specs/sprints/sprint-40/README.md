# Sprint 40 — Cross-Entity Search (Backend)

**Source:** `specs/DEVOS-UI-UX-REDESIGN-BACKLOG.md` §6.13 (E28 UI/UX Redesign & Full Functional Coverage, twelfth sprint).
**Conversion date:** 2026-09-22
**Status:** Converted per explicit user instruction ("Proceed", 2026-09-22, in direct response to a position report naming Sprint 40 as the recorded next action). Depends on Sprint 25's DEVOS-187 full-text pattern (direct template) and Sprint 29's project-scoped `resolveMembership()` convention (reused unchanged, per the epic's own delivery principles).

## Goal

Close the first of the two remaining named-but-backend-less `ui-spec.txt` areas (§2.4): a real cross-entity search capability. This sprint is backend-only — DEVOS-261 generalizes DEVOS-187's real Postgres full-text pattern to four more tables, and DEVOS-262 adds a project-scoped aggregator route fanning out across them. Sprint 41 (not this sprint's scope) wires a UI and the global Command Palette on top of the route this sprint ships.

## Grounding (confirmed by direct code inspection before scoping)

- **DEVOS-187's pattern re-confirmed still live, exact location matches the backlog's own citation.** `packages/database/src/repositories/knowledge-sources.ts:96-112`'s `searchForProject(projectId, query)` — `to_tsvector('english', name || ' ' || content) @@ plainto_tsquery('english', ${query})`, ordered by `ts_rank(...)` descending, `.limit(50)` — is the real, unchanged template DEVOS-261 mirrors for `WorkItemRepository`, `ArtifactRepository`, `WorkflowDefinitionRepository`, and `AgentRepository`. Each gets its own `searchForProject`, added as an **optional** repository method (this codebase's established convention since Sprint 39's `MembershipRepository.listForOrganisation`/`ToolCapabilityRepository.updateStatus` — avoids a required-method ripple across every fake implementing these four widely-faked interfaces).
- **A real structural break from every sprint since 29, confirmed not assumed:** the newest migration on disk is `packages/database/migrations/0041_approvals_add_reliability_evidence.ts` — nothing since Sprint 39 touched schema (org membership/tool-capability-toggle/system-health were all genuinely zero-migration, confirmed in `specs/sprints/sprint-39/README.md`). DEVOS-261 is the first sprint in this epic needing a real migration: Kysely 0.29.5's `CreateIndexBuilder` supports `.using('gin').column(sql\`...\`)`for a functional expression index (confirmed by reading`node_modules/.pnpm/kysely@0.29.5/node_modules/kysely/dist/schema/create-index-builder.d.ts` directly, not assumed from Kysely's public docs) — a single new migration (`0042_add_search_indexes.ts`) adds one GIN index per newly-searchable table, closing DEVOS-187's own disclosed sequential-scan limitation for these four tables. Per the backlog's own DEVOS-261 text, `knowledge_sources`' existing search is left exactly as-is — indexing it is not "trivial to include" today, since its `searchForProject`predicate also filters`status = 'ACTIVE'` in a way the other four tables' searches deliberately do not (see below), so a shared index shape does not exist; out of scope, not silently dropped.
- **Real per-table column grounding, confirmed by reading each domain interface, database repository, and creation migration directly (not assumed from naming alone):**
  - `work_items`: `title` (`text`, `NOT NULL`) and `description` (`text`, `NOT NULL` — confirmed via `migrations/0004_work_items.ts`, so no `coalesce()` needed). No status filter: `WorkItemStatus` is an intentionally-unenumerated opaque string (`packages/contracts/src/status.ts`'s own documented rationale) with no "approved/retrievable" equivalent to DEVOS-187's `ACTIVE` gate — filtering here would invent a business rule no spec defines.
  - `artifacts`: only `name` (`text`, `NOT NULL`) is a real searchable text column — no `description`/`content` column exists on `artifacts` itself (`ArtifactVersion.metadata` holds per-version content, out of this story's scope, consistent with Sprint 35's own finding that no route serves decoded artifact content). No status filter: `ArtifactStatus` is a real nine-value lifecycle (`DRAFT`…`ARCHIVED`) with no single "searchable" subset defined anywhere — filtering would be a new, undocumented rule.
  - `workflow_definitions`: `name` (`text`, `NOT NULL`) and `description` (`text`, nullable — `coalesce(description, '')` needed, confirmed via `migrations/0005_workflow_definitions.ts`). No status column exists on this table at all (lifecycle status lives on `WorkflowVersion`, a separate table) — nothing to filter.
  - `agents`: `name` (`text`, `NOT NULL`) and `description` (`text`, nullable — `coalesce()` needed, confirmed via `migrations/0015_agents.ts`). `Agent.status` is an unenumerated `string` (no `AgentStatus` type exists, unlike `AgentVersionStatus`) — every real creation path (`create-agent.ts`, `install-agent-version.ts`) hardcodes `'ACTIVE'` and no other value is ever set anywhere in this codebase (confirmed by grep) — filtering on it would be a no-op today and an unspecified rule tomorrow. No filter.
  - **Deliberate, disclosed scope boundary**: none of the four new `searchForProject` methods filters by status, unlike DEVOS-187's own knowledge-source search. This is not an oversight — it is the minimal-invented-business-rule reading of §9's "no new business rule invented," grounded per-table above rather than assumed uniformly.
- **DEVOS-262's aggregator has a real, already-proven template to mirror exactly, not invent.** `packages/application/src/system-health/get-project-system-health.ts` (Sprint 39, DEVOS-258) is the closest existing precedent for "one project-scoped use case fanning out across several already-constructed repositories via `Promise.all`, gated by `resolveMembership`" — same `NotFoundError`-on-missing-project/-membership shape, same deps-interface-reusing-already-built-repository-instances convention `apps/api/src/app.ts` already establishes for `systemHealthDeps` (reusing `workItemDeps.workItems`, `artifactDeps.artifacts`, `workflowDeps.workflowDefinitions`, `agentDeps.agents`, `projectDeps.{projects,memberships}` — zero new repository instances constructed). A new `packages/application/src/search/` folder (`deps.ts` + `search-project.ts`) mirrors `system-health/`'s own two-file shape exactly. The route (`apps/api/src/routes/search.ts`, wired in `app.ts` the same way `createSystemHealthRoutes` is) mirrors `routes/system-health.ts`'s own minimal single-route-array shape.
- **Real, deliberate scope boundary on DEVOS-262's own acceptance text, confirmed against the backlog's literal wording**: "fans out across DEVOS-261's per-entity search methods" names exactly the four DEVOS-261 builds. Knowledge sources' own pre-existing `searchForProject` (DEVOS-187, built for RAG context retrieval — confirmed by grep, its only real caller today is `packages/knowledge/src/retrieval/retrieve-knowledge-sources.ts`, never a user-facing search surface) is **not** included in this aggregator — a real, disclosed boundary matching the backlog's own precise text, not an oversight. Sprint 41's UI story may revisit this if the user wants knowledge sources folded into the same result set; out of this sprint's scope to decide unprompted.
- **No web API client wrapper in this sprint.** Sprint 40 is backend-only per the backlog's own sprint title; `apps/web/src/api-client.ts` is untouched — DEVOS-264 (Sprint 41) adds the client wrapper alongside the search UI itself.
