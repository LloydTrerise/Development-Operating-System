# DEVOS-067 — Implement Rework Transitions

**Dependencies:** DEVOS-066 (review evidence), DEVOS-061 (development-path run). **Scope:** "Review failure back to development" (source description) — §20 Rework: "a first-class workflow path... 1. evidence is published; 2. the workflow identifies the appropriate return stage; 3. a new task execution is created; 4. the developer/agent receives the relevant findings; 5. changes are made; 6. validation runs again; 7. review runs again. The workflow must preserve previous outputs and execution history. Rework must not destroy traceability." (ADR-SCW-004; Workflow Principle 7, §8.) **This sprint's README already flags the load-bearing constraint**: the current engine materializes every task in a run up front and only completes a run once every task in it succeeds (found during DEVOS-061), so §20's "a new task execution is created" cannot mean dynamically inserting a task into the already-running development-path run without changes to that same engine machinery DEVOS-061 chose not to touch. The concrete mechanism (most likely: a `CHANGES_REQUIRED` decision triggers a new, separate development-path run — reusing DEVOS-061's own seeded workflow — whose development task consumes the review findings alongside the original plan, mirroring exactly how DEVOS-061 itself resolved an equivalent constraint) is a decision for this task's own implementation to investigate and confirm, not to pre-decide here. **Acceptance:** a `CHANGES_REQUIRED` review outcome results in a new development cycle being started automatically, whose context includes the review findings; every prior run and artifact remains intact and queryable (nothing is overwritten or deleted).
