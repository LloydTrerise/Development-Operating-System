## Grounding (confirmed by direct code inspection before scoping)

- **The source document was read in full** (`Analysis/DEVOS Access Control Model.docx`, extracted via its own `word/document.xml`, since no plain-text/Markdown copy exists on disk) — its permission catalogue, entity-relationship diagrams, and access rules are the literal baseline this task reconciles against, not assumed from the backlog's own summary.
- **`audit_records` (`0012_audit_records.ts`) substantially satisfies `AUDIT_LOG`** as §2.7 already found — full column-by-column reconciliation in `DEVOS-308.md`.
- **A real, significant authorization bug was found during this sprint's own re-audit, not merely disclosed — and fixed**, per this codebase's own established precedent (Sprints 48/49/50 each fixed real bugs found during their own required verification): `resolveOrganisationMembership` (`packages/application/src/organisations/membership-access.ts`), the chokepoint underneath every organisation-scoped route, has always had a documented, deliberately-tested (Sprint 39/DEVOS-254) fallback to _any project-level membership within the organisation_ when no org-level row exists — including, and specifically, a plain project `OWNER`. That fallback was reasonable when written (most organisations genuinely had no org-level membership row at the time), but Sprint 47 (DEVOS-290) has since made every organisation's real org-level `ORGANISATION_ADMIN` row guaranteed to exist (`createOrganisation`; migration `0048`'s own backfill) and given that role far greater weight — full, catalogue-driven, project-`OWNER`-equivalent authority over _every_ project in the organisation via `resolveMembership`'s own separate, correctly narrower, org-level-only fallback. Left unchanged, this meant the `OWNER` of even one project — never granted any organisation-level standing by anyone — could still rename the organisation, add or remove organisation-level co-admins (including granting _themselves_ `ORGANISATION_ADMIN`, which then unlocks every other project in the organisation), or assign/revoke organisation-held job roles. This is exactly the privilege-escalation shape §9.2/§9.3's resolved decisions were written to prevent. Full detail, fix, and live verification in `DEVOS-309.md`.
- **Every one of the six write-gated organisation-scope use cases** (`updateOrganisation`, `addOrganisationMember`, `removeOrganisationMember`, `changeOrganisationMemberRole`, `assignPrincipalJobRole`, `removePrincipalJobRole`) was individually confirmed, by direct inspection, to be the _complete_ set of `canManageMembers`/`canUpdateOrganisation` call sites reachable through `resolveOrganisationMembership` — not assumed from the two or three most obvious ones.
- **The project-scope equivalent, `resolveMembership` (`packages/application/src/projects/membership-access.ts`), was independently re-confirmed correct, not merely assumed safe by symmetry**: its own org-level fallback only ever matches a genuine `projectId: null` row (never a _different_ project's role), so it carries no analogous bug. 76 of the application layer's use-case files call it directly; every one of them inherits the same, now-reconfirmed-correct chokepoint.
- **Every route file was enumerated programmatically**: `apps/api/src/routes/*.ts` now has 25 files (unchanged file count since Sprint 44's own 24 plus this epic's new `job-roles.ts`) and 116 routes (up from 105 at Sprint 44 — the growth entirely accounted for by this epic's own new routes: 7 job-role routes, 3 work-item-assignment routes, and organisation owner/admin/transfer routes from Sprints 47–50).
- **Several real, narrow divergences between the source document's own idealized model and this codebase's actual, longstanding conventions were found and are disclosed, not fixed**, since none is named as in-scope by any of Sprints 46–51's own stories and several predate this epic entirely (e.g. `createProject`/`createOrganisation` are both deliberately, symmetrically ungated at creation time — "any authenticated principal may create one" is this codebase's own established convention, not a regression). Full list in `DEVOS-309.md`'s own disclosure table.

## Scope extension (post-completion)

After the sprint's own initial completion, the user reviewed DEVOS-310's closing disclosure table and asked to fix the findings. Presented with the four kinds of disclosed items — (1) deliberate, already-resolved exclusions (`DIVISION`, `AGENT_CREDENTIAL`, a new `AUDIT_LOG` table), (2) real gaps, (3) longstanding platform-wide ungated-creation conventions, (4) a cosmetic `metadata` reshape — the user chose **"Authorization tightening only"** and **"New work-item capabilities"**, explicitly declining to reopen ungated project/organisation/project-type creation or the `metadata` reshape. Mirroring Sprint 41's/Sprint 50's own precedent for exactly this situation (disclose, let the user choose, implement only what's chosen):

- **`agent.manage` gating — DONE.** A new permission (migration `0057`, granted to `PROJECT:OWNER`/`ORGANISATION:ORGANISATION_ADMIN`) and `canManageAgent()` narrow `createAgent` from "any resolved project member" to that role bar; `createNewAgentVersion` ("configure" an existing agent) additionally accepts the agent's own resolved `AgentProfile.accountableOwnerId`, checked directly (not through the catalogue), matching the source document's own "checked against ... not against a role" precedent for this exact permission. 6 new tests.
- **`audit_records.actor_id` real FK — DONE.** A new, nullable `actor_principal_id` column (migration `0056`) is a real FK to `principals.id`, populated only for `USER`/`AGENT` actor rows that resolve to a real principal — `actor_id` itself stays unconstrained (it also carries `SYSTEM` actor ids like `devos-worker`, which are never `principals` rows by design). Live-verified against real data: 806/806 `AGENT` rows and 11903/12060 `USER` rows resolved (the 157-row gap is the already-known `devos-agent-runtime`-mislabeled-as-`USER` rows Sprint 46 already excluded for the identical reason); `SYSTEM`'s 0/26624 is correct by design.
- **`addMember`/`addOrganisationMember` requiring prior organisation standing — ATTEMPTED, REVERTED.** Implementing this literally broke a common, legitimate, everyday workflow: a plain project `OWNER` (not an organisation admin) inviting a brand-new person to their own project, since that person would have no prior standing anywhere in the organisation yet — 4 existing tests in `projects.test.ts` failed for exactly this reason on the first implementation attempt. The source document's own model assumes a separate "add to division" onboarding step DevOS does not have; forcing the rule through would require inventing one, a materially larger change than "authorization tightening." Reverted rather than silently loosened to keep passing; disclosed back to the user rather than left broken or silently abandoned.
- **`workitem.comment` — DONE, genuinely new.** `work_item_comments` (migration `0058`, `ON DELETE CASCADE`, applied proactively per Sprint 48/49/50/54's own established lesson), `addWorkItemComment`/`listWorkItemComments` (any resolved project member, matching the source document's own permission table exactly), `GET`/`POST /work-items/:workItemId/comments`, web client wrappers, and a Comments panel on `WorkItemDetailPage.tsx`. 3 new application-layer tests, 1 new route-level test, live-verified against a real running `apps/api`/`apps/web` and a real Chromium browser (post → visible with correct author attribution, zero console errors).
- **`workitem.delete` — DONE, as a soft archive.** The source document's own permission table grants `workitem.delete` to admin/project-admin only — the one `workitem.*` permission with no "project member" grant at all, not even for the `ASSIGNEE` — so this is a real, distinct, more-privileged use case (`archiveWorkItem`, `canManageMembers`-gated) deliberately not reachable through `updateWorkItem`'s own broader `ASSIGNEE`/`REVIEWER`/`APPROVER` status-transition path. Implemented as `status: 'ARCHIVED'` (no schema change — `WorkItemStatus` is already an unconstrained string, mirroring `Project.status`'s own identical "archive via status field" convention), not a hard delete, per this codebase's "nothing is hard-deleted" rule. `POST /work-items/:workItemId/archive`, a web client wrapper, and an Archive button in the Details panel. 3 new application-layer tests, 1 new route-level test, live-verified in the same real browser session (archive succeeds, button becomes disabled/"Archived", status field reflects it).

Full validation re-ran clean after all four changes: `pnpm turbo run typecheck lint test build --filter='!@devos/e2e-tests' --force` **76/76 green** (application tests **389/389**, up from 380); the full real `tests/e2e` suite **27/27 files, 52/52 tests green**, zero regression, matching the sprint's own original baseline. Live-verified against real Postgres (`docker-postgres-1`) and a real running `apps/api`/`apps/web`; all real test data (throwaway organisations/projects/work items/comments) cleaned up afterward via direct Postgres deletes in correct FK order, confirmed zero remaining rows each time; no stray `node.exe` processes at any point.
