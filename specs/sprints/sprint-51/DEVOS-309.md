# DEVOS-309 — Full-epic re-audit

**Priority:** P0
**Acceptance summary (from backlog §6.6):** Mirrors Sprint 44's own precedent: every one of the ~105 existing routes re-confirmed to authorize correctly under the new model; every one of the source document's tables/permissions confirmed built and enforced under this epic's resolved scope (§9), or explicitly disclosed as deferred (`DIVISION`, `AGENT_CREDENTIAL` — deliberately never built, per §4).

This task audits **authorization correctness**, a materially different question from Sprint 44's own re-audit, which closed **UI reachability** for a different epic (E28). A route can be perfectly reachable through the UI and still authorize incorrectly (too permissively, or too restrictively) — that is what this task checks.

## Method

1. Every route was enumerated programmatically from `apps/api/src/routes/*.ts` (25 files, 116 routes) and grouped by which application-layer use case it calls.
2. Every use case's authorization chokepoint was traced: `resolveMembership` (project scope, `packages/application/src/projects/membership-access.ts`), `resolveOrganisationMembership`/`resolveOrganisationAdminMembership` (organisation scope, `packages/application/src/organisations/membership-access.ts`), or a work-item-assignment/job-role-specific check layered on top of one of those two.
3. Every application-layer source file that does **not** call one of those chokepoints (or a helper that wraps one, e.g. `requireDraftAgentVersion`/`requireDraftVersion`/`requireArtifactAccess`) was individually inspected to confirm it is either (a) genuinely unauthenticated-by-design (e.g. `ProjectType` management — a global, cross-organisation template resource with no owning tenant, confirmed to have no `organisationId`/`projectId` field on the entity itself), (b) self-scoping by construction (e.g. notification list/mark-read routes, which filter by the caller's own `principalId` as the recipient), or (c) an internal worker task handler never reachable from an HTTP route with an external caller.
4. The source document's 17-permission catalogue (`Analysis/DEVOS Access Control Model.docx`, extracted and read in full) was reconciled against the real, seeded 9-permission catalogue (migration `0047`/`0048`) permission-by-permission.

## Finding 1 — a real, live privilege-escalation bug, found and fixed

**`resolveOrganisationMembership`'s project-level-`OWNER` fallback let a plain project owner reach organisation-admin authority.**

### The bug

`resolveOrganisationMembership` (`packages/application/src/organisations/membership-access.ts`) is the chokepoint every organisation-scoped use case resolves a requester's standing through. Before this task, on finding no direct org-level (`projectId: null`) membership row for a principal, it fell back to:

```ts
return memberships.find((membership) => membership.role === 'OWNER') ?? memberships[0]!;
```

— i.e. _any_ project-level membership within the organisation, preferring an `OWNER` role if one exists. This was a real, deliberate, **tested** Sprint 39 (DEVOS-254) design (`packages/application/tests/organisations.test.ts`'s own, now-renamed, test literally asserted this fallback succeeded) for a real gap at the time: most organisations had no org-level membership row at all, so without _some_ fallback, nobody could manage a freshly-migrated organisation.

That gap no longer exists. Sprint 47 (DEVOS-290) made every organisation's real org-level `ORGANISATION_ADMIN` row guaranteed: `createOrganisation` always creates one for the creator, and migration `0048`'s own backfill gave every pre-existing organisation one (electing a fallback owner from its earliest project-level `OWNER` where no org-level row existed at migration time). Sprint 47 also gave `ORGANISATION_ADMIN` far more weight than Sprint 39's org-level `OWNER` ever had: the _same_ nine permissions the project-scope `OWNER` role holds, applied organisation-wide via `resolveMembership`'s own separate, correctly-scoped org-level fallback (`packages/application/src/projects/membership-access.ts`) — meaning an `ORGANISATION_ADMIN` gets `OWNER`-equivalent authority over **every project in the organisation**, not just the one they administer directly.

Combining these two facts is the bug: any principal who is `OWNER` of even a single project — added there by that project's own owner, with no organisation-level trust ever extended to them — could, via `resolveOrganisationMembership`'s stale fallback, pass `canManageMembers`/`canUpdateOrganisation` at organisation scope and:

- rename or otherwise update the organisation (`updateOrganisation`);
- add themselves (or anyone) as a real `ORGANISATION_ADMIN` (`addOrganisationMember`) — which then, through the correctly-scoped `resolveMembership` fallback, grants them `OWNER`-equivalent authority over **every other project in the organisation**, including ones they were never a member of;
- remove or demote other organisation admins (`removeOrganisationMember`, `changeOrganisationMemberRole`);
- assign or revoke organisation-held job roles for any principal (`assignPrincipalJobRole`, `removePrincipalJobRole`).

This is precisely the escalation §9.2/§9.3's resolved decisions were written to prevent (a deliberately scoped, transferable organisation-owner/co-admin tier, distinct from project-level ownership). It was not introduced by this epic's own code — the fallback's literal shape predates Sprint 46 — but its severity was created by this epic: before Sprint 47, an org-level `OWNER` row conferred no cross-project authority at all, so the same fallback was comparatively low-stakes.

### Confirmed exhaustive blast radius

Every call site of `resolveOrganisationMembership` was enumerated (21 files). Of those, exactly six gate a **write** action via `canManageMembers`/`canUpdateOrganisation` and were therefore exploitable:

| Use case                       | Route(s)                                                                 | Gate                    |
| ------------------------------ | ------------------------------------------------------------------------ | ----------------------- |
| `updateOrganisation`           | `PATCH /organisations/:id`                                               | `canUpdateOrganisation` |
| `addOrganisationMember`        | `POST /organisations/:id/members`                                        | `canManageMembers`      |
| `removeOrganisationMember`     | `DELETE /organisations/:id/members/:membershipId`                        | `canManageMembers`      |
| `changeOrganisationMemberRole` | `PATCH /organisations/:id/members/:membershipId`                         | `canManageMembers`      |
| `assignPrincipalJobRole`       | `POST /organisations/:id/principals/:principalId/job-roles`              | `canManageMembers`      |
| `removePrincipalJobRole`       | `DELETE /organisations/:id/principals/:principalId/job-roles/:jobRoleId` | `canManageMembers`      |

The other 15 call sites are all **read-only** org-wide-visibility routes (`getOrganisationForPrincipal`, member listing, cost/audit/engineering-report reads, policy/workflow/job-role listing, shared-agent/knowledge-source marketplace listing) — a design Sprint 39–42 established deliberately (any project member of any project in the organisation may see organisation-wide rollups) and which this task does not revisit; none of them checks `canManageMembers`/`canUpdateOrganisation`, so none was exploitable this way.

`resolveMembership` (the project-scope equivalent) was independently re-checked and confirmed to carry no analogous bug: its own org-level fallback only ever matches a genuine `projectId: null` row for the _same_ organisation — never a different project's role — so a project owner's authority never leaks sideways into a different project via that path.

### Fix

A new, stricter function, `resolveOrganisationAdminMembership`, was added alongside the existing `resolveOrganisationMembership` in the same file — it returns a principal's org-level (`projectId: null`) membership row only, with **no** fallback to any project-level role. All six write-gated call sites above now use it in place of `resolveOrganisationMembership`; every read-only call site is untouched, preserving the deliberate Sprint 39–42 visibility design.

Files changed:

- `packages/application/src/organisations/membership-access.ts` — new `resolveOrganisationAdminMembership` (existing `resolveOrganisationMembership` untouched, still used by every read-only call site).
- `packages/application/src/organisations/update-organisation.ts`
- `packages/application/src/organisations/add-member.ts`
- `packages/application/src/organisations/remove-member.ts`
- `packages/application/src/organisations/change-member-role.ts`
- `packages/application/src/job-roles/assign-principal-job-role.ts`
- `packages/application/src/job-roles/remove-principal-job-role.ts`

Test changes:

- `packages/application/tests/organisations.test.ts` — the pre-existing test that asserted the old (now-closed) fallback succeeded was rewritten to assert it is denied (`NotFoundError`, matching every other "no standing in this organisation" case in this codebase); a second pre-existing test (project-level `MEMBER` denied) updated to the same `NotFoundError` outcome for the same reason; two new tests added proving the specific self-escalation shape (`OWNER` of one project cannot update the organisation, and cannot add themselves as `ORGANISATION_ADMIN`) is now denied, plus a tenant-isolation case (an admin of a _different_ organisation is denied).
- `packages/application/tests/job-roles.test.ts` — the pre-existing "gated to an org admin" test's denial case updated from `ForbiddenError` to `NotFoundError` (same reasoning); one new test added proving a project-level `OWNER` with no org-level membership cannot grant an organisation-held job role.

All existing tests that exercised the _legitimate_ path (a real `ORGANISATION_ADMIN` performing these six actions) were re-run unmodified and continue to pass, proving the fix is additive-restrictive, not a regression for any correctly-privileged caller.

## Live verification

Verified against real Postgres and a real running `apps/api` (built with the fix already applied, started on port 3000, authenticated via the local dev `Authorization: Bearer <principalId>` provider):

1. A real organisation ("DEVOS-309 Verify Co") was created via `POST /organisations` as principal `verify-owner` — confirmed a real `ORGANISATION_ADMIN` membership row and `owner_principal_id` were both set correctly (unaffected by this task's change, since `createOrganisation` never goes through either `resolveOrganisationMembership` function).
2. A real project was created under that organisation by `verify-owner` (making them a real project-level `OWNER` via the normal creation flow), then `verify-escalator` was added as `OWNER` of that project only, via the ordinary `POST /projects/:id/members` route — deliberately with **no** organisation-level standing of any kind.
3. **Attack, as `verify-escalator` (project `OWNER`, zero organisation-level standing):**
   - `PATCH /organisations/:id` with `{"name":"PWNED BY PROJECT OWNER"}` → **`404 DEVOS_NOT_FOUND` — correctly rejected** (this would have returned `200` and actually renamed the organisation before this task's fix).
   - `POST /organisations/:id/members` with `{"userId":"verify-escalator","role":"ORGANISATION_ADMIN"}` (the specific self-escalation attempt) → **`404 DEVOS_NOT_FOUND` — correctly rejected** (this would have returned `200` and actually granted `verify-escalator` organisation-wide admin authority before this task's fix).
4. **Legitimate, as `verify-owner` (the real `ORGANISATION_ADMIN`):**
   - `PATCH /organisations/:id` with `{"name":"Legit Rename By Owner"}` → `200`, and the organisation's real `name` was confirmed changed.
   - `POST /organisations/:id/members` adding `verify-legit-admin` as `ORGANISATION_ADMIN` → `200`, and the real membership row was created.
   - Confirms the fix is additive-restrictive only, not a regression for a legitimately privileged caller.
5. **Database-level confirmation, not just HTTP response codes**: a direct `psql` query against the real `memberships` table after the attack attempts showed `verify-escalator` still held only their original project-level `OWNER` row — no `ORGANISATION_ADMIN` row for `verify-escalator` was ever created, proving the escalation attempt failed at the point of the actual database write, not merely in an HTTP response that could theoretically have masked a partial success. The final `GET /organisations/:id/members` listing showed exactly `verify-owner` and `verify-legit-admin`, never `verify-escalator`.
6. All real test data (2 organisations — including one from an earlier, corrected verification-script attempt — 1 project, 2 cloned workflow definitions/versions, 3 cloned agents/agent-versions, 6 memberships, 3 audit records, 3 principals/human-profiles/user-identities) was deleted afterward via direct Postgres deletes in correct FK-dependency order (audit records → workflow versions → workflow definitions → agent versions → agents → memberships → projects → organisations → user identities → human profiles → principals); confirmed zero remaining rows across every affected table by direct count query. The `apps/api` dev process used for verification was stopped afterward; confirmed no stray `node.exe` processes remained.
