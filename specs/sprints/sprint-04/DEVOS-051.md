# DEVOS-051 — Implement Tool Definition Model

**Dependencies:** Sprint 1 project scoping (DEVOS-011). **Scope:** The `tool_capabilities` table and domain entity, matching `specs/database/poc-database-schema.md` §14.1 exactly (`id`, `project_id`, `key`, `name`, `risk_class` R0–R4, `input_schema`/`output_schema` JSONB, `status`, `created_at`), within `packages/tools/src/capabilities/` and `packages/tools/src/registry/` (`specs/architecture/repository-code-structure.md` §16). A Tool Capability is "a discrete action that an integration or internal service exposes to DevOS" (`specs/architecture/domain-model.md` §11.2), e.g. `repo-read`, `repo-write`, `git-commit`, `pull-request-create` — the exact capability files the repo-structure spec names. **Acceptance:** A capability is defined with an input/output schema and a risk class (R0–R4, `specs/workflows/software-change-workflow.md` §27); no `tool_permissions` table exists anywhere in the documented schema despite domain-model §11.3 defining a "Tool Permission" concept — how risk/policy actually binds to a capability record is an implementation-level decision (this task defines the capability's own `risk_class`; DEVOS-052 wires authorization against DEVOS-044's policy evaluator, not a separate permissions table), flagged rather than fabricated.
