# DEVOS-053 — Implement Integration Credential Abstraction

**Dependencies:** DEVOS-011 (project scoping). **Scope:** The `integrations` table (`specs/database/poc-database-schema.md` §13.1: `id`, `project_id`, `type`, `provider`, `name`, `status`, `configuration` JSONB — non-secret only) and domain entity, matching `specs/architecture/domain-model.md` §11.1 ("An Integration represents a configured connection between DevOS and an external engineering system... source control; issue tracking; CI/CD..."). "Credentials are references only" (`specs/api/poc-api-contracts.md` §33); "Secrets are referenced through a secret-management mechanism and are not stored in this table as plaintext" (schema §13.1) — the mechanism itself is never named or designed anywhere in the spec corpus, so this task resolves credentials from environment variables by a stored reference name (matching the existing `GEMINI_API_KEY`-via-`@devos/config` precedent), not a secrets-manager integration, flagged explicitly as an implementation choice rather than a spec-mandated design. **Acceptance:** An `Integration` record stores only a provider/type/non-secret configuration and a credential _reference_; resolving that reference to actual secret material happens through an injected `CredentialResolver` port (`specs/architecture/repository-code-structure.md` §47: "Provider adapters receive credentials through injected interfaces"), never by reading a secret column directly; no code path logs, persists, or places a resolved credential value in agent context (`poc-api-contracts.md`: "Secrets... never placed in agent context").
