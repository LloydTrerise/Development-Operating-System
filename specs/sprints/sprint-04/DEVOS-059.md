# DEVOS-059 — Add Mutation Safety Controls

**Dependencies:** DEVOS-052 (Tool Gateway), DEVOS-058 (PR creation). **Scope:** Idempotency, branch binding, and audit (source description). Idempotency is well-grounded: an `Idempotency-Key` header at the API layer (`specs/api/poc-api-contracts.md` §API Standards), a tool contract's own `idempotencyKey` field (§32), a dedicated database idempotency section ("Operations that can be repeated must have an idempotency strategy... tool invocation... Possible mechanisms include: idempotency keys; unique business keys; execution identifiers; conditional updates," `specs/database/poc-database-schema.md` §23), and an explicit retry rule ("Prevent repeated external side effects through idempotency," `specs/workflows/software-change-workflow.md` §24). **"Branch binding" and "mutation safety" appear nowhere in the spec corpus as named mechanisms** — flagged explicitly as a from-scratch design, not a spec derivation. Audit follows the existing `audit_records` mechanism (`poc-api-contracts.md` §36; `specs/technical/poc-technical-implementation.md` §27) already used throughout Sprints 1–3, not a parallel one. **Acceptance:** A tool invocation is idempotent on its supplied key (a retried request with the same key against the same target does not perform the external action twice); a mutation is checked against the specific branch/target it was originally authorised for (an implementation-level "branch binding" check — e.g. a commit/PR-creation request whose target branch differs from what was authorised is rejected) rather than merely idempotent on a bare key; every tool invocation, whether it succeeds, fails, or is rejected, produces an audit record.
