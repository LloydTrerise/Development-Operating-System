### 2.1 Thread A — Approval gates, risk tiers, and reliability signals

| Concept | Where it lives today | Current reality (verified) |
| --- | --- | --- |
| `Policy` entity & evaluation | `packages/domain/src/policy/policy.ts:12-29`, `packages/policy/src/evaluator/{policy-evaluation,evaluate-policies,evaluate-policies-with-precedence}.ts` | Real. A `Policy` row is one version of a JSONB `definition: { rules: PolicyRule[], defaultEffect? }`. Each `PolicyRule` has `action`, `effect` (`ALLOW`/`DENY`/`REQUIRE_APPROVAL`), an optional ABAC `condition` (actor role, resource type, environment, `agentId`/`agentVersion`, `workflowId`/`workflowVersion`, `riskClass`), and, for approval-shaped rules, `requiredApprovers?`/`enforceSeparationOfDuties?`/`requiredRejections?` (DEVOS-143/144/146). `evaluatePolicies` is **purely declarative rule matching** — latest-published-per-key, first exact match wins, deterministic by explicit design intent (the evaluator's own doc comment cites the spec requirement that policy decisions be "independent of model output"). **No numeric or statistical input is accepted anywhere in this evaluation path.** |
| Approval gate configuration | `packages/application/src/tasks/run-approval-task.ts:34-99`, `packages/application/src/approval/decide-approval.ts:55-231`, `packages/domain/src/approval/approval.ts:32-80` | Real, and this is where a gate is actually created (the `APPROVAL` graph node, not a tool-invocation policy check). `ApprovalNodeConfig` is author-set JSON on the workflow node: `approvalType?`, `pollIntervalSeconds?`, `riskClass?`. `resolveApprovalRequirements` resolves `requiredApprovers`/`enforceSeparationOfDuties`/`requiredRejections` from a matching org-level `PUBLISHED` policy rule keyed on `riskClass`, else hardcoded defaults (`1`/`false`/`1`). `decideApproval` only finalizes once distinct `APPROVED` count ≥ `requiredApprovers` or `REJECTED` count ≥ `requiredRejections`, with separation-of-duties and expiry (`expiresAt`, DEVOS-145) enforced. |
| Risk-tier ("risk class") routing | `packages/domain/src/tools/tool-capability.ts:28`, `run-approval-task.ts:45` (`ApprovalNodeConfig.riskClass`) | Real but **entirely static** — `ToolCapabilityRiskClass` (`R0`–`R4`) is a plain author-set field at capability-registration time or workflow-node-authoring time. Routing is a single equality lookup (`condition.riskClass === riskClass`) against a static table keyed by a human-chosen tag. **No function anywhere computes a risk tier from data** — confirmed by grep across `packages/domain`/`packages/policy` (only the two static-field sites exist). |
| Reliability signals that actually exist | `packages/domain/src/engineering-intelligence/{compute-dora-release-metrics,compute-release-recovery-proxy,compute-lead-time}.ts`, `packages/domain/src/agents/compute-agent-version-quality.ts`, `packages/application/src/engineering-intelligence/aggregate-evidence.ts` | Real, and the most credible "reliability" candidates: `computeDoraReleaseMetrics` (deployment frequency, change-failure rate, from `RELEASE_EVIDENCE`); `computeAgentVersionQuality` (E25/Sprint 22, DEVOS-172–176) — a real per-`AgentVersion` pass/rework rate joined from `REVIEW_EVIDENCE.decision` ← `CODE_CHANGE.metadata.agentVersionId`, already exposed via `GET /agents/:agentId/quality`; `aggregateEngineeringEvidence`'s `QualityReport` (review/test/security-scan pass rates, rollback count, rework-cycle count), exposed via `GET /projects/:projectId/engineering-report`. All are **computed on read** — there is no stored `reliability_score` anywhere. `selectAgentForTask` (DEVOS-179, Sprint 23) is the **one place** a reliability signal (`passRate`) already drives a real decision today — but only which agent version is *dispatched*, never an approval requirement. |
| Any existing dynamic approval-reduction mechanism | whole-repo grep for `auto-approve`/`autoApprove`/`skip.?approval`/`waive`/`reliability.?threshold` | **Confirmed absent — zero matches anywhere in source.** E27's Thread A is wholly new functionality: no threshold config field exists on `PolicyRuleCondition`, `PolicyEvaluationRequest`, or `ApprovalNodeConfig`; no code path reads a `QualityReport`/DORA metric/agent-version pass rate and feeds it back into a `Policy` or `Approval`. |
| A pre-existing, disclosed adjacent gap | `DEVOS-BUILD-STATE.md`'s Sprint 15/16 verification-debt entry | A policy's `REQUIRE_APPROVAL` decision on a **tool invocation** still does not create a real `Approval` row at all — `invoke-tool.ts` treats `REQUIRE_APPROVAL` identically to `DENY`. This means the tool-invocation policy path is not mature enough to host a reduction mechanism today; only the `APPROVAL` graph-node path (already real, already exercised in every workflow since Sprint 11/12) is a safe foundation for Thread A. |

**Conclusion Thread A is built on:** "risk-based reduction of human approval gates" cannot be a small extension of anything that exists — every piece (a dynamic threshold config, a code path that reads a reliability signal at approval-creation time, and the decision of what "reduction" means) is green-field. What *is* real and reusable without new capture or new infrastructure is the reliability data itself (`computeAgentVersionQuality`, `aggregateEngineeringEvidence`) and the one already-real gate mechanism (`ApprovalNodeConfig`/`resolveApprovalRequirements`) to attach a reduction to. This document scopes Thread A narrowly: a bounded, floor-protected reduction of `requiredApprovers` on the `APPROVAL` node only, conditioned on a real, already-captured signal — never a full bypass, and never touching the separately-broken tool-invocation `REQUIRE_APPROVAL` path.

## 3. Delivery Principles (carried forward, prior epic backlogs' §3, still correct)

- Extend real, already-provider-agnostic ports (`PullRequestProvider`, `DeploymentProvider`) and the real, already-working `APPROVAL` node/`resolveApprovalRequirements` mechanism — do not redesign either.
- Never fabricate a reliability signal. Thread A reads only `computeAgentVersionQuality`/`aggregateEngineeringEvidence` output that already exists from real captured data — never a new score invented for this epic, the same "never fabricate data" discipline every prior epic backlog has established (E25 §3, E26 §3).
- Never remove a human decision entirely. Thread A reduces `requiredApprovers` within a floor of 1 — it does not add an auto-approve/bypass effect, and it never touches `enforceSeparationOfDuties` downward past what a matching policy already sets. This is a deliberate, disclosed scope limit (§10 Decision 2), not an oversight.
- Zero behaviour change for any existing workflow, policy, or Integration that doesn't opt into the new mechanisms — `resolveApprovalRequirements`'s existing static resolution and both resolvers' existing GitHub/Render inference remain the exact default path, the same principle DEVOS-159/179/187 have each already applied to their own optional extensions.
- Respect tenant isolation and existing audit conventions (ADR-SEC-005, `AGENTS.md` §28): every applied reliability-based reduction is durably recorded against the real evidence that justified it, the same evidence-binding discipline `Approval.evidenceReference` already establishes.
- Do not build a brand-new provider port (CI, Jira) in this document's committed scope — extend an existing one first; a new port is raised as an open decision (§10 Decision 3), not assumed.
- Every sprint ends with demonstrable functionality, verified for real (a real GitHub/GitLab PR pair, a real reliability threshold genuinely crossed by real evidence) — not simulated.

- Any part of a future E28+.

## 10. Open Decisions For The User

1. **One epic or two.** §5 explicitly declines to merge Thread A and Thread B into one epic's narrative the way every prior two-sprint epic did, because — unlike those — the two threads share no code, no data, and no sequencing dependency (§7). **Recommendation:** treat them as two separable epics (e.g. E27 "Integration Adapter Expansion" and E28 "Risk-Based Approval Automation"), authorized and run independently, in whichever order the user prefers — this keeps each epic's own history and "what NOT to build" boundary clean, the same discipline every prior document has applied to a single theme. The alternative — keeping both under one "E27" umbrella with two internal parts, as this document is drafted to allow either way — is equally workable if the user prefers fewer epic labels. Either way, say which framing to use before conversion to `specs/sprints/`.
2. **How far "reduction" should go.** §6.2/DEVOS-199 proposes a bounded, floor-protected reduction of `requiredApprovers` (never to 0, never touching separation-of-duties) as the honest, lowest-risk slice of "risk-based reduction of human approval gates" this codebase's governance discipline (`AGENTS.md` §25/§27/§28) can support without a larger, separately-justified decision to allow full autonomous bypass. If a more radical scope — e.g., a genuine auto-approve/skip-entirely outcome for sufficiently reliable agent versions — is wanted, say so now; it is a materially different (and materially riskier) design than what §6.2 scopes.
3. **New provider port vs. extending an existing one.** §6.1 proposes GitLab (extending the already-provider-agnostic `PullRequestProvider` port) as the single concrete Sprint 27 deliverable, and explicitly excludes building a brand-new CI or Jira port (§9) since neither has any existing shape to extend and each would need its own real third-party account/API chosen and confirmed. If CI or Jira integration is actually the higher-priority want, say so now — it is a larger, differently-shaped scope than this document proposes, and would need its own grounding pass against a chosen real provider.
4. **Scope approval for what's proposed.** If the two-thread, four-plus-five-story breakdown in §6 is the wrong shape (different split, added/removed story, different priority), say so now rather than after Sprint 27/28 begins.
5. Per `AGENTS.md` §35/§4.2, converting whichever sprint(s) are approved into `specs/sprints/sprint-27/` (and/or `sprint-28/`) task files, and any implementation, still requires your explicit separate approval.
