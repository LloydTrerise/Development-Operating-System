**Conclusion this backlog is built on:** the source line's three sub-themes are three genuinely different-sized gaps, not one. "Organisation-specific agent authoring beyond the template CRUD already built" is real, buildable, and foundational — the real `Agent`/`AgentVersion` model already exists but has no versioning-iteration primitive and no UI at all. "Output-quality evaluation" is real and buildable _at the granularity the existing binary review decision honestly supports_ — a per-agent-version pass/rework rate, computed from data that already exists, the same "capture is real, no reporting surface yet" pattern E23/E24 both found for their own themes — not the richer `EvaluationPolicy` model the pre-POC spec describes, which would need a new policy engine this document does not scope. "Agent marketplace" is the most novel piece: a genuinely new capability with zero existing mechanism, which this document scopes narrowly and organisation-scoped only (never cross-organisation, per ADR-SEC-005), mirroring the tenant-isolation discipline every prior epic has maintained.

## 3. Delivery Principles (carried forward, prior epic backlogs' §3, still correct)

- Extend the real `Agent`/`AgentVersion` mechanism that already works (draft → publish, `DRAFT`/`PUBLISHED`/`RETIRED`) — do not replace it with a new agent-management subsystem.
- Never fabricate an evaluation score. The only real quality signal this document adds is a pass/rework rate derived directly from the existing `REVIEW_EVIDENCE.decision` — never a richer weighted score with nothing real behind it, the same "never fabricate data" discipline every prior epic backlog has already established.
- Respect tenant isolation (Security spec ADR-SEC-005): the marketplace is organisation-scoped only, and never crosses organisations — mirroring every prior epic's own real-join, never-a-client-loop, never-cross-tenant precedent (DEVOS-147/150/155).
- Zero behaviour change for any existing selection or workflow that doesn't opt into the new quality-aware tie-break — the same principle DEVOS-159 already applied to its own role/capability selection.
- Every sprint ends with demonstrable functionality, verified for real (real Postgres, a real dev-server run, a real second agent version publish, a real cross-project install) — not simulated.

## 9. What NOT to build in this epic

- The full `EvaluationPolicy`/`Evaluation` entity model `Analysis/DevOS_06_Agent_Framework_Specification_v1.0.docx` §23/§24 describes (a configurable `PASS`/`FAIL`/`REWORK`/`REVIEW`/`INSUFFICIENT_INFORMATION` outcome taxonomy with its own policy engine) — no such policy engine exists or is scoped here; DEVOS-174's own pass/rework rate is the real, honest slice of this that today's binary review decision actually supports.
- Any cross-organisation sharing, listing, or installation — the marketplace is organisation-scoped only, per ADR-SEC-005, the same tenant-isolation boundary every prior epic has maintained without exception.
- Any payment, licensing, rating/review-of-agents-by-humans, or monetization concept for the "marketplace" — this is an internal, same-organisation reuse mechanism, not a commercial product.
- Automatic agent retirement, deprecation, or version-conflict resolution beyond a plain copy-on-install — DEVOS-178's install is a one-time clone, mirroring the existing `ProjectTypeAgent` clone precedent exactly, not a live/linked reference.
- A general-purpose weighted-scoring selection engine — DEVOS-179's tie-break is one disclosed, deterministic secondary sort key (mirrors DEVOS-159's own "no scoring system" principle), not a configurable rules engine.
- Any change to the review agent's own decision logic, or to `getArtifactProvenance` — both reused completely unchanged.
- Duplicating E24 Engineering Intelligence's own organisation-wide dashboards — DEVOS-174's view is agent-version attribution for agent authors/selectors, a different consumer and a different page, not a second copy of `EngineeringIntelligencePage.tsx`.
- Any part of E26–E27.
