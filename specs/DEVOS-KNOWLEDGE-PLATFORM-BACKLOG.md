## 1. Purpose

`specs/architecture/system-context-engineering-knowledge.md` and `specs/workflows/software-change-workflow.md` §28 ("Knowledge and Context Flow") describe a knowledge/context system whose steps are: identify work item and project; resolve approved knowledge sources; retrieve relevant architecture/code/documentation; **apply access controls**; create a context manifest. `specs/DEVOS-POST-POC-BACKLOG-AND-SPRINT-PLAN.md` §10 carried the gap between that description and the POC's actual implementation into E26 as one line, contrasting it against "today's flat permission-tagged source list." This document turns that line into real epics, stories, and sprints — the same way the five prior backlog documents did for their own themes.

As with Governance, Cost, Engineering Intelligence, and Agent Platform, there is no single dedicated pre-POC baseline spec for this theme; `system-context-engineering-knowledge.md` and `software-change-workflow.md` §28 are treated as the authoritative inputs, not re-derived from scratch.

**Conclusion this backlog is built on:** the source line's two nouns — "permission-tagged" and "graph" — do not describe anything that exists or is spec-mandated; they are corrected above rather than propagated. What *is* real and buildable, in the same "extend what's real" discipline every prior epic backlog has followed, are four genuine, independently-verified gaps: (1) knowledge sources are create-only with no UI, the exact pre-E25 agent gap, now the most obviously overdue parity fix; (2) the traceability half of §28's "authorised and traceable" claim is fabricated by omission — the mechanism exists and is silently unused; (3) retrieval is unconditionally flat with zero relevance signal, which a real (not enterprise-grade) improvement can address using this codebase's existing Postgres, with no new infrastructure dependency; (4) there is no cross-project reuse mechanism at all, the most direct interpretation of "enterprise" that this codebase can honestly support without inventing new infrastructure — mirroring E25 Sprint 23's own organisation-scoped, never-cross-tenant sharing precedent, applied to a different resource.

## 3. Delivery Principles (carried forward, prior epic backlogs' §3, still correct)

- Extend the real `KnowledgeSource`/`KnowledgeReference` mechanism that already exists (create, retrieve, a dormant traceability table) — do not replace it with a new knowledge-management subsystem.
- Never fabricate a retrieval signal. §5's relevance retrieval uses Postgres's own built-in full-text search (`tsvector`/`tsquery`) over real `content` already stored — never a vector/embedding score with no real model call behind it, and never a "relevance" number invented without a real query to rank against, the same "never fabricate data" discipline every prior epic backlog has already established (E25 §3 made the identical commitment for its own quality signal).
- Respect tenant isolation (Security spec ADR-SEC-005): knowledge sharing is organisation-scoped only, and never crosses organisations — mirroring E25 Sprint 23's own real-join, never-a-client-loop, never-cross-tenant precedent (DEVOS-177/178).
- Zero behaviour change for any existing workflow run or agent execution that doesn't opt into relevance-scoped retrieval — `buildContext()`'s existing unconditional-inclusion behaviour remains the default when no query context is available, the same principle DEVOS-159/179 already applied to agent selection.
- Every sprint ends with demonstrable functionality, verified for real (real Postgres, a real dev-server run, a real cross-project install, a real durable traceability record) — not simulated.
- Do not introduce a new external dependency (embedding provider, vector database, search service) without the user's explicit confirmation — §10 below raises this as an open decision rather than assuming it.

## 9. What NOT to build in this epic

- Any embeddings, vector database (`pgvector` or otherwise), or semantic/AI-ranked search — DEVOS-187's relevance retrieval is real Postgres full-text search over existing stored text, never a model-scored similarity, unless the user opts into the larger scope raised in §10.
- Any knowledge-graph or relationship model between knowledge sources (supersedes, relates-to, derived-from) — no such concept exists in any spec, pre-POC or POC, per §2's grounding; nothing here should invent one.
- Any cross-organisation sharing, listing, or installation — sharing is organisation-scoped only, per ADR-SEC-005, the same tenant-isolation boundary every prior epic has maintained without exception.
- A general-purpose search/query language over knowledge content — DEVOS-187 is one disclosed, deterministic full-text query shape (work item title/description → matching sources), not a configurable query builder.
- Repository-derived context (`searchRepository`/`retrieveRepositoryFile`/`retrieveRepositoryListing`) remaining unwired — real, but a separate, unrelated mechanism (§2) with no task handler consumer today; wiring it is a distinct, not-yet-scoped gap, deliberately left out of this document to keep E26 focused on the `KnowledgeSource` database concept the source line actually names.
- A richer `status` taxonomy for `KnowledgeSource` beyond `ACTIVE`/`ARCHIVED` (e.g. a draft/review/publish gate mirroring `Agent`'s three-state lifecycle) — no spec requires knowledge edits to go through review, unlike agent/policy/workflow publish; DEVOS-182 proposes the simplest real two-state lifecycle unless the user says otherwise (see §10).
- Automatic content freshness/staleness detection, conflict detection between knowledge sources, or any part of `context-sufficiency.ts`'s already-deferred `Stale`/`Untrusted`/`Conflicting` categories — no data exists anywhere to check any of these against (confirmed unchanged by this document), the same gap that file's own comment already discloses.
- Any part of E27.
