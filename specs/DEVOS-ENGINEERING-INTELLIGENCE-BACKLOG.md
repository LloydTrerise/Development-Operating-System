**Conclusion this backlog is built on:** the same pattern E23's own Grounding section found for cost data repeats almost exactly here — the raw ingredients (task-timing metrics, per-artifact pass/fail evidence, timestamped release/rollback events, an already-working provenance-walk mechanism) are genuinely real and already captured across Sprints 7–14, but **nothing aggregates or surfaces any of it**. Three of the four named DORA metrics (deployment frequency, change failure rate, lead time for changes) are buildable today purely as new queries over existing data, with zero new capture. The fourth (time to restore) and bottleneck analytics both need a small, disclosed, additive real change — a proxy definition for the former, richer metric labels for the latter — neither of which is fabrication, both of which must be presented to a user as exactly what they are: real data under an explicit, disclosed interpretation, not an industry-standard DORA measurement pulled from a system of record DevOS doesn't have (e.g. no real incident-paging tool, no real CI system separate from this platform itself). "Quality trends" is buildable today only at the granularity the evidence artifacts actually support: pass/fail rates and rework-cycle counts over time, not vulnerability severity trends (§9) unless a future story adds structured scan-output parsing.

## 3. Delivery Principles (carried forward, prior epic backlogs' §3, still correct)

- Prioritise closing the specific, named gaps in §2 over speculative generality — extend the real `MetricsRegistry`/artifact-evidence mechanisms that already work; do not build a second, parallel analytics pipeline.
- Never present a computed metric as more authoritative than its real data source supports (mirrors DEVOS-089's cost-estimate disclosure convention exactly) — every DORA figure this epic computes is labelled with the real artifact/event types it was derived from, and every proxy definition (§2's "time to restore" row) is disclosed in the UI itself, not just in this document.
- Respect tenant isolation (Security spec ADR-SEC-005) — any organisation-level rollup aggregates across an organisation's own projects only, mirroring DEVOS-147/DEVOS-150's own real, twice-proven precedent exactly.
- Every sprint ends with demonstrable functionality, verified for real (real Postgres, a real dev-server run, a real deploy/rollback/rework sequence producing a real visible metric) — not simulated.
- No new capture mechanism is added unless a specific story in §6 says so explicitly, and each one that does is scoped as narrowly as possible (e.g. §6's label-richness story adds labels to an existing call site, not a new metrics subsystem).

## 9. What NOT to build in this epic

- **Structured security-scan output parsing (vulnerability counts/severities).** `SECURITY_SCAN_EVIDENCE` today captures only a real pass/fail plus raw `stdout`/`stderr` (§2) — no story in §6 adds parsing of the configured scan tool's own output format. Adding a severity-trend chart with nothing real behind it would mean fabricating structured data this codebase doesn't actually extract today, violating the same "never fabricate data" discipline `DEVOS-COST-MANAGEMENT-BACKLOG.md` §3 already established. A future story could add this if a specific scan tool's real structured-output format is chosen and parsed for real.
- **Full per-node bottleneck attribution.** `DEVOS-170` adds only a `workflowVersionId` label — genuine per-node-id attribution would need a second, larger labelling change (and a real volume-vs-cardinality tradeoff for a metrics registry that keeps every distinct label combination in memory indefinitely) that is explicitly deferred, not silently dropped.
- **Any external BI/analytics tool integration** (Grafana, Looker, Datadog, etc.) — mirrors DEVOS-117's own deliberate "Prometheus only, no second dashboard tool" scoping decision exactly; this epic's own dashboard is the reporting surface, not a connector to a third-party one.
- **Automatic policy/gate changes based on computed metrics** (e.g. auto-loosening an approval gate because change failure rate is low) — that is E27's own named scope ("risk-based gate reduction"), not this epic's; E24 only computes and displays metrics, it does not act on them.
- **A real incident-detection/paging system** — the disclosed time-to-restore proxy (`DEVOS-169`) works entirely from data DevOS already has (release/rollback events, Incident Response work-item lifecycle); this epic does not integrate a real paging tool to get a more precise "detected at" timestamp.
- **Any change to the Tool Gateway, credential broker, identity/auth provider, or the core workflow engine's own execution semantics** — unaffected by this epic, which only reads existing artifact/metrics data and adds one additive label, never changes how a task executes.
- Also out of scope for these two sprints specifically: any part of E25–E27.
