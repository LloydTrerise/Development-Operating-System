## 1. Purpose

`Analysis/DevOS_06_Agent_Framework_Specification_v1.0.docx` §9 ("Agent Selection Algorithm") describes selecting an agent to run a task by matching role/capability, with an optional performance/cost preference layered on top. `specs/DEVOS-COST-MANAGEMENT-BACKLOG.md` §2/§9 confirmed no real algorithm exists today for that preference to attach to. This document turns "build a real selection algorithm" into real, buildable stories — the same way prior backlog documents did for their own themes.

This is a **correction pass, not a fresh gap**, and the correction matters for scoping accurately:

- `DEVOS-COST-MANAGEMENT-BACKLOG.md` §2/§6/§9 describe the router as routing "by a hardcoded seeded `agentRef`, not by role, capability, or any performance/cost preference," citing DEVOS-038's Sprint-2 verification-debt entry.
- That description is **stale**. `DEVOS-PRODUCTION-READINESS-ROADMAP.md` gap **G1** named exactly this ("`agent-task-router.ts` routes `AGENT_TASK` by matching a task's `agentRef` against four hardcoded seeded agent keys, not by the resolved agent version's `role`") and recorded a P1 recommendation to fix it. That fix already shipped — commit `a0086e2` ("Add Organisations & Project Types: management, template cloning, and generalized agent routing"), well before Sprint 17. Direct inspection of `apps/worker/src/agent-task-router.ts` today confirms it resolves a task's `agentRef` to a real `Agent` → its latest `PUBLISHED` `AgentVersion`, then dispatches by that version's `configuration.role` — not a literal four-way string match.
- The **real** remaining gap is narrower and different from what G1 described: `Agent.getByProjectAndKey(projectId, agentRef)` is an exact 1:1 lookup. A workflow node's `agentRef` is a single literal string baked in at authoring time (`packages/contracts/src/workflows.ts`'s `WorkflowNode.agentRef`). There is no _algorithm_ today because there is nothing to choose _among_ — a task never has more than one candidate agent to consider. That is the actual precondition gap this document scopes.

This document does not modify `DEVOS-COST-MANAGEMENT-BACKLOG.md` itself (a different, already-COMPLETE epic's own record) — the stale G1 description there is flagged here, for you to decide separately whether it should be corrected in place.

## 2. Grounding — confirmed against the real, current implementation

Per `AGENTS.md` §7/§8, this section states what is actually true today, verified by direct code inspection.

| Concept                      | Spec intent                                                                                                                      | Current reality (verified)                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Role-based dispatch          | Agent Framework §9 selection criteria                                                                                            | Real and already shipped. `routeAgentTask` (`apps/worker/src/agent-task-router.ts`) resolves `task.input.agentRef` → `Agent` (`getByProjectAndKey`) → latest `PUBLISHED` `AgentVersion` → dispatches via `ROLE_HANDLERS[version.configuration.role]`. Confirmed unrecognized-role and no-published-version cases fail clearly.                                                                                                                                 |
| Multiple candidates per role | Agent Framework §9 ("Apply optional performance/cost preferences" implies more than one eligible agent exists to prefer between) | Not modeled anywhere today. `AgentRepository.getByProjectAndKey` is a single-key exact lookup; nothing enumerates "every agent in this project with role X." A seeded project has exactly one `Agent` per role (six total, confirmed by DEVOS-124/125's own evidence) — no project in this codebase has ever had two agents sharing a role.                                                                                                                    |
| Node-level targeting         | —                                                                                                                                | `WorkflowNode` (`packages/contracts/src/workflows.ts`) has exactly one targeting field: `agentRef?: string`, a literal key. `validateWorkflowDefinition` (`packages/domain/src/workflows/validation.ts`) requires it to be a non-empty string for every `AGENT_TASK` node — there is no alternative, role-based way to declare "any agent capable of X" today.                                                                                                 |
| Capability data              | Agent Framework §9 Selection Criteria table                                                                                      | `AgentConfiguration.allowedCapabilities: string[]` (`packages/contracts/src/agents.ts`) already exists and is already enforced elsewhere (DEVOS-085's Tool Gateway capability check) — real, usable data, just never read by the router. No cost/quality/tier field exists on `AgentConfiguration` at all — confirms §2's own cost-management-backlog finding that "cost-aware" specifically has no data yet, independent of the selection-algorithm question. |
| Task input plumbing          | —                                                                                                                                | `run-creation.ts` folds `node.agentRef` into each `WorkflowTask.input.agentRef` at run-start, the same reserved-key extensibility point `correlationId`/`dependsOn` already use (DEVOS-088/096's own precedent) — the natural, already-proven place to add a second, alternative reserved key.                                                                                                                                                                 |

**Conclusion this backlog is built on:** the pieces a real capability-based selection algorithm needs (published `AgentVersion`s, a real `role` field, a real `allowedCapabilities` array, an established task-input extensibility pattern) already exist and are already real. What's missing is the ability for a workflow node to target a _role_ instead of a _literal agent_, a project's ability to have more than one real candidate for a role, and the actual selection function that picks between them. This document builds exactly that — and nothing about cost, since no cost data exists yet (unchanged from `DEVOS-COST-MANAGEMENT-BACKLOG.md`'s own finding).

## 9. What NOT to build in this sprint

- Any cost, quality, latency, or budget-tier preference in the selection algorithm itself — no such data exists yet (`DEVOS-COST-MANAGEMENT-BACKLOG.md` §2/§9), and fabricating a preference with nothing real behind it would violate this codebase's own established "never fabricate data" discipline.
- Tool-invocation cost tracking — the other, unrelated Sprint-19-named item; still blocked on a real provider cost figure, untouched by this document.
- Automatic load balancing, failover, or retry-with-a-different-agent on task failure — selection happens once, at dispatch time, the same as today's literal-`agentRef` resolution; no new runtime retry semantics.
- Any change to the Tool Gateway, credential broker, or identity/auth provider — unaffected by this document, which changes only which agent a task resolves to, not how tools or agents are invoked once resolved.
- A general-purpose rules engine or weighted-scoring system for selection — the disclosed, deterministic tie-break rule (§6, DEVOS-159) is intentionally simple; a richer scoring model is future work only if a real need for it appears.
