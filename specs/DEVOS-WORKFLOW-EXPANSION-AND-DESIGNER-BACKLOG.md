## 1. Purpose

`Analysis/DevOS_POC_Product_Backlog_and_Sprint_Plan_v1.0.docx` §41 ("Post-POC Roadmap Themes") lists, in order: Workflow Expansion, Workflow Designer, Governance, Cost, Engineering Intelligence, Agent Platform, Knowledge, Autonomy, Integrations. The post-POC backlog already carried this exact order into `E20`–`E27`. This document turns the first two themes — **E20 Workflow Expansion** and **E21 Workflow Designer** — into real epics, stories and sprints, the same way `DEVOS-POST-POC-BACKLOG-AND-SPRINT-PLAN.md` §7/§8 did for E17/E18 before Sprint 9 began.

Two pre-POC baseline specifications exist for exactly this scope and are treated as authoritative inputs here, not re-derived from scratch:

- `Analysis/DevOS_05_Workflow_Engine_Specification_v1.0.docx` — the execution-kernel design (node types, concurrency, conditions, human tasks, validation, acceptance criteria).
- `Analysis/DevOS_14_Workflow_Designer_Specification_v1.0.docx` — the authoring-layer design (component palette, lifecycle, validation severities, versioning/diff, workflow library, explicit MVP scope and explicit deferrals).

Both predate the POC by design (their own "Future Capabilities"/§39/§48 sections list "visual workflow designer" and equivalents as _future_ work relative to themselves) — the POC intentionally built only the reference Software Change Workflow against a narrow slice of each. This document is the reconciliation: what those two specs originally called for, against what Sprints 1–10 actually built, scoped into buildable stories.

## 2. Grounding — confirmed against the real, current implementation

Per `AGENTS.md` §7/§8, this section states what is actually true today, verified by direct code inspection, not assumed from the original specs' aspirational scope.

| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Workflow node types                           | `Analysis/DevOS_14...` §7 palette: Trigger, Task, Agent Task, Tool Task, Human Task, Approval, Condition, Parallel, Join, Wait, Loop, Subworkflow, Artifact, Notification, End | `@devos/contracts`' `workflowNodeTypes` (`packages/contracts/src/status.ts`) declares only `TRIGGER, TASK, AGENT_TASK, TOOL_TASK, APPROVAL, CONDITION, PARALLEL, JOIN, WAIT, END` — already narrower than the spec's palette (no Human Task, Loop, Subworkflow, Artifact, or Notification node types).                                                                                                                                                                                                                                                                                                                                           |

Placing an `APPROVAL`, `CONDITION`, `PARALLEL`, `JOIN`, or `WAIT` node in a graph today reaches `task-dispatcher.ts`'s `No handler registered for task type "..."` failure at run time — confirmed by reading `task-dispatcher.ts`'s handler-map lookup and every `registerHandler` call site. These four node types exist **only as an accepted enum value**, not as executable behaviour.                                              |
| Approval as a graph primitive                 | §14: Approval is a node in the graph, with approver role, target, evidence, risk, expiry                                                                                       | Today's "approval" is not a graph node at all — it is a `PENDING` gate created by `requestApproval`/`decideApproval` against a **marker in the workflow version's own `policies` array** (`transitionAfterApprovalDecisionInTrx`'s type-derived map, `DEVOS-BUILD-STATE.md`'s DEVOS-047/073 history), consulted at two fixed points the current 4-workflow chain hardcodes (post-planning, post-release-readiness). It is real and policy-gated (DEVOS-110/111), but it is not something a workflow author can place anywhere in an arbitrary graph shape the way §14 describes.                                                                 |
| Edges / branching                             | §15/§16: Conditions are deterministic, evaluated by the engine, and drive real branching                                                                                       | `packages/domain/src/workflows/validation.ts` validates edges for **referential integrity only** (a `from`/`to` must name a declared node id) — confirmed by its own code comment: "this codebase does not traverse edges for execution ordering." `run-creation.ts` creates a `WorkflowTask` for **every** node in the graph unconditionally; the only edge-driven behaviour that exists is Sprint 9's `dependsOn` barrier (`claimNext()` won't claim a task until its named upstream dependencies reach `SUCCEEDED`) — a _sequencing_ mechanism, not a _branching_ one. There is no code path anywhere that skips a node based on a condition. |
| A second, genuinely different workflow type   | §35 (Designer): Software Change, Incident Response, Release, Quality, Documentation, Dependency Update templates                                                               | Exactly one shape exists in the whole codebase: the 4-workflow Software Change chain (`intake-to-artifact` → `planning-path` → `development-path` → `release-path`), and it is the only thing every seeded `ProjectType` template currently clones (`specs/architecture/organisations-and-project-types.md` §7). No other workflow shape has ever been authored, validated, or run.                                                                                                                                                                                                                                                              |
| Visual workflow authoring                     | §6/§37 (Designer): drag-and-drop canvas, palette, contextual inspector, zoom/pan/minimap                                                                                       | `specs/architecture/organisations-and-project-types.md` §10.1/§12.2 (already implemented, `ProjectTypeWorkflowsEditor.tsx`) is an explicit, self-declared stand-in: "a structured form editor, **not** a visual graph canvas... a visual canvas is a natural, larger follow-up if the form editor proves too limiting in practice." That follow-up has not been built. There is no drag-and-drop canvas, no properties inspector beyond a table row's inline fields, and no execution-path preview, dry-run, version diff, or workflow library anywhere in `apps/web`.                                                                           |
| Per-project workflow authoring UI             | Every published `WorkflowVersion` should be authorable                                                                                                                         | `specs/architecture/organisations-and-project-types.md` §2 confirms: "the web app has zero client functions or UI for it" for `WorkflowVersion`'s own draft → validate → publish lifecycle. The only workflow-authoring surface in the entire product is the Project Type _template_ editor — a project's own cloned, independent workflow (which the same spec's §3 explicitly makes freely editable after cloning) has no UI path to actually edit it today.                                                                                                                                                                                   |

**Conclusion this backlog is built on:** Workflow Expansion (E20) is blocked on real, missing _engine_ behaviour, not UI — a second workflow type that actually needs a condition, a parallel branch, a wait, or a human gate somewhere other than the two hardcoded points cannot be built today regardless of how it's authored. Workflow Designer (E21) is blocked on a _UI_ gap the product itself already flagged and deferred. The post-POC backlog's own dependency note (§11: "E21 additionally depends on E20... per the original plan's own explicit sequencing") is correct and load-bearing here for a second reason beyond the original plan's: the designer's component palette (§7 of the Designer spec) cannot let an author place a real Condition/Parallel/Wait node until the engine can actually run one.

## 3. Delivery Principles (carried forward, `DEVOS-POST-POC-BACKLOG-AND-SPRINT-PLAN.md` §2, still correct)

- Prioritise closing what already blocks real capability over speculative generality — build the second workflow type the theme's own source example names (Incident Response, §41/§35), not an abstract "any workflow shape" engine.
- Keep published workflow definitions immutable; keep agent authority outside the model — both already proven through Sprint 1–10, both must survive new node types and a visual authoring surface untouched.
- Every sprint ends with demonstrable functionality, verified for real (real Postgres, real dev servers, a real end-to-end run) — not simulated.
- Per the Designer spec's own Design Principle: "design for a small number of understandable primitives before adding advanced orchestration" — this backlog implements exactly the primitives §2 above shows are missing (Condition, Parallel/Join, Wait, a first-class Approval node), not the full aspirational palette (Loop, Subworkflow, Human Task, Artifact, Notification are explicitly deferred — see §9 below).
- Per the Designer spec's own MVP/deferred split (§45/§46): a visual canvas that authors, validates, versions and previews is in scope; natural-language workflow generation, AI-assisted optimisation, real-time collaborative editing, and a workflow marketplace are explicitly not.

## 8. Dependencies

- E21 (Sprints 13–14) depends on E20 (Sprints 11–12) for its palette to be meaningful — `DEVOS-129`'s palette items must correspond to node types the engine can actually run, per §2's grounding table above and the post-POC backlog's own already-stated E20→E21 sequencing.
- `DEVOS-122` (Approval as a graph node) is the one E20 story with a real design decision to confirm before implementation: whether the existing policies-array-marker mechanism is generalized to be addressable by node id, or a graph `APPROVAL` node becomes a thin wrapper that calls the existing mechanism at that point in traversal. Flag in review — this affects `DEVOS-131`/`DEVOS-130`'s inspector design in Sprint 13.
- `DEVOS-124`'s tool-capability/agent-role choices for Incident Response should avoid inventing a new real external provider (paging, status pages) unless the user explicitly authorizes one, mirroring this codebase's own long-standing "real-vs-simulated" scoping discipline (Sprint 4–9's Git/deployment/credential precedent) — a local-staging-equivalent simulation is an acceptable, disclosed substitute for this epic's purpose (proving the _engine primitives_, not adding a new real integration).

## 10. What NOT to build in Sprints 11–14

Per the Workflow Designer spec's own §46 "Explicitly Deferred" list (carried forward verbatim, still correct): advanced loops, complex dynamic graph generation, natural-language-to-workflow generation, AI-assisted workflow optimisation, full visual debugging, real-time collaborative editing, a marketplace of third-party workflow components, advanced simulation against production replicas, automatic workflow generation from historical runs. Also out of scope for these four sprints specifically: a `LOOP`, `SUBWORKFLOW`, `HUMAN_TASK`, `ARTIFACT`, or `NOTIFICATION` node type (none of these are in `@devos/contracts`' current `workflowNodeTypes` enum — adding one would be a contract change beyond "make the already-declared enum real," which is this backlog's actual scope), and any part of E22–E27.
