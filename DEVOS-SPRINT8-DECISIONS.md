## DEVOS-094 — Reliability hardening

**Decision:** `TaskQueue.complete()`/`fail()` previously updated a `workflow_tasks` row by `id` alone — a worker that was genuinely still alive but running past `reclaimStale()`'s purely time-based threshold (a slow build, a slow real model call, not a crash) could be reclaimed by a restarted worker while still working, and its eventual, real completion would then silently overwrite whatever the reclaiming worker had already recorded. Fixed at the `TaskQueue` interface level (`packages/domain/src/workflows/task-queue.ts`): both methods now take the `attempt` the caller believes it still holds (the `WorkflowTask.attempt` it was handed by `claimNext()`) as a fencing token. The real Postgres implementation (`packages/database/src/repositories/task-queue.ts`) applies `complete()`'s UPDATE only `WHERE id = taskId AND status = 'RUNNING' AND attempt = attempt`, via `executeTakeFirst()` (not `executeTakeFirstOrThrow()`) — no matching row means the call is a safe no-op, not an error, not corruption. `fail()` gained the same guard ahead of its existing `resolveTaskFailure()` logic. `reclaimStale()` itself is unaffected — it already re-checks `status = 'RUNNING'` under its own row lock inside its own transaction, and calls `resolveTaskFailure()` directly rather than through the now-fenced public `fail()`. `apps/worker/src/task-dispatcher.ts`'s `processNext()` now threads `task.attempt` into both its `queue.complete()` and `queue.fail()` calls (all three call sites: the no-handler-registered path, the success path, and the caught-error path).

**Live verification, reproducing the exact race against real Postgres:** Added a new `describe('DEVOS-094: completion fencing against a stale reclaim')` block to `tests/e2e/hardening.test.ts`, using `createPostgresTaskQueue` primitives directly (not simulated) against the real local Postgres: worker A claims a task (attempt 1) and is treated as still genuinely working; a reclaim pass (`reclaimStale(0)`, threshold 0 so every RUNNING row is immediately eligible — same mechanism a restarted worker's timer-driven reclaim uses) resets it to PENDING; worker B claims it (attempt 2) and completes it first, and the run reaches `COMPLETED` with B's real output recorded; worker A, unaware, then calls `complete()` with its stale attempt-1 token — confirmed to be a true no-op: the task's status/output/attempt and the run's `COMPLETED` status are all unchanged, still exactly what B recorded. A's late `fail()` call (same stale attempt) was confirmed equally inert.

**Real bug proven, not just asserted:** Per this session's established discipline, the fix was backed up, reverted (`complete()`'s fencing removed, back to update-by-id-alone), `@devos/database` rebuilt so the e2e suite (which imports its compiled `dist/`, not source) actually exercised the reverted code, and the new test re-run — it failed exactly as predicted: `expected { completedBy: 'workerA-late' } to deeply equal { completedBy: 'workerB' }`, i.e. worker A's late completion silently clobbered worker B's real, already-recorded outcome. The fix was then restored from the backup, `@devos/database` rebuilt again, and the full suite reconfirmed green.

**Files changed:** `packages/domain/src/workflows/task-queue.ts` (interface signatures + fencing-token doc comments), `packages/database/src/repositories/task-queue.ts` (`complete()`/`fail()` fencing), `apps/worker/src/task-dispatcher.ts` (`processNext()` threads `task.attempt` through all three `complete()`/`fail()` call sites), `apps/worker/tests/task-dispatcher.test.ts` (fake `TaskQueue` signatures updated to match), `tests/e2e/hardening.test.ts` (two existing `queue.complete()` call sites updated to pass `attempt`; new DEVOS-094 race-reproduction test added).

**Full validation:** Forced `pnpm turbo run typecheck test lint build --filter=@devos/domain --filter=@devos/database --filter=@devos/worker --force`: 22/22 tasks green. `@devos/e2e-tests` typecheck/lint clean; its real-Postgres suite (`tests/e2e`, `fileParallelism: false`) 13/13 tests green across all 6 files, including the new DEVOS-094 test and the two pre-existing DEVOS-092 real-`TaskDispatcher` recovery tests (unaffected — neither exercises a completion race, only a crashed/abandoned worker whose handler never resolves at all). `prettier --check` clean on every touched file.
