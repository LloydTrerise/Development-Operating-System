## DEVOS-104 — Real GitHub `PullRequestProvider` adapter

### Loose end 2 — the DEVOS-096 task-dispatch-ordering race, root-caused by DEVOS-108, now fixed

**Decision:** `run-creation.ts` (`startRunForVersion`) now folds each node's real upstream dependencies — every `edge.from` where `edge.to === node.id`, read directly from the workflow version's own already-populated, already-validated (DEVOS-096) `definition.edges` — into that node's task as `input.dependsOn: string[]`, the same extensibility point `agentRef`/`correlationId` already use (no new column). `claimNext()` (`packages/database/src/repositories/task-queue.ts`) now refuses to claim a `PENDING` task until every task named in its own `dependsOn` has reached `SUCCEEDED` in the same run — enforced as a real, atomic barrier inside the same `SELECT ... FOR UPDATE SKIP LOCKED` query that does the claiming (a `NOT EXISTS`/`jsonb_array_elements_text` subquery, this codebase's first use of Kysely's raw `sql` tag — every prior query used the pure query-builder API), not a separate check with its own race window. Verified directly against a hand-built, isolated SQL reproduction (a temp table, no application code involved) before trusting the real fix, and again end-to-end against real Postgres via `tests/e2e/hardening.test.ts`'s three new tests, one of which deliberately gives the downstream task an _earlier_ `createdAt` than its upstream dependency specifically to prove the barrier is real, not an accident of the pre-existing ordering hint.

**A necessary companion fix, not scope creep:** once a task can be genuinely blocked on a dependency that itself permanently fails, that downstream task would otherwise sit `PENDING` forever — claimable-but-never-claimable, since its dependency will never reach `SUCCEEDED`. Before this fix, such a task would eventually get claimed anyway, fail immediately on its own missing-upstream-artifact check, and reach a terminal `FAILED` status through its own wasteful retry-then-fail cycle. `resolveTaskFailure` now marks every remaining `PENDING` sibling task in the same run `FAILED` (`DEVOS_UPSTREAM_TASK_FAILED`, "Not attempted") at the same moment the run itself becomes permanently `FAILED` — preserving the pre-existing "a failed run's tasks are all terminal" invariant without the wasted attempts. Covered by its own new test.

**A real debugging lesson, not a design flaw, hit twice in one session:** the first attempt at verifying this fix against real Postgres failed with the barrier apparently not working at all — not a logic bug (confirmed by testing the exact SQL in isolation against a temp table first, which behaved correctly), but `tests/e2e` importing `@devos/database`'s compiled `dist/` output, which a source-only edit does not update. The same class of mistake DEVOS-108's own entry above already flagged once this session (`apps/worker`/`apps/api`'s `dev` scripts) — this is its second, independent occurrence (`tests/e2e`), confirming it as a recurring, worth-remembering-for-real pattern in this monorepo, not a one-off.
