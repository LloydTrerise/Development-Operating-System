## DEVOS-114 — Wire a real rollback trigger

**Root cause found before implementing:** `runReleaseRollbackTask` (DEVOS-077) reads `task.input.rollbackToRevision`, but `run-creation.ts` (`startRunForVersion`) never folded a run-start caller's own generic `inputs` (`StartRunInput.inputs`, already accepted end-to-end by the real `POST /api/v1/workflows/:id/runs` API and stored on `run.input`) into any individual task's own `input` — only `agentRef`/`correlationId`/`dependsOn` were ever threaded that way. This is why the function had "no flagged gap" of its own (it was already real and tested) but also no real caller: nothing in the engine could ever have gotten a caller-supplied revision to it. Fixed by spreading `input.inputs` into every task's own `input`, with the existing reserved system-managed keys (`agentRef`/`correlationId`/`dependsOn`) spread afterward so they always win over a same-named caller input — additive only; no existing task handler reads any other key from `task.input`, so every other workflow's behavior is unaffected (confirmed via the existing `dependsOn`/`correlationId` test's `toMatchObject` assertions, which don't break under an extra key, plus a new dedicated reserved-key-wins test).

**Real trigger chosen: a real UI action**, per the task's own stated preference ("the more immediately useful option, given `apps/web` already has a Runs page") — and `apps/web`'s `RunsPage.tsx` already had a real, working, generic "start a run" form (pick a work item, pick a workflow, submit), reachable through the real API, not a mock. Rather than inventing a bespoke rollback screen, that same generic form now detects the new `release-rollback` workflow (by its real seeded `key`) and reveals one additional required field, "Revision to roll back to," folding it into the same real `inputs` the form already sends — reusing real, existing UI/API plumbing rather than adding a parallel path.

**New `release-rollback` workflow — a separate single-node workflow, not a new `release-path` node:** a rollback isn't a stage in the standard release pipeline (it never runs as part of a normal release, and needs a real caller-supplied `rollbackToRevision` no other release-path node needs), so `SEED_RELEASE_ROLLBACK_WORKFLOW_DEFINITION_ID`/`_VERSION_ID`/`_GRAPH` (`seed-constants.ts`, new) is its own real `workflow_definitions`/`workflow_versions` row pair under `SEED_PROJECT_ID` (one `TOOL_TASK` node, `id: 'rollback'`, no edges, no approval-gate policy — an authorized rollback is itself the authorization, per DEVOS-077's own design). `routeToolTask` (`apps/worker/src/tool-task-router.ts`) gained a `'rollback'` case dispatching to the existing, unchanged `runReleaseRollbackTask`.

## DEVOS-118 — Move rate limiting to a shared store

**Flagged gap, resolved as this task's own recorded choice:** Redis, the sprint README's own suggested example — self-hosted here via `infrastructure/docker/docker-compose.yml`'s new `redis` service, the same precedent DEVOS-106/117 already set for Vault/Prometheus. `ioredis` added to `apps/api` (no existing Redis client anywhere in the monorepo, confirmed by search first).

**Implementation:** `RateLimiter.tryAcquire` is now `Promise<boolean>` rather than plain `boolean` — the one shape change both the pre-existing in-process limiter (DEVOS-091) and this task's real shared-store backend share, so callers don't need two different interfaces. `createRedisRateLimiter` (`apps/api/src/http/rate-limiter.ts`) keeps a sliding-window log per key in a Redis sorted set, scored by request timestamp — but the read-count-then-write sequence a naive implementation would use is a real race under genuine concurrent load from multiple processes (two simultaneous requests could both read a count just under the limit, then both write, exceeding it). The entire check-and-increment runs as one atomic Lua script via `EVAL`, the standard, correct way to make a multi-step Redis operation atomic across concurrent real clients — not a check-then-act pair hoping requests don't interleave.

**Selection, mirroring DEVOS-106/107's own established pattern exactly:** `apps/api/src/app.ts` uses the real Redis-backed limiter by default whenever `REDIS_URL` is configured (`@devos/config`'s new `rateLimit.redisUrl`, wired through `environment.ts`/`validation.ts`/`config.ts` the identical way `VAULT_ADDR`/`VAULT_TOKEN` already are), falling back to the pre-existing in-process limiter otherwise — every existing test/local-dev run that never sets `REDIS_URL` is completely unaffected, and `options.mutationRateLimiter`'s own test-override escape hatch (`apps/api/tests/app.test.ts`) still works unchanged, since it's checked first and short-circuits Redis-client creation entirely.

**Files changed:** `apps/api/src/http/rate-limiter.ts` (`createRedisRateLimiter`, new; `RateLimiter.tryAcquire` now async), `app.ts` (selection logic, `await` at the one real call site, Redis client disconnected in `close()`), `package.json` (`ioredis`); `packages/config/src/config.ts` (new `RateLimitConfig`), `environment.ts`, `validation.ts` (`REDIS_URL`, mirroring `VAULT_ADDR`'s exact validation shape); `infrastructure/docker/docker-compose.yml` (new `redis` service); `.env.example` (`REDIS_URL`, not a secret); test files: `apps/api/tests/rate-limiter.test.ts` (existing three cases converted to `async`/`await`, behavior unchanged), `packages/config/tests/config.test.ts` (4 new cases mirroring the existing `VAULT_ADDR` coverage exactly — loads, omits, blank-treated-as-absent, malformed-rejected); `tests/e2e/rate-limiter-redis.test.ts` (new).
