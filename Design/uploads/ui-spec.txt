[Heading1] 1. Executive Summary
DevOS should present a single engineering workspace in which users can understand work, inspect workflow progress, review agent activity, inspect artifacts, approve consequential actions and intervene when necessary.
The UI should not attempt to expose every internal platform concept equally. The primary experience should be task-oriented: what is happening, what has been produced, what needs attention and what happens next.
The design should make autonomous activity observable without overwhelming users with model-level detail. Users should be able to drill from a high-level workflow view into tasks, agents, context, tool calls and artifacts when they need evidence.
[Heading1] 2. UX Principles
Work first: organise the experience around engineering work rather than AI novelty.
Human control: users can understand, approve, pause and stop automation.
Progressive disclosure: show summaries first, evidence on demand.
Traceability: every important action can be followed to its source and output.
Explainability without exposing hidden chain-of-thought: show decisions, evidence, policies and outcomes, not private model reasoning.
Consistency: common interaction patterns across workflows, agents, artifacts and integrations.
Safe defaults: destructive actions are visibly differentiated and protected.
Low cognitive load: users should not need to understand DevOS internals to use it.
Fast path for experts: keyboard navigation, search and deep links.
Accessible by design.

[Heading1] 35. Design System
Use a consistent component library.
Use semantic status indicators rather than colour alone.
Use cards sparingly; prioritise information hierarchy.
Use tables for dense operational data.
Use timelines for execution history.
Use drawers/modals for focused inspection.
Use confirmation dialogs for consequential actions.
Maintain consistent spacing, typography and interaction states.

[Heading1] 46. Empty States
Explain what the screen is for.
Provide the most useful next action.
Do not imply a failure when there is simply no data.
Respect permissions when explaining unavailable resources.
[Heading1] 47. Loading States
Use skeletons for page-level loading.
Use progress indicators for long-running operations.
Show stage/task status for workflow execution.
Do not display fake progress.
Where duration is unpredictable, show elapsed time and current state.

[Heading1] 51. Architectural Decisions
[Heading2] ADR-UX-001: Work-centric UI
The primary navigation and dashboards are organised around engineering work and outcomes rather than AI components.
[Heading2] ADR-UX-002: Progressive disclosure
Summaries are shown first; detailed execution evidence is available on demand.
[Heading2] ADR-UX-003: Server-side security
The UI never acts as the security boundary; all permissions are enforced by the platform.
[Heading2] ADR-UX-004: No chain-of-thought
DevOS exposes inputs, evidence, actions, decisions and outcomes rather than private model reasoning.
[Heading2] ADR-UX-005: Workflow run as primary operational view
The workflow run provides the central operational representation of autonomous engineering work.
[Heading2] ADR-UX-006: Desktop-first engineering experience
Core development workflows are optimised for desktop, while mobile focuses on alerts, approvals and monitoring.

[Heading1] 53. Conclusion
The DevOS UI should make autonomous software development understandable and controllable. The user should be able to move from a work item to workflow progress, agent activity, tools, artifacts, approvals and final evidence without needing to understand the internal architecture.
The workflow run is the central operational experience. Around it, the UI provides work management, artifacts, agents, knowledge, approvals, integrations and administration. This creates a product experience that feels like an engineering operating environment rather than a collection of AI utilities.
