# DevOS Production-Readiness Roadmap

**Product:** DevOS
**Task:** DEVOS-103 — Production-readiness roadmap (Sprint 8, last task); A1/A2/A3/C1 closed by Sprint 9 (DEVOS-104–108); B1/B2/D1/D2/D4/D5/E2/E3/F1/F2 closed by Sprint 10 (DEVOS-109–118)
**Last Updated:** 2026-08-29

## Purpose

This document consolidates every sprint's own carried-forward "explicit
verification debt" — already tracked, sprint by sprint, in
`DEVOS-BUILD-STATE.md`'s own verification-debt section and each sprint's
own `DEVOS-SPRINTn-DECISIONS.md` — into a single, prioritized
production-readiness gap list. It is a synthesis of already-identified,
already-flagged gaps, not a re-derivation of new ones: every item below is
traceable to the specific task and decision-log entry that originally
flagged it.

**No target production architecture is specified anywhere in the spec
corpus.** The recommendations in the right-hand column of each table below
(a real external secret-management provider, a real distributed
metrics/tracing backend, real cloud deployment, a real OIDC-based auth
provider, and similar) are this document's own reasonable proposals,
grounded in this codebase's own already-identified gaps — explicitly
flagged as recommendations for a future decision, not committed future
work.

## How to read this document

Each table row names a real gap, the task/decision-log entry that
originally flagged it, why it exists (the scoping reason, not an oversight
in most cases), and a recommended next step. Priority is this document's
own judgment, not a spec-stated ranking: **P0** blocks any real production
deployment; **P1** should be resolved before meaningful production load;
**P2** is a real but lower-urgency gap.

## Priority summary

- **P0 (blocks any real production deployment): none remaining.** A1 (real GitHub integration), A2 (real deployment provider), A3 (real secret management), and C1 (real OIDC auth) — every P0 item this document ever named — are all CLOSED as of Sprint 9 (DEVOS-104–108, 2026-08-28), each with real, live evidence recorded in `DEVOS-SPRINT9-DECISIONS.md`. This satisfies Sprint 9's own exit criterion ("the full monorepo validation gate is green, and this document's P0 row is empty").
- **P1 (resolve before meaningful production load): only G1 remains.** B1/B2 (metrics/tracing export, shared rate-limit store), D1/D2/D4/D5 (context/policy engine wiring, atomic approval transaction, re-planning loop), E2/E3 (real security scanning, wired rollback), and F1/F2 (audit/capability coverage extension) — every P1 item this document named except G1 — are all CLOSED as of Sprint 10 (DEVOS-109–118, 2026-08-29), each with real, live evidence recorded in `DEVOS-SPRINT10-DECISIONS.md`. G1 (role-based agent routing) was not in Sprint 10's own scope and remains open.
- **P2 (real but lower urgency):** B3, D3/D6, E1/E4, F3, G2, H1–H4, I1.
- **New this sprint, found and fixed (not carried forward as debt):** DEVOS-108 found (and fixed) a real task-dispatcher-adjacent gap while live-verifying against a real private GitHub remote — `runGit` had no defense against a git operation that can't authenticate hanging forever on an interactive credential prompt (fixed with `GIT_TERMINAL_PROMPT=0` + `-c credential.helper=`, both now unconditional). It also confirmed, via live investigation of a real DEVOS-108-introduced test failure, that DEVOS-096's own already-recorded "tasks are not dependency-ordered at dispatch" gap was not merely theoretical — it produced a real, reproducible race under real timing variance. Unlike a typical carried-forward gap, this one was also fixed the same sprint, as an explicit user-requested follow-up: `run-creation.ts` now folds each node's real upstream dependencies (from the workflow graph's own declared edges) into its task's `input.dependsOn`, and `claimNext()` refuses to claim a task until every dependency named there has reached `SUCCEEDED` in the same run, enforced atomically inside the claiming query itself — proven against real Postgres with the downstream task's `createdAt` deliberately set earlier than its upstream's. Not added as a new lettered row here since it's already resolved, not open debt — both are recorded in full in `DEVOS-SPRINT9-DECISIONS.md`'s "Sprint 9 loose ends" section.
- **Sprint 10 (DEVOS-109–118), found and fixed in the process, not carried forward as debt:** DEVOS-116's own named example (review-agent "tool use") did not correspond to real code — the real, adjacent gap actually found and fixed there was `agentVersionId` being checked for the DEVOS-085 gate but never durably recorded on the invocation/audit trail (now fixed, mirroring `correlationId`). DEVOS-117's live verification hit a real, root-caused debugging detour (a respawning `tsx watch` child racing a fresh worker for the same real queue rows), resolved via full process-tree inspection, not assumed. Two transient e2e batch-run flakes were hit while stress-testing DEVOS-118's own real verification, both attributed to genuine Windows resource contention under heavy parallel `tests/e2e` load (the same class already recorded above for DEVOS-108/Sprint-9-loose-ends), confirmed not code defects by isolated re-runs. One real, disclosed verification gap remains: DEVOS-113's own new stage could not be freshly live-re-verified against a real Gemini call in two pre-existing e2e files, blocked by the real Gemini free-tier daily quota exhausted mid-session — reported explicitly rather than silently worked around. Full detail in `DEVOS-SPRINT10-DECISIONS.md`.

None of the items above block this POC's own stated success criteria (DEVOS-102's own review confirmed 9 of 10 fully met, the 10th honestly stated as structurally supported but not yet stress-tested) — every item here is about what would need to change to move from a proven POC to a real production deployment, consistent with `specs/product/devos-product-overview.md` §7's own Phase 8 framing ("Harden and pilot the platform") as the last of eight planned phases, not the final destination.
