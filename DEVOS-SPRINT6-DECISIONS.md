## DEVOS-077 — Implement Release Failure Handling

**A genuine, pre-existing gap this task's own acceptance criteria required closing: nothing anywhere in this codebase distinguished a retryable failure from a permission denial.** `apps/worker/src/task-dispatcher.ts`'s catch block unconditionally passed `retryable: true` to `queue.fail()` for every thrown error, regardless of type — §24 Retry Rule 1 ("Retry only transient failures automatically") and Rule 2 ("Do not automatically retry permission denials") had no mechanism to be honoured by _any_ task handler in this codebase, not just release. Rather than rewriting the dispatcher's classification logic generically (out of this task's own scope), a minimal, opt-in signal was added: new `NonRetryableTaskError` (`packages/domain/src/errors.ts`) — a task handler that recognises its own failure as non-transient throws this instead of a plain `Error`; the dispatcher now checks `error instanceof NonRetryableTaskError` and passes `retryable: false` accordingly (`apps/worker/src/task-dispatcher.ts`). Every other task handler in this codebase (all of Sprints 1–6) is completely unaffected — it keeps throwing plain errors and keeps being retried up to the existing `MAX_TASK_ATTEMPTS = 3`, exactly as before.

**`ToolInvocation.status`'s own existing `REJECTED`/`FAILED` distinction maps directly onto Retry Rules 1/2, with no new concept needed.** `REJECTED` is explicitly documented (`invoke-tool.ts`) as "everything the Tool Gateway itself rejects" — Typed Validation, Project Scope, Policy, Capability Permission: permission-denial-shaped failures by construction. `FAILED` is "the provider adapter's own outcome" — a real infrastructure problem, plausibly transient. New `requireSucceeded()` helper (`run-release-task.ts`) throws `NonRetryableTaskError` for a `REJECTED` deploy/health-check invocation and a plain `Error` for a `FAILED` one — a policy-denied release is never retried; a genuine deploy/health-check infrastructure failure is retried up to the bound (Rule 3, "Bound agent retries" / Rule 7, "Escalate after the configured retry threshold" — both already provided by the existing, unmodified `MAX_TASK_ATTEMPTS` mechanism, not reinvented here).

**Rollback reuses the exact same deploy/health-check/evidence pipeline `runReleaseTask` already built, factored into a shared `performRelease()` helper** — a genuinely new capability or mechanism was avoided; rollback is release, just of an explicit prior revision instead of the latest one, so it goes through the identical Tool Gateway chain (the same policy/authorisation discipline §27's Risk Model requires for R3/R4 actions) and produces its own `RELEASE_EVIDENCE` artifact (`action: 'rollback'`). New `runReleaseRollbackTask` **requires `rollbackToRevision` explicitly in the task's own input — there is no "automatic" or "latest" fallback, by construction**: rollback is never triggered by this codebase itself (no failure path calls it), satisfying "rollback is itself a controlled external action requiring the same authorisation discipline as the original release, not an automatic recovery" as an architectural guarantee rather than a runtime check. Which authorised human/process actually supplies that input (a UI action, a follow-up API call, a manually-started run) is left to DEVOS-079/080, mirroring the same "topology is a later task's job" boundary DEVOS-076 already drew for `runReleaseTask` itself.

**"Every attempt (success or failure) is recorded"** was already true by construction before this task — `invokeTool` writes a `tool_invocations` row and an audit record for every outcome (`SUCCEEDED`/`REJECTED`/`FAILED`), and both `runReleaseTask` and `runReleaseRollbackTask` go through it for both the deploy and health-check steps; nothing new was needed here. **"No path loops indefinitely"** holds because rollback is never automatically triggered (no failure handler calls it) and every retryable failure is still bounded by the pre-existing, unmodified `MAX_TASK_ATTEMPTS` limit.

New unit tests: `packages/application/tests/run-release-task.test.ts` gained 4 cases (a policy-denied deploy throws `NonRetryableTaskError` specifically, not a plain `Error`; a genuine adapter failure throws a plain `Error`, not `NonRetryableTaskError`; an authorised rollback with an explicit revision deploys it and publishes its own `action: 'rollback'` evidence; a rollback with no explicit `rollbackToRevision` throws — proving rollback can never happen silently), bringing that file to 8 cases. `apps/worker/tests/task-dispatcher.test.ts` gained 1 case (a handler throwing `NonRetryableTaskError` is recorded with `retryable: false` and fails immediately, not retried).

## DEVOS-079 — Full Software Change Workflow

**The topology question this task owned, resolved concretely**: release execution (DEVOS-076's `runReleaseTask`) and closure (DEVOS-078's `closeWorkItem`) are wired as **two nodes in a new `release-path` version 2** (`release` → `closure`, both `TOOL_TASK`), started as a genuinely separate run from `release-path` v1 (the readiness-check + approval gate, DEVOS-073) — not a fifth node bolted onto v1, and not folded into v1's own definition. This is the same reasoning applied a fourth time this sprint (after DEVOS-061 for planning→development, DEVOS-067 for the rework loop, DEVOS-073 for release-approval itself): the engine only advances a gate once every task in _that run_ succeeds and has no mechanism to insert a task into an already-running run, so anything that must happen _after_ a human decision still needs its own run. v2 carries **no `policies` marker of its own** — it isn't itself gated, because it exists to run only after a v1 run's release approval was already `APPROVED`; nothing in this codebase automatically starts v2 on approval (mirroring the existing precedent that approving a planning gate doesn't auto-start `development-path` either — the caller/orchestration decides when, exactly as DEVOS-061 already established and this task deliberately did not change). New `SEED_RELEASE_PATH_WORKFLOW_V2_VERSION_ID`/`_V2_GRAPH` (`packages/database/src/seed-constants.ts`, id `...0022`), inserted as workflow version 2 of the same `release-path` `WorkflowDefinition` DEVOS-073 created (`packages/database/src/seed.ts`) — v1 untouched, per Workflow Principle 8.

**`release` and `closure` sit in one run, not two, because no gate separates them** — the same reasoning DEVOS-067 already applied to development→validation→review. New `runClosureTask` (`packages/application/src/tasks/run-closure-task.ts`) is a thin wrapper: it resolves `task.workflowRunId` → `workItemId` (the one thing a task handler needs that the `closeWorkItem` use case doesn't provide on its own) and calls `closeWorkItem` directly — no separate logic duplicated. **`routeToolTask` (DEVOS-073's own router) gained two more cases** (`'release'` → `runReleaseTask`, `'closure'` → `runClosureTask`), now handling four deterministic handlers behind the one `TOOL_TASK` node type — mirroring `routeAgentTask`'s identical pattern. `apps/worker/src/main.ts`'s `agentTaskDeps` gained `approvals`/`closeWorkItem` (its type annotation widened to include `ClosureUseCaseDeps`, a purely structural addition — every other field `runReleaseTask`/`runClosureTask` need was already present from DEVOS-074–078's own wiring).
