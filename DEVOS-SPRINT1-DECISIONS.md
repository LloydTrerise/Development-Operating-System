## DEVOS-011 — Projects & Memberships

1. **Introducing `packages/domain` and `packages/application` now.** Through DEVOS-010, business logic lived directly in `apps/api`. From here on we're dealing with multiple entities, cross-cutting authorization, and (soon) a workflow engine — `specs/architecture/repository-code-structure.md` prescribes this separation (`domain` = entities/rules/ports, `application` = use-case orchestration) and continuing to stuff it into `apps/api` would violate "controllers must not contain domain logic." Repository ports live in `packages/domain` (matches the dependency table: `database` may import "domain persistence ports"); concrete Postgres implementations stay in `packages/database`.
2. **Role catalogue: `OWNER` | `MEMBER`.** `specs/architecture/domain-model.md:190` explicitly says "the exact role catalogue is not defined by this document." Minimal two-role model: OWNER can manage membership and project settings; MEMBER can do content mutations (work items, workflows, runs — added in later tasks) but not manage membership or delete the project.
3. **Single-organisation model for Sprint 1.** The API contract's `POST /api/v1/projects` has no organisation in the path or body, and there's no organisation-creation endpoint anywhere in the spec. Sprint 1 seeds exactly one organisation; all projects are created under it. Multi-organisation isolation isn't exercised until a task actually needs it.
4. **No `users` table exists in the DB schema** (`poc-database-schema.md`'s table list has no `users` — only `memberships.principal_id`, a plain external identity string). The API contract's `Membership.userId` and our `memberships.principal_id` are treated as the same concept — there's no separate user profile to look up in Sprint 1, consistent with DEVOS-010's `Principal = {id: string}`.
5. **Seed data: one org, one project, one membership** for a fixed seed principal id (`seed-user`), role `OWNER`. Seeding is idempotent (upsert on natural key) so re-running it is safe.
6. **Non-member access to a project returns 404, not 403.** Avoids confirming a project's existence to non-members. Not spec-mandated; a common, low-risk default.
7. **Cannot remove the last OWNER of a project** (a small safety check to avoid orphaning a project with no one able to manage it) — not spec-mandated, but a direct, obvious consequence of the OWNER-manages-membership rule.

## DEVOS-012 — Work Items

1. **`@devos/contracts`' already-established `WorkItem`/`CreateWorkItemRequest` shapes (source, metadata) win over the raw DB column names (source_system, source_url, type, priority, no metadata column).** These contracts were verified/fixed during today's earlier DEVOS-003 follow-up and reflect the API contract spec's resource examples directly; the DB schema spec's table is a looser sketch by comparison (no `metadata` column, and separate `source_system`/`source_url` instead of one `source` field). Reconciling: `source` maps to `source_system` (`source_url` stays unused/null for Sprint 1); a new additive migration (`0013`) adds the missing `metadata jsonb` column rather than dropping the field.
2. **`type` and `priority` are DB NOT NULL but absent from the established `CreateWorkItemRequest` contract.** Neither has a defined enumeration anywhere (DB spec: "Feature/bug/refactor/etc." — non-exhaustive). Rather than alter the already-shipped column constraints, the application layer defaults `type: 'GENERAL'`, `priority: 'MEDIUM'` when the caller doesn't supply them — same "don't invent an enum the spec doesn't define" treatment already applied to `WorkItemStatus`.
3. **Any project member (OWNER or MEMBER) can create/read/update work items** — work items are content, not project administration, matching DEVOS-011's OWNER-administers/MEMBER-does-content-mutations split.
4. **Acknowledged gap: multi-row writes aren't wrapped in DB transactions yet** (e.g. DEVOS-011's create-project-then-membership, DEVOS-012's inserts). `specs/database/poc-database-schema.md` §22 calls for transactional boundaries around related writes; doing this properly means repository methods accepting a shared `QueryExecutor` (the `withTransaction` foundation from DEVOS-008) instead of a hardcoded `Kysely<Database>`, which is a real refactor across every repository. Flagging rather than silently skipping — worth a dedicated pass, most naturally during DEVOS-024's hardening task where restart/duplicate-delivery/isolation get tested anyway. From DEVOS-013 onward, genuinely atomic multi-row creates (e.g. workflow definition + its first version) will use `withTransaction` where the effort is low; the rest stays on the list.

## DEVOS-013 — Workflow Definitions

1. **`PATCH /api/v1/workflows/{workflowId}` updates the current DRAFT version's JSON graph**, not just the definition's name/description — confirmed by the full endpoint table (`specs/api/poc-api-contracts.md` §12): "Create draft" (POST) / "Update draft" (PATCH) / "Validate draft" / "Publish version" all operate on a single implicit current-draft-version concept per definition. `POST .../workflows` creates the definition and its version 1 (DRAFT) together, wrapped in `withTransaction`.
2. **No new-draft-after-publish endpoint exists in the API contract**, so editing a workflow after its version is published isn't supported yet — attempting `PATCH` on an already-published definition returns 400. Sprint 1 only needs one published version (the seeded intake-to-artifact workflow) to run against; iterative re-drafting isn't exercised.
3. **`GET /api/v1/workflows/{workflowId}/diff` (compare versions) is deferred** — not specified beyond its name/purpose, and nothing in Sprint 1's vertical slice (DEVOS-014/016) needs it. Every other row in the Workflow Definition API table (§12) is implemented.
4. **Workflow graph validation is structural, not a full JSON-schema library**: name present, at least one node, each node has an `id` and a `type` from the already-established `workflowNodeTypes` enum, edges is an array. Matches the repo's consistent "minimal, explicit, no premature framework" pattern.
5. **Reusing `@devos/contracts`' already-fixed `WorkflowVersionStatus`** (`DRAFT, VALIDATING, PUBLISHED, DEPRECATED, ARCHIVED`, resolved during the DEVOS-003 follow-up against the spec) rather than inventing a new draft/published enum.
6. **Seeded "intake-to-artifact" workflow**: one definition (key `intake-to-artifact`) with a single published version containing one `TASK` node (id `discovery`) — deliberately minimal, matching Sprint 1's deterministic-stub scope (DEVOS-016). Exported as new seed constants for DEVOS-014/016 to reference.
7. **Repositories generalized to accept `QueryExecutor`** (the pool or an active transaction) instead of a hardcoded `Kysely<Database>` — needed to wrap the definition+version create in `withTransaction`. Applied retroactively to the DEVOS-011/012 repositories too (organisations/projects/memberships/work-items) since it's a compatible, low-risk widening (no behavior change when not inside a transaction). Doesn't retrofit transactions into DEVOS-011/012's own multi-row writes — that's still the acknowledged gap in decision 4 above; this just makes fixing it later mechanical.

## DEVOS-014 — Workflow Runs & Tasks

1. **Scoped to the minimal read from the task text**: "Run references an immutable workflow version." Implemented: start a run (from a definition's active/published version, or an exact version), persist the run + its tasks (one per graph node) transactionally, get a run, list a run's tasks. **Deferred, not built**: pause/resume/cancel/retry (`specs/api/poc-api-contracts.md` §16) and run events/timeline — nothing in Sprint 1's deterministic, synchronous vertical slice (DEVOS-016/021) exercises interactive run control; those read as later-sprint concerns once real async agent execution exists. Flagging as an explicit deferral, not a silent drop.
2. **New additive migration (`0014`) adds `workflow_runs.idempotency_key`** (nullable, `UNIQUE (workflow_version_id, idempotency_key)`) — the already-established `StartWorkflowRunRequest` contract requires `idempotencyKey`, and `specs/database/poc-database-schema.md` §23 explicitly calls out workflow-start idempotency, but no column existed for it in the DEVOS-009 migration set. Same additive-migration pattern as DEVOS-012's `work_items.metadata`.
3. **Starting a run creates one `workflow_tasks` row per graph node**, `task_key` = node id, `status: PENDING`, `attempt: 0`, empty `input` — task input binding from the run's own input is explicitly out of scope here (that's DEVOS-016's "deterministic task stub" territory, which is the first thing that actually needs to read task input).
4. **"Active version" = the definition's latest `PUBLISHED` version.** Starting a run against a definition with no published version, or an explicit version that isn't `PUBLISHED`, is a validation error — matches "immutable published versions" being the only thing a run may reference.
5. **Run/task creation wrapped in `withTransaction`**, matching `specs/database/poc-database-schema.md` §22's explicit "Start workflow: Create Run + Create Initial Tasks (+ Create Outbox Event)" transaction boundary — the outbox-event part is DEVOS-018's job and left out for now, consistent with the sequential build.

## DEVOS-015 — Queue & Worker Dispatch

1. **`workflow_tasks` itself is the durable queue** — claimed via `SELECT ... FOR UPDATE SKIP LOCKED` inside a transaction (a standard Postgres-as-queue pattern), not a separate queue table or external broker. This is what "durable queue... Application code depends on a replaceable queue port" most directly supports: no queue tech was ever chosen (flagged back in DEVOS-006), and workflow tasks already persist with a `status` column that models exactly the states a queue needs.
2. **New port `TaskQueue` (`claimNext`/`complete`/`fail`) lives in `@devos/domain`, separate from DEVOS-006's generic `Queue`/`QueueJob` port.** They solve different problems: DEVOS-006's port is a generic enqueue/dequeue demo (still valid, still tested, left untouched) with no completion/retry tracking; workflow task dispatch needs claim-with-lock, completion with output, and retryable-failure semantics the generic port never had. Forcing one shape onto both would have meant bolting `complete`/`fail` onto a port that has no real "enqueue" use case for this adapter (workflow tasks are created by DEVOS-014's start-run flow directly in Postgres, not enqueued through a queue API) — genuinely a different concept, not just a naming variation.
3. **`apps/worker/src/main.ts` is rewritten to dispatch real workflow tasks** instead of DEVOS-006's `demo.echo` bootstrap job — the demo's job was proving the worker mechanism exists at all (its own acceptance criterion), and now there's something real to dispatch. `queue.ts`/`handlers.ts`/`worker.ts` (the DEVOS-006 primitives) and their tests are left completely untouched, still passing, still valid demonstrations of the pattern — only the entry point's wiring changed.
4. **No task handler is registered in `main.ts` yet.** DEVOS-016 ("Deterministic Task Stub") is the very next task and owns the actual `TASK`-type handler logic; registering it here would be scope creep. Verified instead that dispatch is _safe_ without one: claiming a task with no registered handler fails it gracefully (`DEVOS_NO_HANDLER`-style message, non-retryable) rather than crashing the dispatcher.
5. **`MAX_TASK_ATTEMPTS = 3`** — no spec value exists for this. A retryable failure gets re-queued (back to `PENDING`) until the attempt count reaches this ceiling, then terminally `FAILED`. Reasonable, unremarkable default; easy to change later if a real retry-policy spec shows up (§23's "Idempotency" section calls for _a_ retry strategy, not a specific number).
6. **Known minor imprecision, not fixed**: `TaskDispatcher.processNext()`'s return value always reports `outcome: 'retrying'` when a handler throws, even on the exhausting attempt where the task actually goes terminal (`FAILED`) in the database. Verified live against real Postgres that the DB state itself is always correct (attempt count, terminal status, error message) — this only affects the dispatcher's own return-value precision, which nothing currently consumes for decision-making. Would need `TaskQueue.fail()` to report back whether it retried or terminated; not worth the port change for an in-memory-only cosmetic gap.

## DEVOS-016 — Deterministic Task Stub

1. **Minimal artifact persistence built now, ahead of DEVOS-017 ("Artifact Service").** DEVOS-016's acceptance explicitly requires "publishes artifact," and its dependencies are only DEVOS-014/015 (not 017) — so a bare-bones `Artifact`/`ArtifactVersion` repository pair is added now; DEVOS-017 is where the _real_ artifact service (proper storage abstraction, retrieval API) gets built on top. Same "earlier task does the minimum, later task does the enrichment" pattern as DEVOS-011→017 or DEVOS-013→(future workflow polish).
2. **No object storage exists yet** (that's explicitly DEVOS-017's "storage abstraction" scope), so artifact content is stored inline in `artifact_versions.metadata` (already a JSONB column) rather than referenced externally. `content_hash` is a real SHA-256 of that content (Node's `crypto.createHash`) — not a placeholder — so DEVOS-017 inherits a correct hash when it adds real external storage. `content_uri` is a synthetic `inline://artifact-versions/{id}` locator, clearly not a real storage URL.
3. **Artifact `status: 'GENERATED'`** — reuses the already-provisional `ArtifactStatus` enum from `@devos/contracts` (flagged during the DEVOS-003 follow-up as having no spec-defined enumeration) rather than inventing a separate one.
4. **Artifact type `DISCOVERY_REPORT`** — directly named in both the task text and `specs/api/poc-api-contracts.md` §26's Artifact Types table ("Discovery" stage), so this one _is_ spec-grounded, unlike the provisional status enum.
5. **The handler is a plain use case function (`runDiscoveryTask`) in `@devos/application`, registered into the worker's dispatcher for task type `TASK`** — matches "replaceable by an agent handler": swapping in real agent execution later is a one-line change in `apps/worker/src/main.ts` (`registerHandler('TASK', ...)` → a different function), nothing about the dispatcher, queue, or task machinery needs to change.
6. **Content is a deterministic, templated summary** (work item title/description + static discovery narrative + timestamp) — explicitly "without an LLM" per the task text, so no model call, no randomness beyond the timestamp.

## DEVOS-017 — Artifact Service

1. **New `packages/storage` package for the `ArtifactStorage` port + a local-filesystem adapter.** DEVOS-016 stored content inline in `artifact_versions.metadata` as an explicit placeholder for this task. No object-storage technology was ever chosen (nothing wires S3/MinIO/etc. anywhere in the repo), so — same reasoning as every other undecided-infra call this session (queue tech, DB client) — the minimal, dependency-free, real implementation is a local filesystem adapter, content-addressed by SHA-256 hash under `./data/artifacts/` (already covered by the existing `.gitignore`'s `data/` entry, which suggests this was anticipated). Swappable later for a real object-storage adapter behind the same port without touching callers.
2. **Hash computation moves into the storage adapter** (`put()` returns `{uri, hash}`), not the caller — single source of truth, avoids the caller and storage layer computing potentially-divergent hashes. `run-discovery-task.ts` (DEVOS-016) is updated to use it instead of computing its own inline hash+URI.
3. **Storage location is a plain constructor argument, not new `@devos/config` fields.** `@devos/config`'s existing `StorageConfig` (`endpoint`/`bucket`/`region`) is clearly shaped for a future real object-storage backend — reusing it for a local-filesystem placeholder would conflate two different concerns. `apps/worker` passes `process.env.ARTIFACT_STORAGE_DIR ?? './data/artifacts'` directly instead.
4. **Retrieval API added**: `GET /api/v1/projects/{projectId}/artifacts`, `POST .../artifacts` (spec-complete even though Sprint 1's only real creation path is the worker), `GET /api/v1/artifacts/{artifactId}`, `GET .../versions`, `GET .../versions/{version}`, `GET .../provenance` (workflowRunId/workflowTaskId — `agentExecutionId` omitted, no agent-execution tracking exists yet). Matches `specs/api/poc-api-contracts.md` §24's endpoint table.
5. **Immutability is structural, not enforced by a check**: `ArtifactVersionRepository` has never had an update method (since DEVOS-016), so there's nothing to guard against — versions are immutable by construction, same as published workflow versions.

## DEVOS-018 — Events & Outbox

1. **`outbox_events`'s `payload` JSONB column holds the full serialized `EventEnvelope`** (already defined in `@devos/contracts`, including its `correlationId`/`version`/`causationId` fields) rather than adding migrations for each envelope field as its own column. The outbox row's own columns (`event_type`, `aggregate_type`, `aggregate_id`, `published_at`, `attempts`) serve the _outbox's_ operational needs (what's unpublished, retry tracking); the envelope is the _wire format_ once actually delivered. This needed zero new migrations, unlike DEVOS-012/014's additive-column gaps.
2. **No real message bus exists** (same unresolved-infra situation as the queue and object-storage decisions), so "publish" means marking `published_at` and handing the envelope to a pluggable sink function — for Sprint 1, a console-log sink. `publishPendingEvents()` is idempotent (re-running is safe — already-published rows are excluded by the `published_at IS NULL` filter) but is **not** wired into a continuously-running background loop; nothing in Sprint 1's synchronous vertical slice needs continuous publishing, and there's no real subscriber to publish _to_. It's callable on demand (and is how this task's live verification exercises it).
3. **Minimum events wired at their natural transaction boundaries**, extending existing transactional code rather than adding new orchestration: `WorkflowRunStarted` in the run+tasks creation transaction (DEVOS-014's `createWorkflowRunStarter`); `WorkflowTaskStarted` in the claim transaction; `WorkflowTaskCompleted`/`WorkflowTaskFailed` in `complete()`/`fail()` (DEVOS-015's task queue, now wrapped in `withTransaction` — previously single-statement, non-transactional); `ArtifactCreated` in the artifact-publish transaction (DEVOS-016/017).
4. **`complete()`/`fail()` now also own workflow-run completion tracking** — when a task succeeds, checks whether every task for that run has succeeded and if so transitions `workflow_runs.status` to `COMPLETED` (emitting `WorkflowRunCompleted`); a terminal (non-retryable-exhausted) task failure transitions the run to `FAILED` (emitting `WorkflowRunFailed`). This didn't exist before — DEVOS-014 deliberately left `workflow_runs.status` static at `PENDING` — but `WorkflowRunCompleted`/`WorkflowRunFailed` events are meaningless without the run's own status actually reflecting completion, so implementing it here (not scope creep, a direct prerequisite of "minimum workflow events") closes that gap. Correct for any task count per run, not just Sprint 1's single-task graphs.
5. **`GET /api/v1/runs/{runId}/events` stays deferred**, consistent with the DEVOS-014 decision to defer run events/timeline endpoints — DEVOS-018's own scope is the write side (envelope, tables, transactional write, publisher), not the read API. Verified the write side directly against Postgres instead.

## DEVOS-019 — Audit

1. **Audit writes happen at the application-use-case layer, not inside the low-level database transactional helpers** — unlike DEVOS-018's events. The reason: `actorId` (who did this) is only known where the principal is — the use case (`startRunForVersion`, `createArtifact`) — not inside `packages/database`'s generic transaction helpers, which never receive a principal. `StartWorkflowRun`/`PublishArtifact`'s signatures gain an explicit `actorId` parameter (both call sites already have it in scope) so the audit write can still happen inside the _same_ transaction as the state change, preserving DEVOS-018's transactional guarantee without threading a principal through code that shouldn't need to know about one.
2. **Worker-driven task events (claim/complete/fail) are always `actorType: 'SYSTEM'`, `actorId: 'devos-worker'`** — hardcoded, not parameterized, since the dispatcher genuinely has no user principal (it's polling and executing autonomously). The deterministic discovery handler's artifact-creation audit uses the existing `'devos-deterministic-stub'` constant (already used for `createdBy` since DEVOS-016) as its actor.
3. **No dedicated Audit API section exists in `specs/api/poc-api-contracts.md`** (unlike artifacts/workflows, which had explicit endpoint tables) — added a minimal `GET /api/v1/projects/{projectId}/audit` anyway since it's cheap, and DEVOS-020 (Basic Run UI)/DEVOS-021 (E2E slice) will want _some_ way to observe audit history without going through `psql` directly.
4. **`outcome` is `'SUCCESS' | 'FAILURE'`** (not reusing any existing status enum, since none of them fit an audit outcome) and `correlationId` is copied from the corresponding outbox event's envelope where one exists, giving a traceable link between an audit record and its event without a foreign key (outbox events aren't guaranteed to survive/stay queryable forever once genuinely published to an external system later).
5. **`PublishArtifact`'s signature was left unchanged** (unlike `StartWorkflowRun`) — `artifact.createdBy` already carries the correct actor identity (the principal for API-created artifacts, `'devos-deterministic-stub'` for the discovery handler), so no extra parameter was needed; `actorType` is derived from whether `createdBy` equals the stub constant.
6. **Not every worker-emitted outbox event gets a matching audit record** — `WorkflowTaskStarted` (fired on every claim, including retries) is deliberately left un-audited to keep `audit_records` reserved for materially significant state transitions (task/run completion and failure, artifact creation, run start) rather than every polling/claim event. The outbox event stream remains the source of truth for that finer-grained activity.
7. **The new `GET /api/v1/projects/{projectId}/audit` endpoint has no query-string filtering** (no `?limit=`, no action/actor filters) — the router (`apps/api/src/http/router.ts`) has no query-string parsing at all yet, and adding it purely for this one endpoint felt like scope creep for a "minimal" addition; it returns the repository's default of the 100 most recent records for the project, newest first.
8. **Live-verified end-to-end against real Postgres**: started a workflow run as `seed-user` (produced `workflow_run.started`, USER), ran the worker to completion (produced `artifact.created` as SYSTEM/`devos-deterministic-stub`, `workflow_task.completed` as SYSTEM/`devos-worker`, `workflow_run.completed` as SYSTEM/`devos-worker`), and confirmed all four records via the new audit endpoint with correct actor types, correlation IDs, and org/project scoping. The failure/retry-exhaustion path was not re-verified live for this task (the `fail`/`failRun` audit-write code is structurally identical to the already-verified `complete`/`maybeCompleteRun` path, and the underlying retry/failure state machine itself was already live-verified end-to-end in DEVOS-018).

## DEVOS-020 — Basic Run UI

1. **No login UI — every web-app request authenticates as a fixed dev principal (`seed-user` by default, `DEV_PRINCIPAL_ID` in `apps/web/src/api-client.ts`, overridable via `VITE_DEV_PRINCIPAL_ID`).** Real OIDC/session auth isn't in Sprint 1 scope and DEVOS-010's local dev auth provider treats the bearer token as the principal id directly with no credential check, so this exactly mirrors how the API itself already behaves — it just moves the fixed token from curl's `-H` flag into the fetch client. `session.tsx` was updated from a fake `'anonymous'` placeholder to reflect this real (if fixed) identity, and the header now shows `Session: dev-identity (seed-user)` so the limitation is visible in the UI, not hidden.
2. **A `ProjectProvider` React context (`apps/web/src/project-context.tsx`) is the "project selector"** — it fetches `GET /api/v1/projects` once, holds the selected project id, and is shared by every page via a `<select>` in the app header (`App.tsx`). Work Items and Runs pages read `selectedProjectId` from context rather than each managing their own project picker, so switching projects in the header immediately re-scopes both pages.
3. **Runs are tracked client-side only, not loaded from a "list runs for project" endpoint — because no such endpoint exists.** DEVOS-014 explicitly deferred a runs-list/timeline API (`DEVOS-BUILD-STATE.md` DEVOS-014 entry: "Pause/resume/cancel/retry/events/timeline explicitly deferred"). The Runs page therefore shows only runs started in the current browser session (`useState<WorkflowRun[]>`), not full project history. This is a real, disclosed gap, not an oversight — closing it would mean inventing a new backend endpoint outside DEVOS-020's stated scope.
4. **Status/timeline via polling** (`POLL_INTERVAL_MS = 2000`), exactly as the task's acceptance criterion permits ("Polling is permitted; realtime is deferred"). Each started run polls `GET /runs/:id` and `GET /runs/:id/tasks` every 2s until the run reaches a terminal status (`COMPLETED`/`FAILED`/`CANCELLED`), then stops. The task list doubles as the "timeline" (ordered list of node/type/status/attempt/error) since no separate timeline/events API exists (also deferred by DEVOS-014).
5. **Artifacts are shown per-run by client-side filtering, not a per-run API.** `GET /api/v1/projects/{projectId}/artifacts` returns all of a project's artifacts; each already carries `provenance.workflowRunId`, so the Runs page fetches the project's artifact list once and each run card filters to its own `workflowRunId`. The list is explicitly refreshed when a run's poll first observes a terminal status (`onCompleted` callback), since the initial page-load fetch predates any run this session created.
6. **"Start a run" always uses the active-version endpoint** (`POST /workflows/{workflowId}/runs`, resolves the current published version server-side) rather than fetching each workflow's versions to pre-filter to only-published workflows. If a workflow has no published version, the API's existing `ValidationError` ("Only a published workflow version can be run") surfaces directly in the form's error area — satisfying the "errors" scope item without an extra round of N+1 version-list calls per workflow shown in the dropdown.
7. **No component-level UI tests** — `apps/web` has no `@testing-library/react` (or any DOM-assertion test utility) installed, and adding one wasn't judged in scope for a task about wiring existing APIs into pages. Verification for this task is: full typecheck/lint/test/build passing (`pnpm turbo run typecheck test lint build`, 76/76), new unit tests for the `api-client.ts` additions (auth header, network-error handling, request-body shape), a clean production `vite build`, and — same limitation as DEVOS-007 — no actual browser available to this agent, so **visual rendering was not confirmed**. As a partial substitute, both dev servers (API + web) were started together and every new/changed source file was curled through the Vite dev server (all returned 200, meaning no server-side transform/syntax error), which rules out broken imports and syntax errors but not runtime/React errors. This should be manually verified in an actual browser before relying on it.

## DEVOS-021 — End-to-End Vertical Slice

1. **New workspace package `@devos/e2e-tests` at `tests/e2e/`** — the repository already had an empty `tests/e2e/.gitkeep` placeholder from DEVOS-001's bootstrap (`README.md`: "`/tests` — Cross-package and end-to-end tests"), but `pnpm-workspace.yaml` never actually included `tests/*` as a workspace glob, so it wasn't a real package. Added `tests/*` to the workspace globs and gave the new package `typecheck`/`lint`/`test` scripts (no `build` — nothing depends on this package, so there's no library output to emit); `turbo run typecheck test lint build` picks it up automatically.
2. **The test drives the system purely through its public HTTP API — no importing of `apps/api`'s or `apps/worker`'s internals.** `apps/api`/`apps/worker` have no `main`/`exports` field in `package.json` (they're deployables, not libraries), so there was no natural "call `createApp()` in-process" path anyway — but even if there were, driving the real system exactly the way a real client would (real HTTP, real process boundary, real worker polling loop) is a strictly stronger proof of "the entire Sprint 1 control loop passes" than exercising internals directly.
3. **The test spawns its own API and worker processes rather than assuming they're already running**, so `pnpm --filter @devos/e2e-tests test` is a genuinely self-contained, automatable proof (the only external precondition is a reachable Postgres — this test does not start Postgres itself, matching every other live-verification step done throughout Sprint 1). The API listens on port 3901 (not 3000) specifically so this test doesn't collide with a developer's already-running `pnpm dev` instance.
4. **Processes are spawned as `node <resolved tsx/cli path> src/main.ts` directly, not via `pnpm --filter ... run dev` or `pnpm exec tsx`.** First attempt used `spawnSync('pnpm.cmd', ...)`/`spawn('pnpm.cmd', ...)` and hit a real bug: Windows' `child_process.spawn(Sync)` throws `EINVAL` on `.cmd`/`.bat` targets unless `shell: true` is passed — a known Node-on-Windows quirk. Fixing it with `shell: true` worked for the synchronous one-shot migration call, but for the _long-running_ API/worker processes it would wrap each in a `cmd.exe` shell process that `child.kill()` does not reliably tear down — exactly the class of zombie `tsx watch` process this repository has hit repeatedly during manual verification this session (see `packages/database`/worker dev-server cleanup notes elsewhere in this log). Resolving `tsx/cli`'s real path via `import.meta.resolve('tsx/cli')` and spawning it with `node` directly sidesteps the shell entirely — the child is directly killable and cross-platform. Confirmed via `Get-CimInstance Win32_Process` that no process survives after the test run (both a standalone run and a full `turbo run` were checked).
5. **The workflow used by this test is a freshly-created definition (`key: e2e-...`, unique per run), not the seeded `intake-to-artifact` workflow** — proves the full "create → publish → run" lifecycle from scratch rather than depending on `pnpm --filter @devos/database seed` having been run, making the test's project/work-item/workflow/run all self-contained and disposable (unique slug/key per run via `Date.now()`, so repeated runs never collide).
6. **Single `it()`, not one-assertion-per-step.** The task's acceptance criterion is "Entire Sprint 1 control loop passes" (singular) — splitting into many small tests would create false independence (a later step's fixture setup for its own isolated test would just re-run everything before it anyway) and would obscure the point: this is one proof of one connected chain, and its natural unit of pass/fail is the whole chain.

## DEVOS-024 — Sprint Hardening & Demo

1. **The one critical (P0) fix implemented: stale-task reclaim for restart safety.** Auditing the worker/queue design for the "restart" item in this task's explicit scope surfaced a real gap that had existed since DEVOS-015: `claimNext()` only ever selects `PENDING` tasks — a task a worker claimed (moved to `RUNNING`) and then never finished, because the process crashed or was killed, stayed `RUNNING` forever with no recovery path. Fixed by adding `reclaimStale(staleThresholdMs)` to the `TaskQueue` port (`@devos/domain`) and its Postgres implementation: any `RUNNING` task whose `started_at` is older than the threshold is put through the exact same terminal-vs-retry accounting as an ordinary `fail()` call (extracted into a shared `resolveTaskFailure()` helper in `packages/database/src/repositories/task-queue.ts` so `fail()` and `reclaimStale()` can't drift apart) — reset to `PENDING` if attempts remain, else `FAILED` with the same audit/outbox-event shape. `apps/worker/src/task-dispatcher.ts` calls it once immediately on `start()` (the scenario this exists for — a replacement worker booting up — shouldn't wait a full interval) and then every `reclaimIntervalMs` (default 60s) inside its existing poll loop, with a default `staleThresholdMs` of 5 minutes.
2. **This fix is explicitly disclosed as a simplification, not a complete solution — see `docs/LIMITATIONS.md`.** Time-based polling reclaim (no real heartbeat/lease renewal) can't distinguish "the worker died" from "the worker is alive but genuinely still working on a slow task" — a task that legitimately runs past the threshold would be incorrectly reclaimed and could be double-processed by a second worker. Sprint 1's only task type (the deterministic discovery stub) completes in well under a second, so this risk is theoretical today, not observed — but it's real, and a proper fix (heartbeat renewal extending a lease, reclaim only on lease expiry) would be needed before task handlers run for minutes rather than milliseconds. Flagging this clearly rather than presenting the simple polling version as a finished solution.
3. **Two new hardening proofs added to `@devos/e2e-tests`, in a new `hardening.test.ts`, deliberately NOT reusing `vertical-slice.test.ts`'s HTTP-black-box approach** — there is no HTTP endpoint for "claim a task" (that only happens inside the worker process), so proving "duplicate delivery never happens" (concurrent `claimNext()` calls via `SELECT ... FOR UPDATE SKIP LOCKED` must never hand the same task to two callers) and "restart safety" (the new `reclaimStale()`) genuinely requires calling `@devos/database`'s `createPostgresTaskQueue` directly against real Postgres, bypassing both the HTTP layer and the application layer's auth/membership resolution (already covered by their own unit tests, and not what's under test here). This new file composes `@devos/database`'s repositories directly to build minimal project/work-item/workflow/run fixtures — legitimate at this layer (top-level integration tests are allowed to depend on anything), and it now needs `@devos/database`/`@devos/domain` as devDependencies of `@devos/e2e-tests` alongside the `@devos/api`/`@devos/worker` build-ordering ones from DEVOS-021.
4. **Found and fixed real test-isolation bugs while getting these new tests to pass reliably** — not the queue logic, but the tests' own assumptions: (a) `claimNext()`/`reclaimStale()` are deliberately _global_, not scoped to a run or project (matching production — a worker drains the whole system's queue), so a test creating a 2-task run and expecting a specific task back after a reclaim can get its sibling task instead if both share the same `created_at` millisecond; fixed by using single-node workflows in the reclaim tests, and by asserting "no id repeats across concurrent claims" (a global-queue-safe property) rather than "the queue holds exactly N tasks" in the duplicate-delivery test. (b) Vitest runs test _files_ concurrently by default; `hardening.test.ts` and `vertical-slice.test.ts` both drive the same live, shared Postgres task queue, so running them in parallel let one file's claims steal the other's tasks. Fixed with a package-local `tests/e2e/vitest.config.ts` (`fileParallelism: false`) rather than touching the shared root `vitest.config.ts` used by every other package (most of which have no such cross-file shared-state concern). (c) Every test that claims a task now explicitly drives it to a terminal state before finishing, specifically so a failed/incomplete test run doesn't leave `RUNNING`/`PENDING` debris in the shared database that corrupts a _later_ test's `claimNext()` ordering — this was diagnosed by literally hitting it: an earlier, not-yet-fully-fixed version of this test file left debris from failed assertions, and a subsequent run's `claimNext()` picked up that older leftover task instead of the current test's own (`ORDER BY created_at ASC` prefers whatever's oldest, and the debris was, by construction, older). A completely fresh Postgres — the real CI environment — would never carry this cross-run debris; it only bit during local iteration on this repository's long-lived dev database.
5. **Real bug found and fixed via the "clean-environment demo" check**: `pnpm dev` crashed immediately (`ConfigValidationError: DATABASE_URL is required`) _even with `DATABASE_URL` exported_, because Turborepo 2.x defaults to strict environment-variable filtering — a task only receives an env var if it's declared in `turbo.json`'s `globalEnv` (or the task's own `env`), and nothing had ever declared `DATABASE_URL`. This had never surfaced earlier in the session because every prior verification either called `apps/api`/`apps/worker` directly (`node`/`tsx`, bypassing turbo) or ran via `pnpm --filter @devos/api dev` — **`pnpm dev`, the actual top-level documented command, had never once been exercised end-to-end until this explicit demo pass.** Fixed by adding `globalEnv: ["DATABASE_URL", "PORT", "ARTIFACT_STORAGE_DIR", "VITE_API_BASE_URL", "VITE_DEV_PRINCIPAL_ID"]` to `turbo.json`. Documented in `docs/DEVELOPMENT.md`'s troubleshooting section, since it will bite again the moment a new env var is needed by any `dev`/`test` task without a matching `globalEnv` update.
6. **New `docs/LIMITATIONS.md`** — the task's third explicit scope item ("limitations"), linked from `README.md`. Covers identity/access, workflow lifecycle, task execution (including the reclaim caveat from decision 2), storage/events/audit, infrastructure (container images, no observability/policy stack, CI branch-protection gap), and testing gaps — one browsable document pointing back at `DEVOS-SPRINT1-DECISIONS.md` for the full reasoning behind each item, rather than duplicating it.

The clean-environment demo pass (decision 5) exercised exactly this: `pnpm bootstrap` → `pnpm dev` → `pnpm smoke` → a full project→work-item→workflow→publish→run→artifact→audit cycle via curl against the freshly started dev servers, all passing.
