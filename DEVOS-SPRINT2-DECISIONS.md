## DEVOS-028 — Prompt/Version Management

1. **Prompts are files, not a database table.** `specs/architecture/repository-code-structure.md` §42 is explicit: "Agent prompts are implementation assets. They must be reviewed and versioned like code." That's a materially different model from Agent/AgentVersion (DEVOS-025) — those are genuinely dynamic, user-registered-through-the-API entities; a prompt is closer to source code. New `packages/agents/src/prompts/<role>/v<N>/system.md`, resolved by a `PromptRepository` port (`resolve(reference): Promise<string>`) with a `createFilesystemPromptRepository()` implementation. "Creating a new prompt version" means adding a file and committing it — the same workflow as any other source change — not a REST endpoint. No API surface was added for this task.
2. **Reference format is `<role>/v<N>`** (e.g. `requirements/v1`), validated against a strict pattern before touching the filesystem, mapping directly to `prompts/<role>/v<N>/system.md`. Chosen for direct correspondence to the directory layout and because `AgentVersion.promptReference` (already a free-form string since DEVOS-025) needed _some_ concrete convention; nothing in the specs mandates this exact shape.
3. **Prompt files are read from `src/`, never copied into `dist/`.** `tsc` doesn't copy non-`.ts` files, and treating prompts as "implementation assets... versioned like code" (decision 1) means they're source, not build output. `createFilesystemPromptRepository()`'s default path climbs two directories up from wherever the _currently executing_ module lives (`dist/prompts/` when built, `src/prompts/` when run via `tsx`/vitest) and back down into `src/prompts/` — verified working in both modes (ran the compiled `dist/index.js` directly, then vitest, both resolved the same real file).
4. **`AgentInvocationRequest` gained `systemInstructions?: string`, kept separate from `promptReference`.** `promptReference` stays on the request purely for traceability (which reference produced this call), while `systemInstructions` is the already-resolved text — a provider adapter shouldn't need to know how to resolve a reference, only how to use resolved text. `runAgentTask` (DEVOS-026) does the resolution via a new required `prompts: PromptRepository` dependency; `createGeminiModelAdapter` (DEVOS-027) now prepends `systemInstructions` to its constructed prompt when present, closing the exact gap DEVOS-027's own decision log flagged ("promptReference is not yet resolved into actual stored prompt text").
5. **A missing or malformed `promptReference` fails the task, not silently continues without it.** Consistent with every other guard clause in `runAgentTask` — a configured-but-broken reference is a real configuration error, not something to paper over.
6. **Found a pre-existing, unrelated repo convention while adding tests**: every package's `tsconfig.json` excludes `tests/` from the `typecheck` gate (`"exclude": ["tests"]`), so test files are transpiled by vitest but never actually type-checked by `pnpm typecheck` — a change to a shared `deps` interface (adding the new required `prompts` field) didn't surface as a typecheck failure in `run-agent-task.test.ts`, only as a would-be runtime failure once the tests actually ran. Not something to fix as part of this task (pre-existing, repo-wide, not a regression), but worth knowing: shared interface changes need their test fixtures updated by hand, not caught by `tsc`.
7. **Live-verified the full chain against real infrastructure**: real Postgres (project → work item → agent with `promptReference: 'example/v1'` → workflow → run → task) plus the real Gemini API, using the actual filesystem-resolved prompt text. The response showed the model genuinely following the prompt's instruction ("don't invent facts, use an uncertainty field instead") — it returned a real `uncertainty` entry noting the work item's description was empty, not a canned string. `apps/worker` doesn't depend on `@devos/agents` yet (not wired until DEVOS-035), so this verification temporarily added that dependency, ran the check, then reverted `apps/worker/package.json` and re-ran `pnpm install` to restore the lockfile — no permanent dependency added ahead of the task that's supposed to introduce it.

## DEVOS-029 — Agent Output Schemas

1. **Hand-rolled structural validation, not a JSON Schema library.** The task's own docx boilerplate ("Add or update ... database, event and artifact contracts") gives no format mandate, and this codebase already has exactly one precedent for validating a structured document — `validateWorkflowGraph` (`packages/domain/src/workflows/validation.ts`), a small hand-rolled function returning `{field, message}` issues, not a schema-library dependency. Sprint 2's actual near-term need (DEVOS-031–034's four agents each producing a handful of top-level fields) doesn't need full JSON Schema's `$ref`/`oneOf`/nested-keyword machinery. New minimal format: `{name, version, fields: {[field]: {type, required?}}}` — presence + primitive/array/object type only. `validateAgentOutput()` mirrors `validateWorkflowGraph`'s exact issue shape for consistency.
2. **Output schemas are files too, mirroring DEVOS-028's prompt-storage decision exactly** — `packages/agents/src/schemas/<name>/v<N>/output-schema.json`, resolved by a `SchemaRepository` port. Same rationale: an output contract is an implementation asset, reviewed and versioned like code, not dynamically user-edited through an API. Reference format is `<name>-v<N>` (e.g. `prd-v1`) rather than prompts' `<role>/v<N>` — chosen to match the literal example value already given in `specs/api/poc-api-contracts.md` §21's Agent Definition Contract (`"outputSchemaRef": "prd-v1"`), so the wire-format string an agent definition actually carries needed no reinterpretation, just a different internal file-path parse.
3. **A schema-violating output is recorded as a `FAILED` AgentExecution with a distinct `errorCode: 'DEVOS_SCHEMA_VALIDATION_FAILED'`** (separate from a provider/network failure's unset error code) and then thrown — reusing the exact same throw-based signal `runAgentTask` already uses for provider failures, so it's retried by the ordinary task-attempt mechanics (DEVOS-026), not specially non-retryable. A bad response shape is often transient (the model might format differently on a retry), so treating it identically to a provider hiccup was a deliberate, not accidental, choice.
4. **Live-verified against the real Gemini API with a real schema file**: an agent configured with `outputSchemaRef: 'example-v1'` (requires a `summary` string field) produced a genuinely conforming response from a live model call, validated, and persisted. The schema-_violation_ path itself was not re-proven live — its logic doesn't depend on whether the invocation came from a real or fake adapter (only on `invocation.result` failing `validateAgentOutput`, already covered by four dedicated unit tests including the exact `DEVOS_SCHEMA_VALIDATION_FAILED` path), so a second live call to unreliably coax a real model into non-conformance wouldn't have added meaningfully stronger proof.
