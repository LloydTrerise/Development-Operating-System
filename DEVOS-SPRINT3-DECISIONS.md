## Sprint-wide: activating `packages/knowledge` and `packages/policy`

`specs/architecture/repository-code-structure.md`'s "Applications vs Packages" table explicitly assigns `packages/knowledge` ("Context retrieval") and `packages/policy` ("Policy/authority") — unlike Sprint 1/2's domains (workflow, agent, artifact), which have no dedicated package and were built entirely inside `packages/domain`/`packages/application`/`packages/database`, matching every other sprint's pattern so far. Sprint 3 is the first sprint to populate these two previously-empty scaffold packages. Decision: keep the established division of labor — simple entity/repository-port definitions stay in `packages/domain/src/{knowledge,policy,approval}/` (consistent with every existing entity), straightforward CRUD/orchestration use cases stay in `packages/application/src/{knowledge,policy,approval}/` (consistent with every existing use case, and matching every task's own acceptance-criteria phrase "the capability works through its intended application/service boundary") — and `packages/knowledge`/`packages/policy` are reserved for the genuinely algorithmic logic the spec names those packages for: retrieval (DEVOS-040), context assembly (DEVOS-041), and policy evaluation (DEVOS-044). This avoids both re-implementing Sprint 1/2's proven CRUD pattern differently for no reason, and leaving the two purpose-built packages empty when their named responsibility (deterministic context assembly, deterministic policy evaluation) is exactly what those tasks need. `packages/domain` already has `approval/`/`policy/` listed as subfolders in the repo-structure spec (§11), confirming domain entities for these areas belong there.

## DEVOS-041 — Implement Context Builder

1. **Authority-level mapping (`packages/knowledge/src/context/authority.ts`) is an explicit implementation choice, not a spec table.** `specs/architecture/system-context-engineering-knowledge.md` §18 states its own precedence diagram is "a conceptual model rather than a universal ordering" and defers concrete per-type precedence to "a later technical specification" that does not exist anywhere in this repo. `KNOWLEDGE_SOURCE`/`PROJECT_CONTEXT` are mapped to level 2 ("Project Constitution/Standards"); `ARTIFACT` is deliberately placed at level 8 ("Generated/Proposed Information"), not level 4 ("Approved Architecture/Technical Design") — DevOS's planning artifacts today are schema-validated but not yet human-approved (DEVOS-047 introduces that gate later this sprint), so treating them as "approved" ahead of that gate would overstate their authority. An unrecognized type falls back to level 9 (lowest / "Transient Agent Reasoning"), a safe default rather than an error.
2. **Steps 9–10 of the Context Assembly pipeline ("Detect Conflicts", "Validate Context Sufficiency") are explicitly deferred, not half-built.** This sprint's own task backlog already lists "Uncertainty" as a separate task (DEVOS-048) — building a partial, ungrounded conflict/sufficiency check now (with no policy engine or real multi-source disagreement to test against yet) would risk fabricating behavior the spec has no concrete algorithm for. `buildContext()` implements steps 2–8 and 11 of §22 only: identify required context, retrieve project context/knowledge sources/run artifacts, apply precedence, and assemble — explicitly not conflict detection or sufficiency validation.
3. **Step 3 ("Identify Applicable Policies") is a no-op today.** No policy model exists yet (DEVOS-043/044 come later in this sprint); `buildContext()` does not fabricate a policy snapshot beyond what DEVOS-030 already established as a placeholder (`{ policyVersion: 'none' }`) for `runAgentTask`'s existing context manifest recording, which this task does not touch.
4. **Size limiting drops whole lowest-authority sources, never truncates a single source's content.** Given the pre-sorted (highest-authority-first) list, the first source is always kept regardless of size (so context is never silently empty when the highest-authority item alone exceeds the budget); subsequent sources are added only while the running total stays under `maxContentLength`. 5. **No integration into DEVOS-032–034's existing agent handlers, and no `WorkItem` retrieval added.** Consistent with DEVOS-040's decision #4: the existing planning-path agents already resolve their own upstream artifact/work-item content directly and are not touched. `buildContext()` is new infrastructure with its own tests and live verification; wiring it into the live agent-execution path (and, if ever needed, adding `WORK_ITEM` as a retrievable source type) is left for a future task if the product direction calls for it — not fabricated as already integrated.

## DEVOS-043 — Implement Policy Model

1. **One flat, self-versioned `policies` table — no separate "definition" parent table, unlike Agent/Workflow.** `specs/database/poc-database-schema.md` §12.1 defines a single `policies` table where `key`+`version` together identify a specific version; there is no second table analogous to `agents`/`agent_versions` or `workflow_definitions`/`workflow_versions`. `Policy` (`packages/domain/src/policy/policy.ts`) models the row directly — creating a new version means inserting a new row with the next `version` number for the same `(projectId, key)`, not creating a child row under a stable parent.
2. **A new `PolicyStatus` contract type, not reuse of `AgentVersionStatus`.** Both happen to be the identical three-value shape (`DRAFT`/`PUBLISHED`/`RETIRED`, per the schema's own "Draft/Published/Retired" wording for both tables) — but Policy and Agent are conceptually distinct domains that merely share a lifecycle shape by coincidence; reusing the Agent-named type would be a semantically wrong dependency.
3. **CRUD API is project-scoped only (`/projects/{projectId}/policies`); no organisation-wide (`projectId = null`) policy creation endpoint.** The schema's `project_id` column is nullable (an org-wide policy is representable), but no existing route anywhere in this codebase is organisation-scoped — every resource (including `Project` creation itself) is reached through a project-scoped path, with `organisationId` resolved internally from the project. Building a first-ever organisation-scoped route just for policies would be architecture drift beyond this task's own scope; the `Policy.projectId` field stays optional so an org-wide policy remains representable once/if that pattern is introduced.
4. **A second draft cannot be created while one is already pending for the same `(projectId, key)`.** Not explicitly required by the spec, but a natural consequence of "published policy versions are immutable" (§31) — without this guard, a caller could accumulate an unbounded pile of un-published drafts. A new draft (version N+1) may only be created once the latest existing version is `PUBLISHED` (or none exists yet).
5. **Live-verified against real Postgres**: migration `0020_policies` applied cleanly; the real API was exercised end-to-end — create v1 draft, reject a duplicate concurrent draft (400), publish, reject publishing again (400, immutability), create v2 draft only after v1 was published, list (both versions visible), and unauthenticated rejection (401). Dev process confirmed torn down. New unit tests (7 cases). Full forced (no-cache) `pnpm turbo run typecheck lint test build` at 79/79; `pnpm format:check` clean.

## DEVOS-044 — Implement Policy Evaluator

1. **A minimal, hand-rolled rule shape for `Policy.definition`** (`packages/policy/src/evaluator/policy-evaluation.ts`: `{ rules: [{action, effect, condition?}], defaultEffect? }`) — no evaluation algorithm or rule language is specified anywhere in the spec corpus (flagged explicitly in `specs/sprints/sprint-03/DEVOS-044.md`), so this is a from-scratch implementation choice, not a translation of a documented format. Kept deliberately simple (exact-match `action` + optional exact-match `condition` fields) rather than a general expression language, matching this codebase's existing precedent of hand-rolled minimal validators over heavyweight rule engines (`validateWorkflowGraph`, `validateAgentOutput`).
2. **Only the highest-version _published_ row per `key` governs evaluation; `DRAFT` policies are ignored entirely.** A draft is, by definition, not yet in effect — evaluating against an unpublished draft would let an unreviewed policy silently govern real decisions, contradicting "published policy versions are immutable" (§31) and the whole draft/publish distinction DEVOS-043 just built.
3. **Precedence: a specific rule match (any applicable policy) beats every policy's `defaultEffect`, which beats the evaluator's own global fallback.** Without this ordering, a policy with only a `defaultEffect` and no matching rule could accidentally override another policy's specific, intentional rule for the same action — an implementation choice, since nothing in the spec addresses cross-policy precedence at all.
4. **Global fallback (when literally no applicable policy addresses the action) is `ALLOW`, not `DENY`.** Explicitly flagged as an assumption: this POC's workflow already enforces its own hard-coded human gates (ADR-SCW-002's planning approval, independent of any policy), so a project with zero policies configured for a given action isn't left ungoverned by this evaluator alone — but defaulting unaddressed actions to `DENY` would risk silently blocking behavior no policy author ever intended to restrict, which is a worse failure mode for a POC where most actions have no policy defined yet.
5. **Lives in `packages/policy`, not `packages/domain`, unlike `Policy` itself.** Consistent with the sprint-wide package-boundary decision: `Policy` (the entity) belongs in `packages/domain`; the evaluation _algorithm_ is exactly the "genuinely algorithmic logic" `packages/policy` was scaffolded for (`specs/architecture/repository-code-structure.md` §17: "Policy evaluation must be deterministic and independent of model output").
6. **Not yet wired into any real decision point** (e.g., the planning approval gate, DEVOS-047). This task delivers a standalone, independently testable evaluator; DEVOS-047 is where a real gate first consumes a real evaluation decision — consistent with DEVOS-041/042's same "build the capability, wire it in when its actual consumer task arrives" pattern.
7. **Live-verified against real Postgres**: created and published a real policy (two rules plus a `defaultEffect`) through the real `PolicyRepository`, fetched it back, and ran the evaluator against the real, JSONB-round-tripped `definition` — confirmed correct `REQUIRE_APPROVAL` for a conditioned match, `ALLOW` for the same action under a non-matching condition, and `DENY` via `defaultEffect` for an unaddressed action. New unit tests (7 cases, including determinism and version-precedence). Full forced (no-cache) `pnpm turbo run typecheck lint test build` at 79/79; `pnpm format:check` clean.

## DEVOS-047 — Add Planning Approval Gate

1. **The gate is expressed by reusing the existing (previously unpopulated anywhere) `WorkflowDefinition.policies: string[]` field as a plain marker list** (`['planning-approval']` on the seeded planning-path workflow) — not a new boolean field, and not a real integration with DEVOS-044's policy evaluator. The evaluator has no rule language a marker-string check could meaningfully delegate to yet, and fully wiring it here would be a much larger integration than "add the gate" calls for; that remains explicit future work (already flagged in DEVOS-044/045's own decision entries). This is a from-scratch implementation choice, not a spec-mandated mechanism.
2. **The gate is enforced inside `maybeCompleteRun`** (`packages/database/src/repositories/task-queue.ts`), the exact existing function that already decides "have all this run's tasks succeeded → mark it COMPLETED." When the run's workflow version definition carries the marker, this function creates the approval request and transitions to `AWAITING_APPROVAL` instead of completing — inside the same transaction as the last task's completion, so there is no window where a run could observe a gated task suite as "all succeeded" without the gate having already fired.
3. **Evidence collection duplicates DEVOS-040's `retrieveArtifactsForRun` query logic as a raw, in-transaction query**, rather than calling into `packages/knowledge`. That package's retrieval functions take repository ports as parameters, not a `QueryExecutor`/transaction — composing them here would require constructing throwaway repository instances bound to the transaction, adding indirection for what is a 15-line query. Flagged as intentional duplication, not an oversight.

## DEVOS-048 — Add Uncertainty Handling

1. **Only `SUFFICIENT`/`INCOMPLETE` are implemented for context sufficiency — `Conflicting`/`Stale`/`Untrusted` are not.** `system-context-engineering-knowledge.md` §23 names five categories; this codebase only has a concrete, mechanically checkable signal for two of them: `buildContext()` either found at least one source or it found none. `Stale` (a freshness/expiry concept) and `Untrusted` (a trust-tier concept) have no data anywhere in this codebase to check against — no source records a freshness window or a trust level — so a check for them would invent a signal rather than surface a real one. Flagged explicitly rather than fabricated.
2. **"Conflicting" context is handled at the policy layer instead, as a genuinely mechanically-detectable case, not a context-builder one.** `evaluatePolicies` (DEVOS-044) previously picked the alphabetically-first matching policy key when more than one policy addressed the same action — an arbitrary, undocumented tie-break, exactly the "guessing" Domain Invariant §37.5 and the constitution's Principle 13 ("Fail Safely") warn against. Extended to collect _every_ matching policy for a request; if they disagree on effect, the result is a new `'CONFLICT'` decision value with `conflictingMatches` listing every policy and its effect, instead of silently resolving it. If they agree, behavior is unchanged (attributed to the first match, deterministically).
3. **Neither `assessContextSufficiency` nor policy-conflict detection is wired into any live call site** (`runAgentTask`, the approval decision flow, etc.). Consistent with this sprint's established pattern (DEVOS-041/044's own decision entries): `buildContext()` itself still isn't wired into the live agent-execution path, so wiring a sufficiency check on top of context that isn't actually being assembled for real executions would be checking a value nothing yet produces in production. Both capabilities are standalone, independently tested, and ready for a future integration task — not fabricated as already integrated.
4. **The required response text (`INSUFFICIENT_CONTEXT_MESSAGE`) is the literal string from Constitution Principle 2/13 and §23** ("I do not have enough information to determine this."), reused verbatim rather than paraphrased, and asserted verbatim in tests.
5. **Live-verified against real Postgres**, composed directly (both capabilities remain library-level, not HTTP endpoints): `assessContextSufficiency` against the real seeded project (SUFFICIENT) and an unknown project (INCOMPLETE, exact required message confirmed); `evaluatePolicies` against two real, published, genuinely conflicting policies created for this verification (one `ALLOW`, one `DENY`, same action) — confirmed `CONFLICT` with both policies correctly attributed. New unit tests (2 in `packages/knowledge`, 2 in `packages/policy`). Full forced (no-cache) `pnpm turbo run typecheck lint test build` at 79/79; `pnpm format:check` clean.
