## DEVOS-052 — Implement Tool Gateway

New `tool_invocations` table (migration `0023`) matching `specs/database/poc-database-schema.md` §14.2 exactly. New `ToolInvocation`/`ToolInvocationRepository` (`packages/domain/src/tools/tool-invocation.ts`) and a new `ToolInvocationStatus` contract type (`REJECTED`/`SUCCEEDED`/`FAILED` — PROVISIONAL, no enumeration is specified). A row is created exactly once, at chain completion, rather than as a PENDING-then-updated row: nothing in this sprint needs to observe an in-flight state, and it keeps the repository symmetric with `ToolCapabilityRepository`'s create-only shape.

The full chain from `specs/api/poc-api-contracts.md` §56 — Typed Validation → Project Scope → Policy → Capability Permission → Credential Resolution → Provider Adapter — is implemented as `invokeTool()` in `packages/tools/src/gateway/invoke-tool.ts`. One reconciliation against the spec's named order, logged rather than silently deviated from: `tool_invocations.tool_capability_id` is a required FK, so **no row can be recorded at all — including a Policy rejection — without the capability already resolved.** Capability lookup therefore happens immediately after Project Scope, ahead of the named "Capability Permission" step; Policy still evaluates using the capability's own `key` as the action, exactly as the chain names it, and "Capability Permission" remains the step that actually gates on the capability's `status`. A request that fails Typed Validation, Project Scope, or capability-key lookup itself (unknown key) is never recorded at all — those cases have no valid FK to record against and are surfaced to the caller as thrown errors (`ValidationError`/`NotFoundError`) instead.

DEVOS-044's policy evaluator is deliberately consulted here — closing the "not yet wired into any real decision point" gap `DEVOS-SPRINT3-DECISIONS.md` flagged for it. `evaluatePolicies` is called with `{action: capability.key, actorRole: membership.role, resourceType: 'TOOL_CAPABILITY'}`; anything other than `ALLOW` (`DENY`/`REQUIRE_APPROVAL`/`CONFLICT`) rejects with `DEVOS_TOOL_POLICY_<decision>`, with no dedicated tool-invocation approval-gate flow built for `REQUIRE_APPROVAL` (no such mechanism is specified; treating it as a rejection rather than fabricating an approval flow).

Credential Resolution is a deliberate no-op pass-through: no `Integration`/credential-broker mechanism exists yet (DEVOS-053). Provider Adapter is likewise not hardcoded to any real system — `ToolGatewayDeps.adapters` is an injected `Record<capabilityKey, ProviderAdapter>` map, empty in production until DEVOS-054 (Git adapter) and DEVOS-058 (PR creation) register real ones; invoking a capability with no registered adapter is itself a valid, recorded `FAILED` outcome (`DEVOS_NO_PROVIDER_ADAPTER`), not an error hidden from the caller. This keeps the gateway algorithm itself provider-agnostic, matching the Sprint-wide package-boundary split (gateway logic in `packages/tools`, provider mechanics in `packages/integrations`).

`resolveProjectScope` (`packages/tools/src/gateway/resolve-project-scope.ts`) is a deliberate local duplicate of `@devos/application`'s internal `resolveMembership` (not part of that package's public `index.ts` barrel) rather than a reach into its internals — a small, explicitly-commented duplication in exchange for respecting the package boundary.

New unit tests: `packages/tools/tests/invoke-tool.test.ts` (8 cases — success, no-adapter, adapter-throws, capability-disabled, policy-DENY, invalid-input, unknown-capability, non-member).

**Live-verified against real Postgres**: ran migration `0023`; created an isolated verification project (avoiding a leftover `defaultEffect: DENY` policy from DEVOS-044's own live-verification data still present in the shared seeded project — found during this task's verification, not a bug in this task's code, flagged as pre-existing verification-hygiene debt) and registered its capabilities; confirmed all four real-database outcomes: SUCCEEDED with a real (fake, non-network) adapter invoked and its output recorded; REJECTED on missing required input; FAILED with no adapter registered; REJECTED against a real, freshly-published DENY policy. Scratch script removed after use. Full forced (no-cache) `pnpm turbo run typecheck lint test build` run; `pnpm format:check` clean (after formatting the new gateway file) except the same pre-existing `pnpm-lock.yaml` warning. Marked COMPLETE. DEVOS-053 is next.

## DEVOS-053 — Implement Integration Credential Abstraction

New `integrations` table (migration `0024`) matching `specs/database/poc-database-schema.md` §13.1 exactly (`id`, `project_id`, `type`, `provider`, `name`, `status`, `configuration` JSONB, `created_at`, `updated_at`). New `Integration`/`IntegrationRepository` (`packages/domain/src/integrations/integration.ts`) and `IntegrationStatus` contract type (`ACTIVE`/`DISABLED`, mirroring `ToolCapabilityStatus`'s shape).

One spec-schema reconciliation, flagged per the task's own spec rather than silently resolved: §13.1's column list has **no `credential_reference` column**, despite `specs/api/poc-api-contracts.md` §33 requiring a "credential reference" as part of the Integration contract ("Credentials are references only"). Rather than adding an undocumented column, `credentialReference` is nested inside the one JSONB column the schema does provide (`configuration`) — a reference _name_ (e.g. `"GITHUB_TOKEN"`) is not itself secret material, so this doesn't violate §13.1's "Secrets are referenced through a secret-management mechanism and are not stored in this table as plaintext." The domain entity and application-layer CRUD still expose `credentialReference` as its own first-class field for ergonomics; only the database repository (`packages/database/src/repositories/integrations.ts`) knows it's actually nested inside `configuration` at the row level, splitting it back out on read and merging it back in on write.

`CredentialResolver` (`packages/integrations/src/credential-resolver.ts`) is the injected port `specs/architecture/repository-code-structure.md` §47 requires ("Provider adapters receive credentials through injected interfaces"). No secret-management mechanism is named or designed anywhere in the spec corpus, so `createEnvCredentialResolver()` resolves a reference from `process.env` by that same name — a direct generalization of the existing `GEMINI_API_KEY`-via-`@devos/config` precedent (DEVOS-027) to an arbitrary per-integration reference, not a secrets-manager integration; flagged as an implementation choice, exactly as the task's own spec anticipates. Placed at `packages/integrations`'s top level (not under a provider subfolder like `github/`) since it's provider-agnostic, mirroring how `@devos/agents`'s `AgentModelAdapter` port sits at that package's top level rather than under a specific provider.

CRUD in `packages/application/src/integrations/` (`createIntegration`, `getIntegrationForPrincipal`, `listIntegrationsForProject`) follows the same project-scoped, membership-gated pattern as every other CRUD use case in this codebase. No HTTP API route was added — same precedent as DEVOS-051's `tool_capabilities` (no route added there either): nothing in this task's acceptance criteria calls for one, and Integration records exist for DEVOS-054's Git adapter to consume internally, not for end-user CRUD yet.

New unit tests: `packages/application/tests/integrations.test.ts` (6 cases) and `packages/integrations/tests/credential-resolver.test.ts` (2 cases).

## DEVOS-054 — Implement Git Adapter

New `packages/integrations/src/github/` following the exact adapter-internal file structure `specs/architecture/repository-code-structure.md` §36 names: `github.client.ts` (the only place in the codebase that shells out to the real `git` CLI, via `execFile` — never `shell: true` — mirroring DEVOS-021's Windows-safe process-spawning precedent), `github.mapper.ts` (extracts a commit SHA from `git rev-parse` output), `github.schemas.ts` (validates the adapter's own _input_ shapes — there is no JSON "provider response" to validate here as there would be for an HTTP API, since Git itself is provider-agnostic and these operations talk to the local `git` binary, not GitHub's API), and `github.adapter.ts` (`openRepository`, `cloneRepository`, `createBranch`, `writeFileChange`, `createCommit`).

As the task's own spec flags: **no concrete GitHub API contract, and no `repositories`/`branches`/`commits` table or domain entity, exists anywhere** in the spec corpus. Because Git itself is provider-agnostic (a repository path/URL can be a real GitHub remote or a local path), the adapter's clone/open/branch/write/commit mechanics are implemented purely against the real `git` CLI with no GitHub-specific code at all — only PR creation (DEVOS-058) will actually be GitHub-API-specific, and that belongs in a separate module, not this one.

This task's own acceptance criterion is unusual among this sprint's tasks: "verified against a real local git repository (not a mock of the `git` CLI)." Since there is no fake/mock `git` client anywhere to bridge from, the automated test suite itself (`packages/integrations/tests/github-adapter.test.ts`) _is_ the live verification — a real throwaway repo is created via `mkdtemp` + real `git init` in a `beforeEach`, exercised through every adapter function, and torn down afterward, rather than a separate manual/scratch-script pass the way Postgres-backed tasks require. This is the user-authorized "local git repo only" scoping decision in concrete form: no real GitHub remote is contacted anywhere in this task.

One environment-dependent finding, not an adapter defect: cloning on Windows Git commonly runs with `core.autocrlf=true`, rewriting `LF` to `CRLF` on checkout — the clone test's assertion normalizes line endings before comparing rather than asserting an exact byte match, since the CRLF rewrite is correct git behavior on this platform, not something the adapter should suppress or correct.

The test fixture explicitly sets a local `user.email`/`user.name` via `git config` (not global) after `git init`, since a fresh throwaway repository — especially in a CI runner with no global git identity configured — would otherwise fail `git commit` with "Please tell me who you are." This is test-fixture setup, not the adapter's own responsibility: a real deployment is expected to already have git identity configured wherever the adapter runs.

No wiring into `packages/tools`'s `ProviderAdapter` interface (DEVOS-052) was done in this task — DEVOS-054's acceptance criteria are only about the adapter's own clone/open/branch/write/commit operations, not about plugging them into the Tool Gateway's `adapters` map. That composition is deferred to whichever later task actually exercises it end-to-end (likely DEVOS-057's development agent), avoiding a coupling `packages/integrations` → `packages/tools` that this task doesn't actually need.

New unit tests: `packages/integrations/tests/github-adapter.test.ts` (6 cases — open, reject-non-repo, branch+write+commit, clone), all against a real local git repository.

Full forced (no-cache) `pnpm turbo run typecheck lint test build`; `pnpm format:check` clean except the same pre-existing `pnpm-lock.yaml` warning. Marked COMPLETE. DEVOS-055 is next.

## DEVOS-055 — Implement Controlled Workspace

The thinnest task in the sprint, by its own spec: "workspace" appears in the spec corpus exactly once, as a negative constraint ("Development agent workspaces must not contain unrelated credentials," `specs/architecture/repository-code-structure.md` §47) — no entity, table, lifecycle state machine, or isolation mechanism (container, VM, git worktree) is specified anywhere. Every design choice here is an implementation-level assumption, flagged rather than presented as spec-derived.

`packages/integrations/src/workspace/development-workspace.ts` implements the assumption the task's own spec proposes: a workspace is a temporary local directory, scoped one-per-development-task (keyed by `WorkflowTaskId`), populated by cloning the target repository via DEVOS-054's `cloneRepository`, and removed afterward — mirroring this codebase's existing `mkdtemp`/`rm` temp-directory pattern (`@devos/storage`, `tests/e2e/*.test.ts`) rather than a heavier container-based isolation mechanism, consistent with the sprint's own "prefer modular monolith patterns" risk guidance.

"Must not contain unrelated credentials" is satisfied by construction, not by a runtime check: `createWorkspace` takes no `CredentialResolver` and reads no environment/secret material at all — there is simply nothing in the code path capable of writing a credential into the workspace, so the constraint holds trivially rather than needing to be verified after the fact.

"Reliably cleaned up whether the task succeeds or fails" is enforced mechanically via a `withWorkspace(workflowTaskId, repositoryUrlOrPath, fn)` helper wrapping the caller's work in a `try`/`finally`, rather than left as a convention every future caller has to remember to follow. `createWorkspace`/`destroyWorkspace` remain separately exported for callers needing more control over the lifecycle boundary.

Added `@devos/contracts` as a new dependency of `packages/integrations` (previously depended on nothing) purely for `WorkflowTaskId`'s branded type — a lightweight addition with no cycle risk, matching how every other package here uses contracts' branded IDs for scoping.

New unit tests: `packages/integrations/tests/development-workspace.test.ts` (5 cases — content-only-checkout, reliable removal, two-tasks-non-interfering, `withWorkspace` cleans up on success, `withWorkspace` cleans up on throw), all against a real local git repository and the real filesystem — same as DEVOS-054, this task's own test suite is its live verification; no separate scratch-script pass was needed.

Full forced (no-cache) `pnpm turbo run typecheck lint test build`; `pnpm format:check` clean except the same pre-existing `pnpm-lock.yaml` warning. Marked COMPLETE. DEVOS-056 is next.

## DEVOS-056 — Implement Repository Context

Repository Context as a _category_ is well-specified (`specs/architecture/system-context-engineering-knowledge.md` §10: repository structure, source directories, configuration, dependency info, relevant source files — "dynamic," and "an agent working on implementation should generally receive relevant repository information rather than an unbounded copy of the entire repository"), but the _retrieval mechanism_ is explicitly deferred: "This document does not decide: ... repository indexing technology; file chunking strategy; retrieval algorithms" (§39). Implemented as four new functions in `packages/knowledge/src/retrieval/` (`listRepositoryFiles`, `retrieveRepositoryListing`, `retrieveRepositoryFile`, `searchRepository`) — a direct bounded filesystem walk plus a plain substring search, explicitly not vector search/embeddings/indexing, exactly as the task's own spec anticipates.

Placed in `packages/knowledge` (not `packages/integrations`, despite depending conceptually on DEVOS-055's workspace) to keep the existing `RetrievedSource` shape and retrieval-function family in one place, and to avoid a new `knowledge` → `integrations` dependency the architecture's dependency-direction diagram doesn't show (`knowledge` and `tools` are documented as sibling leaves under `application`/`domain`; `integrations` isn't part of that fan-out at all). Every function therefore takes a plain `repositoryPath: string`, never a `DevelopmentWorkspace`, and a plain `revision: string` for the "tied to a specific revision" requirement (§28, Domain Invariant §37.9) — obtaining that revision (`git rev-parse HEAD`) is the caller's job, not something these functions do themselves, keeping `@devos/knowledge` free of any `git` dependency.

Bounding is enforced at two levels: `listRepositoryFiles` caps the total file count (default 200, `.git`/`node_modules`/`dist`/`.turbo` excluded from the walk entirely) and `retrieveRepositoryFile` caps bytes read per file (default 100,000), marking `truncated: true` rather than silently returning a partial file indistinguishable from a complete one. `searchRepository` reuses the same bounded listing and caps total matches (default 50), skipping unreadable files (binaries, permission errors) rather than surfacing them as search failures.

New unit tests: `packages/knowledge/tests/repository-context.test.ts` (6 cases — listing exclusions, file-count cap, RetrievedSource wrapping/revision-tagging, size-bounded read with truncation, substring search, match cap), all against a real temporary directory tree (no mocked filesystem).

**Live-verified end-to-end**: beyond the unit tests' plain directories, a scratch script composed a real DEVOS-055 workspace (`createWorkspace`, cloning a real local git repository) with this task's retrieval functions — confirmed the real cloned file list, a `RetrievedSource` correctly tagged with the real commit SHA, real file content read back byte-for-byte, and a real substring search match — proving the two packages compose correctly at runtime despite having no compile-time dependency on each other. Scratch script removed after use. Full forced (no-cache) `pnpm turbo run typecheck lint test build`; `pnpm format:check` clean except the same pre-existing `pnpm-lock.yaml` warning. Marked COMPLETE. DEVOS-057 is next.

## DEVOS-058 — Implement PR Creation Capability

New `PullRequestProvider` port (`packages/integrations/src/pull-requests/pull-request-provider.ts`) and its fake/local implementation, `createLocalPullRequestProvider()` — the only implementation built this sprint, per the user-authorized scoping decision this task's own spec restates explicitly. No concrete GitHub PR request/response schema, endpoint, or auth scope exists anywhere in the spec corpus, flagged rather than invented.

The capability key itself reuses DEVOS-051's already-registered `pull-request-create` (hyphenated, matching `repository-code-structure.md`'s own file-naming convention), not the dotted `git.pull_request.create` this task's spec quotes as `poc-api-contracts.md` §32's literal worked example — introducing a second, differently-named capability for the same operation would have fragmented the model `tool_capabilities` already persists; the existing key is reused instead, and the naming mismatch between the two specs is flagged here rather than silently resolved either way.

`createPullRequestProviderAdapter` (`packages/application/src/tasks/pull-request-provider-adapter.ts`) wires the provider into DEVOS-052's `ProviderAdapter` shape, mirroring DEVOS-057's `createGitProviderAdapters` for the same package-boundary reason. One implementation note: `ProviderAdapter.invoke` only receives `(target, parameters)`, not the invocation's own top-level `idempotencyKey` — since this capability's idempotency genuinely depends on that key reaching the provider, the caller is expected to also place it inside `parameters.idempotencyKey`, duplicating the top-level field rather than reopening DEVOS-052's already-complete `invoke-tool.ts` to thread it through generically.

## DEVOS-059 — Add Mutation Safety Controls

Neither "branch binding" nor "mutation safety" is a named mechanism anywhere in the spec corpus (this task's own spec states this explicitly) — idempotency itself is well-grounded (`poc-api-contracts.md`'s `Idempotency-Key` header and tool-contract `idempotencyKey` field; `poc-database-schema.md` §23's "idempotency strategy... possible mechanisms include: idempotency keys"; `software-change-workflow.md` §24's "Prevent repeated external side effects through idempotency"), but everything past "use an idempotency key" is this task's own from-scratch design, flagged rather than presented as spec-derived.

New `idempotency_key` column on `tool_invocations` (migration `0025`) and a new `getByCapabilityAndIdempotencyKey` repository method. **Deliberately no unique constraint** — unlike `workflow_runs`'s equivalent column (DEVOS-014), which does have one. A "branch binding violation" (see below) needs to persist a _second_ row sharing the same `(tool_capability_id, idempotency_key)` pair, documenting that the key was replayed with different parameters and rejected; a unique constraint would make that row impossible to insert. Real idempotent-replay detection is enforced in `invokeTool` itself (lookup-before-proceeding), not by the database — flagged as a deliberate deviation from the `workflow_runs` precedent, for a concrete, stated reason.

`invokeTool` (`packages/tools/src/gateway/invoke-tool.ts`) now looks up any existing invocation for `(capability, idempotencyKey)` immediately after capability resolution, before Policy even runs:

- If one exists and its recorded `target`/`parameters` match the new request exactly (`JSON.stringify` equality — a pragmatic, explicitly-flagged choice, not deep structural diffing) — this is a genuine retry. The original invocation is returned unchanged; no new row, no second call to the provider adapter, no re-running Policy/Capability Permission. An audit record is still written for this replay, referencing the _original_ invocation's id, since "every tool invocation... produces an audit record" covers the replay attempt itself even though it isn't a new invocation.
- If they don't match — the same key is being reused to authorise a _different_ mutation than it originally was — this is rejected as `DEVOS_TOOL_BRANCH_BINDING_VIOLATION`, recorded as a new `REJECTED` row (sharing the same idempotency key, which is exactly why no unique constraint exists), and audited as a `FAILURE`. This is the task's own "branch binding" language taken as broadly as the literal request (not narrowly as only the `branch` parameter) — any difference in `target` or `parameters` triggers it, on the reasoning that a from-scratch mechanism should err toward rejecting more mismatches, not fewer.

New `auditRecords: AuditRecordRepository` added to `ToolGatewayDeps` (from `@devos/domain`, which `packages/tools` already depends on — no new package dependency). Every exit path — REJECTED (policy/capability/input/branch-binding), FAILED (no adapter/adapter threw), and SUCCEEDED — now writes exactly one audit record, via a shared `recordAndAudit` helper so the persistence-plus-audit pairing can't be forgotten at a new call site. `actorType` is classified `SYSTEM`/`USER` via a small local copy of `packages/database`'s `SYSTEM_ACTOR_IDS` set (mirroring the same package-boundary reasoning as `resolveProjectScope`, DEVOS-052).

Updated every existing in-memory `ToolGatewayDeps`/`DevelopmentAgentTaskHandlerDeps` test fixture (`packages/tools/tests/invoke-tool.test.ts`, `packages/application/tests/pull-request-provider-adapter.test.ts`, `packages/application/tests/run-development-agent-task.test.ts`) to add the new repository method and an in-memory audit-records fake — none of these were "broken," they simply hadn't existed against this shape before. One test assertion from DEVOS-058 was corrected, not just updated: its comment ("the gateway itself doesn't yet dedupe invocations") described exactly the gap this task closes, so the assertion now correctly expects the same invocation id on replay instead of two separate ids — see DEVOS-058's own entry for why it wasn't rewritten there.

New unit tests: `packages/tools/tests/invoke-tool.test.ts` gained 2 cases (idempotent replay with adapter-call-count assertion, branch-binding violation) plus an audit-record assertion on the existing success case.

**Live-verified against real Postgres**: ran migration `0025`; a scratch script proved all three real-database outcomes on a real project — a first invocation SUCCEEDED and was recorded; an exact replay returned the _identical_ row (confirmed by id, and by the adapter's call count staying at one implicitly via the returned data matching); a same-key-different-branch replay was REJECTED with `DEVOS_TOOL_BRANCH_BINDING_VIOLATION` as a genuinely new row sharing the same `idempotency_key` value (proving the no-unique-constraint decision was necessary, not just theoretical); exactly one real `audit_records` row was written per `invokeTool` call (3 calls, 3 audit rows), including the replay. Scratch script removed after use. Full forced (no-cache) `pnpm turbo run typecheck lint test build`; `pnpm format:check` clean except the same pre-existing `pnpm-lock.yaml` warning. Marked COMPLETE. DEVOS-060 is next.

## DEVOS-061 — Development E2E

The last task in Sprint 4. Wires DEVOS-057's development agent into `apps/worker`'s dispatch table and a real workflow, folds PR creation into the same task (closing DEVOS-057/058's own deferral), and proves the whole chain end to end against real Postgres, a real spawned API process, a real spawned worker process, and a real local git repository.

**Not a fifth `planning-path` node.** An `Explore` investigation of `packages/database/src/repositories/task-queue.ts`'s `maybeCompleteRun`, `packages/application/src/workflows/run-creation.ts`, and `packages/database/src/repositories/approval-run-transition.ts` found that the current engine materializes every workflow task up front at run-creation time and only advances a run's approval gate once _every_ task in that run has succeeded — with no "unblock the next task after approval" concept anywhere in `createApprovalRunTransition`'s `APPROVED` branch, which unconditionally sets the run straight to `COMPLETED`. Appending development as a fifth node to the seeded `planning-path` graph would therefore block the planning-approval gate itself on development also succeeding, inverting the intended "approve the plan, then develop" order — a real engine constraint, not a matter of taste. Chose a genuinely separate seeded workflow instead: `SEED_DEVELOPMENT_PATH_WORKFLOW_*` (`packages/database/src/seed-constants.ts`, ids `...000017`/`...000018`, key `development-path`), one `AGENT_TASK` node (`agentRef: 'development-agent'`), no `policies` marker — there is nothing to gate, since this run's own single task is its last one. Consuming project's plan lookup was changed from run-scoped to project-scoped (`run-development-agent-task.ts`: `deps.artifacts.listForProject(run.projectId)`, filtered to `IMPLEMENTATION_PLAN`, sorted to the newest) — a development-path run has no relationship to the planning-path run that produced its plan beyond sharing a project.

**PR creation folded into `runDevelopmentAgentTask` itself**, not a separate task or workflow node — Stage 7's own "Expected activities" list (`specs/workflows/software-change-workflow.md` §17) includes "create a pull request where authorised" as part of the same stage, matching every other planning-path stage's one-task-per-stage shape. After the `git-commit` invocation succeeds, the task now also calls `invokeTool` for `pull-request-create` (target/source/destination branch, title from the model's `summary` or the commit message as a fallback, description from the commit message), and fails the task if that invocation doesn't succeed. The `CODE_CHANGE` artifact's metadata and the task's own return value both gained `pullRequestReference`. `DevelopmentAgentTaskHandlerDeps` (`packages/application/src/tasks/deps.ts`) gained `pullRequestProvider: PullRequestProvider`, and `gatewayDeps.adapters` now merges `createGitProviderAdapters` with a new `createPullRequestProviderAdapter(deps.pullRequestProvider)`.

**Three real bugs found during live verification, all fixed (none introduced by this task's own new code, but all blocking it):**

1. **`Artifact.createdAt` is typed `string` but arrives as a `Date` at runtime.** `b.createdAt.localeCompare is not a function` on the very first real run — pg's default type parser returns `timestamptz` columns as JS `Date` instances; nothing in `packages/database`'s repositories converts them to strings despite the domain type's contract, and no other call site in this codebase had ever called a string-only method on `createdAt` before. Flagged as pre-existing, repo-wide verification debt outside this task's scope (a proper fix would touch every repository's `toDomain` mapping, a much larger blast radius than DEVOS-061 warrants); fixed locally and narrowly in `run-development-agent-task.ts`'s own new plan-lookup sort, using `new Date(x.createdAt).getTime()` instead of `x.createdAt.localeCompare(...)` — correct whether the runtime value is a `Date` or a string.

2. **A third instance of this sprint's recurring cross-task verification-data pollution** (see DEVOS-052/057's entries for the first two): a policy left over from DEVOS-044's own live verification, `devos044-verify-release-approval`, `status: PUBLISHED`, `defaultEffect: 'DENY'`, with rules addressing only `release.deploy`. `evaluatePolicies` (`packages/policy`) falls through to a policy's `defaultEffect` for any action none of its rules address — this policy's blanket `DENY` default silently rejected `repo-write` (and would have rejected `git-commit`/`pull-request-create` too) for the entire seeded project, with no rule of its own ever matching those actions. Unlike the first two occurrences, this one couldn't be routed around by verifying against a fresh isolated project — the seeded `development-path`/`planning-path` workflow versions are fixed to `SEED_PROJECT_ID`. Fixed by having the new E2E test's `beforeAll` un-publish that one specific stray policy (`status: 'DRAFT'`, not deleted, so the row survives for history) before running — the same treatment already given to stray `ACTIVE` Git `Integration` rows there.

3. **`invokeTool`'s idempotency-replay comparison was key-order-sensitive.** `packages/tools/src/gateway/invoke-tool.ts` compared a persisted invocation's `target`/`parameters` against a fresh request's via plain `JSON.stringify(...) === JSON.stringify(...)` (DEVOS-059's own implementation). A genuine, byte-for-byte-identical retry of `repo-write` — the task queue retried the same task after an earlier attempt's `repo-write` call was rejected by bug #2 above — was itself then rejected as a `DEVOS_TOOL_BRANCH_BINDING_VIOLATION`, because Postgres's `jsonb` storage does not preserve the original object's key insertion order: the freshly constructed `parameters: { path, content, branch }` round-tripped back as `{ path, branch, content }`, and `JSON.stringify` is order-sensitive. This is a real bug in DEVOS-059's own code, invisible to its unit tests (which use an in-memory fake repository with no real `jsonb` round-trip) and only surfaced by this task's real-Postgres live verification. Fixed with a small recursive `stableStringify` helper (sorts object keys before serializing) used for both sides of the comparison; a real mismatch is still detected correctly, since sorting doesn't change value equality. New regression test in `packages/tools/tests/invoke-tool.test.ts` constructs a request with every key deliberately reversed and asserts it still replays as a match. This patches DEVOS-059's own mechanism after the fact — its entry above is left describing the code as originally written, per the same "don't retroactively rewrite a prior entry" convention DEVOS-058's entry already established.

New/updated unit tests: `apps/worker/tests/agent-task-router.test.ts` gained a case asserting the `development-agent` agentRef dispatches to `runDevelopmentAgentTask` (asserting on the specific "no `IMPLEMENTATION_PLAN` artifact" error it fails with first, given a deliberately minimal scenario — that function's own behavior is already exhaustively covered elsewhere); `packages/application/tests/run-development-agent-task.test.ts` gained the `pull-request-create` capability fixture and `pullRequestProvider` dependency, and its assertions now cover 3 successful tool invocations (`repo-write`, `git-commit`, `pull-request-create`) and a `pullRequestReference` on both the published artifact and the task's return value; `packages/tools/tests/invoke-tool.test.ts` gained the key-order regression case above.
